
Балансировка нагрузки (Load Balancing) в Nginx — это распределение входящих HTTP/HTTPS или TCP/UDP запросов между группой физических или виртуальных серверов (бэкендов).

В терминологии Nginx группа серверов называется **`upstream`** (апстрим) или пулом бэкендов. Nginx работает на седьмом уровне модели OSI (L7 / HTTP балансировка), что позволяет ему не просто пересылать пакеты, а анализировать заголовки, куки и URL перед отправкой запроса на конкретный сервер.


- **Upstream блок:**

```nginx
upstream backend {
	server 10.0.0.1:3000 weight=3;
	server 10.0.0.2:3000;
	server 10.0.0.3:3000 backup;
}
server {
	location / {
		proxy_pass http://backend;
	}
}
```

#### Все методы балансировки в Nginx

Nginx выбирает, на какой сервер отправить очередной запрос, руководствуясь одним из пяти встроенных алгоритмов:

##### 1) Round Robin (Циклический / По очереди)
- Метод по умолчанию. Запросы распределяются строго по очереди: первый запрос — на Сервер-1, второй — на Сервер-2, третий — на Сервер-3, затем цикл повторяется. Используется когда все бэкенды имеют абсолютно одинаковую мощность.

##### 2) Weighted Round Robin (Взвешенный карусельный)
- Модификация предыдущего метода с учетом «веса» (`weight`) каждого сервера. **Когда использовать:** Если серверы имеют разную мощность. Например, если вы выделили Мастеру-0 4 ядра CPU, а Мастеру-1 всего 2 ядра, вы можете сказать Nginx слать на первый сервер в два раза больше трафика.

##### 3) Least Connections (Наименьшее количество соединений)
- Запрос отправляется на тот сервер, который в данный момент обрабатывает меньше всего активных сетевых соединений. Nginx непрерывно мониторит счетчик сокетов каждого бэкенда. Идеален для тяжелых запросов, время обработки которых непредсказуемо (например, генерация сложных отчетов, скачивание файлов или долгие SQL-запросы). Это защищает один из серверов от «захлебывания» трафиком.
- **Директива:** `least_conn;`

##### 4) IP Hash (Привязка по IP-адресу клиента)
- Nginx берет IPv4-адрес клиента (первые 3 октета), прогоняет его через хэш-функцию и на основе результата намертво закрепляет этого клиента за конкретным бэкендом. Когда вашему приложению критически важна **сессионность (Stateful / Sticky Sessions)**. Например, если пользователь залогинился на Сервере-1 и положил товар в корзину, а его сессия хранится в локальной памяти этого сервера (а не в Redis), то при использовании Round Robin следующий клик улетит на Сервер-2, и корзина «обнулится». `ip_hash` гарантирует, что пользователь останется на Сервере-1.
- **Директива:** `ip_hash;`

##### 5) Generic Hash (Пользовательский хэш)
- Вы сами определяете текст или встроенную переменную Nginx, на основе которой будет рассчитываться хэш для выбора сервера. Для продвинутого кэширования или микросервисов. Например, можно балансировать по URL-адресу (`hash $request_uri;`) или по кастомному заголовку.
- **Директива:** `hash ...;`

#### Директивы контекста `upstream`

```nginx
upstream go_cluster {
    # 1. Задаем алгоритм (если пустая строка — включится Round Robin)
    least_conn; 

    # 2. Описание серверов пула и их флагов
    server 192.168.100.11:8080 weight=3 max_fails=3 fail_timeout=10s;
    server 192.168.100.12:8080 max_fails=2 fail_timeout=15s;
    
    # 3. Сервер в режиме ожидания (Включится только если умрут ВСЕ остальные)
    server 192.168.100.13:8080 backup;
    
    # 4. Временно выведенный из балансировки сервер (для техработ)
    server 192.168.100.14:8080 down;

    # 5. Пул постоянных соединений с бэкендами (Keep-Alive)
    keepalive 32;
}

```

Подробный разбор флагов директивы `server`:

- **`weight=N`** — вес сервера (по умолчанию `1`). Сервер с весом `3` получит в три раза больше запросов, чем сервер с весом `1`.
- **`max_fails=N`** — пассивный Health Check (проверка здоровья). Сколько раз подряд бэкенд должен ответить ошибкой (например, `502`, `504` или таймаутом TCP), чтобы Nginx посчитал его «мертвым». По умолчанию равен `1`.
- **`fail_timeout=Время`** — работает в паре с `max_fails`.
    1. Время, в течение которого должны накопиться ошибки (например, 3 ошибки за 10 секунд).
    2. Время, на которое Nginx полностью исключит этот сервер из балансировки (в нашем примере на 10 секунд трафик на `.11` идти не будет вообще, давая серверу возможность перезагрузиться).
- **`backup`** — помечает сервер как резервный. На него не упадет ни один пакет, пока живы основные серверы. Идеально для развертывания страниц заглушек («Сайт на техработах»).
- **`down`** — принудительно переводит сервер в статус офлайна. Помогает админу временно остановить трафик на ноду, чтобы обновить там код, не удаляя строку из конфига и не ломая хэширование.

Директива `keepalive N`

Это важнейшая оптимизация производительности. По умолчанию Nginx для каждого чиха клиента открывает новое TCP-соединение с бэкендом, а после отдачи ответа — закрывает его. Директива `keepalive 32;` заставляет Nginx **держать 32 сетевых сокета с бэкеьприложением постоянно открытыми**. Запрос клиента прилетает в Nginx, тот берет уже готовый открытый сокет и мгновенно пробрасывает пакет в Go. Это снижает нагрузку на CPU бэкенда и убирает задержки на сетевой handshake.


#### Директивы контекста `location`

```nginx
location /api/ {
    proxy_pass http://go_cluster;

    # 1. При каких условиях Nginx имеет право перенаправить запрос на СЛЕДУЮЩИЙ сервер пула
    proxy_next_upstream error timeout http_500 http_502 http_503;

    # 2. Ограничение по времени на попытки спасти запрос
    proxy_next_upstream_timeout 5s; # Если за 5 секунд не нашли живой бэкенд — выдать ошибку клиенту
    proxy_next_upstream_tries 3;    # Пробовать не более 3 серверов из пула для одного запроса
}
```

`proxy_next_upstream`:

Если пользователь отправил запрос, и Round-Robin выбрал Сервер-1, но Сервер-1 упал в ошибку `502 Bad Gateway`, благодаря этой директиве **Nginx прозрачно для пользователя перехватит эту ошибку, заберет запрос и тут же переотправит его на Сервер-2**. Клиент в браузере даже не заметит, что один из ваших серверов только что погиб — страница просто загрузится как обычно.
