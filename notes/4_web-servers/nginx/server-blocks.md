**Server Blocks** в Nginx (в мире Apache их по старинке называют **Виртуальными хостами / Virtual Hosts**) — это фундаментальный механизм, который позволяет на одном физическом сервере (или одной виртуалке Proxmox) независимо размещать и обслуживать **сотни разных сайтов и доменов**.

Клиенты обращаются на один и тот же IP-адрес вашего сервера, но Nginx на лету понимает, кому какой сайт показать, анализируя заголовки сетевых пакетов 7-го уровня (HTTP).

Когда пакет прилетает из интернета или локальной сети на порт `80` или `443`, ядро Nginx использует двухэтапный алгоритм выбора правильного блока `server`:

Этап 1. Сверка по IP и Порту (`listen`)

Nginx ищет блоки `server`, у которых директива `listen` максимально точно соответствует параметрам сетевого сокета, на который пришел пакет.
- Если пришел пакет на порт 443, все блоки с `listen 80` мгновенно отбрасываются.


Этап 2. Сверка по имени домена (`server_name`) — Главная магия

Если порты одинаковые (например, три сайта сидят на `listen 443`), Nginx врезается в заголовки HTTP-запроса (L7) и ищет строчку **`Host`** (например, `Host: app.kubernetes.local`), которую туда записал ваш браузер.
- Nginx сравнивает текст из заголовка `Host` со значениями директив `server_name` в оставшихся блоках. При совпадении пакет передается внутрь этого хоста.

Что если домен не совпал ни с чем? (Дефолтный сервер)

Если клиент ввел в браузер голый IP-адрес (`https://192.168.100.10`) или домен, которого нет в конфигах, Nginx перенаправит запрос в **дефолтный блок** (Default Server). По умолчанию дефолтным считается **самый первый по порядку чтения конфигурационный файл**

---

#### Разбор основных директив


- **Пример:**

```nginx
server {
    # 1. СЕТЕВОЙ СЛОЙ (На каком порту ловить пакеты)
    listen 443 ssl;
    listen [::]:443 ssl; # Включаем поддержку IPv6, чтобы роботы не спотыкались
    
    # Флаг default_server делает этот блок главным. 
    # Сюда прилетит любой "чужой" или неопознанный домен.
    # listen 443 ssl default_server; 

    # 2. ДОМЕННЫЙ СЛОЙ (На какие имена откликаться)
    server_name app.kubernetes.local www.app.kubernetes.local;

    # 3. КРИПТОГРАФИЧЕСКИЙ СЛОЙ (Паспорт именно этого домена)
    ssl_certificate     /etc/nginx/ssl/app.kubernetes.local.crt;
    ssl_certificate_key /etc/nginx/ssl/app.kubernetes.local.key;
    
    # 4. ФАЙЛОВЫЙ СЛОЙ (Где искать статику на SSD, если не сработает прокси)
    root /var/www/app_site;
    index index.html index.htm;

    # 5. СЛОЙ ОГРАНИЧЕНИЙ И БЕЗОПАСНОСТИ (Индивидуально для этого сайта)
    client_max_body_size 5m;       # Больше 5 МБ файлы на этот сайт заливать нельзя
    keepalive_timeout 30;          # Закрывать ленивые сокеты через 30 сек

    # 6. СЛОЙ ИНДИВИДУАЛЬНЫХ ЛОГОВ (Для изоляции аналитики)
    access_log /var/log/nginx/app_access.log production;
    error_log  /var/log/nginx/app_error.log warn;

    # 7. МАРШРУТИЗАЦИЯ (Локации)
    location / {
        try_files $uri $uri/ =404;
    }
}
```

Директива `server_name` поддерживает не только точечные имена сайтов, но и мощные маски (Wildcards), а также регулярные выражения:

1. **Точное совпадение:** `server_name vmlinuz.ru;`
2. **Маска с начала (Wildcard):** `server_name *.vmlinuz.ru;`
    - Поймает `blog.vmlinuz.ru`, `shop.vmlinuz.ru`, но не поймает голый `vmlinuz.ru`.
3. **Маска с конца:** `server_name mail.*;`
    - Поймает `mail.ru`, `mail.com`, `mail.local`.
4. **Специальная маска (Два в одном):** `server_name .vmlinuz.ru;`
    - Точка в начале — это шорткат в Nginx. Эта строка идентична записи: `server_name vmlinuz.ru *.vmlinuz.ru;`. Идеальный стандарт для обычных сайтов.

Приоритет проверки имен (Если домен подходит под несколько правил). Если вы написали много серверов, Nginx сверяет их в строгом порядке:

1. Точное совпадение.
2. Самая длинная маска в начале (например, `*.sub.vmlinuz.ru` важнее, чем `*.vmlinuz.ru`).
3. Самая длинная маска в конце.
4. Регулярные выражения (в порядке их появления в конфигурационных файлах)


#### Продакшн-приёмы работы с Server Blocks

В реальной практике используют Server blocks не только для хостинга сайтов, но и для защиты периметра.

Приём 1. Сброс «левого» трафика (Защита от сканеров портов)

Боты-сканеры непрерывно сканируют интернет, стучась на ваш IP-адрес без указания домена. Чтобы они не тратили ресурсы процессора и не читали ваши SSL-сертификаты, в самый верх конфигов вешают **«Глухой» дефолтный сервер-заглушку**:

```nginx
server {
    listen 80 default_server;
    listen 443 ssl default_server;
    server_name _; # Символ подчеркивания означает "любое имя"
    
    # Подсовываем боту любой фейковый или просроченный сертификат, 
    # чтобы просто запустить порт 443
    ssl_certificate     /etc/nginx/ssl/fake.crt;
    ssl_certificate_key /etc/nginx/ssl/fake.key;

    # 444 — это специальный кастомный код ответа Nginx (No Response).
    # Nginx не будет тратить трафик на отправку HTML-ошибки, а просто 
    # мгновенно разорвет TCP-сокет, выкинув бота.
    return 444; 
}
```

Приём 2. Идеальный редирект на красивое имя (Склеивание зеркал)

Чтобы SEO-оптимизация не страдала, сайт должен открываться строго по одному имени. Если пользователь пишет `www.app.kubernetes.local`, его нужно бесшовно перекинуть на чистый домен:

```nginx
server {
    listen 443 ssl;
    server_name www.app.kubernetes.local;
    
    ssl_certificate     /etc/nginx/ssl/app.crt;
    ssl_certificate_key /etc/nginx/ssl/app.key;

    # Переменная $request_uri бережно сохранит весь путь (например /api/v1/stats)
    return 301 https://kubernetes.local$request_uri;
}
```
