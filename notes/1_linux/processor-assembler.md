### Как инструкции попадают к процессору

> Термины:

- **RIP (Relative Instruction Pointer / Указатель Инструкций)** — это один из самых важных регистров процессора в 64-битной архитектуре x86-64.
	Простыми словами, **RIP — это «курсор» процессора**, который указывает на текущее место в программе. В нем всегда хранится **адрес памяти следующей инструкции**, которую процессор должен выполнить.
	
	Когда компьютер работает, он выполняет бесконечный цикл:
	1. Считать инструкцию по адресу, на который указывает **RIP**.
	2. Изменить **RIP** так, чтобы он указывал на _следующую_ инструкцию (сдвинуть курсор на длину только что считанной команды).
	3. Выполнить считанную инструкцию.
	4. Повторить


Процессор — это цифровая схема. У него есть:
- **Регистры**: быстрая память внутри ядра. На x86-64: `rax`, `rbx`, `rcx`, `rdx`, `rsi`, `rdi`, `rbp`, `rsp`, `r8`–`r15`, `rip`, `rflags`, плюс сегментные, плюс векторные `xmm`/`ymm`/`zmm`.
- **Блок выборки (fetch unit)**: читает байты из памяти по адресу `RIP`.
- **Декодер**: превращает байты в микрооперации (µops).
- **Исполнительные блоки**: ALU, FPU, load/store, branch.
- **Кэши**: L1I (инструкции), L1D (данные), L2, L3.
- **MMU**: переводит виртуальные адреса в физические через page tables.
- **Таблицы прерываний**: IDT на x86, vector table на ARM.

Процессор **не понимает** ни C, ни Python, ни «ассемблер». Он понимает только байты, закодированные по его ISA. Процессор не читает файлы с диска. Он читает инструкции из памяти по адресу, который лежит в регистре-указателе команд: `RIP` на x86-64, `PC` на ARM.

```
высокие адреса
+------------------+
|     stack        |  растёт вниз
+------------------+
|        |         |
|      heap        |  растёт вверх
+------------------+
|  .bss            |  нулевые данные
+------------------+
|  .data           |  инициализированные данные
+------------------+
|  .rodata         |  константы
+------------------+
|  .text           |  КОД (read + execute)
+------------------+
низкие адреса
```

`RIP` указывает на точку входа в `.text`.


Что делает ОС, когда вы запускаете программу:
1. Оболочка или GUI просит ядро создать процесс.
2. Ядро открывает исполняемый файл: ELF в Linux, PE в Windows.
3. Загрузчик читает заголовки, смотрит сегменты:
    - `.text` — код, обычно read + execute;
    - `.data` — глобальные данные;
    - `.bss` — нулевые данные;
    - stack, heap.
4. Создаётся виртуальное адресное пространство процесса.
5. Сегменты отображаются в память через [[virtual-memory|page tables]].
6. Если есть динамические библиотеки, запускается динамический линкер: подгружает `libc.so`, `libm.so` и т.п., делает релокации.
7. Ядро устанавливает `RIP` на точку входа: обычно `_start`, которая потом вызывает `__libc_start_main`, а та — `main`.
8. Процессор начинает цикл:
	- **Fetch**: MMU переводит виртуальный `RIP` в физический адрес, кэш L1I отдаёт байты. Процессор читает несколько байт вперёд.
	- **Decode**: определяется, какая это инструкция, какие у неё операнды, длина. x86 — переменная длина (1–15 байт), ARM — фиксированная (4 байта), RISC-V — переменная.
	- **Execute**: инструкция выполняется в соответствующем блоке. Результат пишется в регистр или память.
	- **Update RIP**: либо `RIP += длина`, либо переход по новой ветке.

>**На современных процессорах это не последовательно, а конвейер и out-of-order:**

- **Pipeline**: несколько инструкций одновременно на разных стадиях.
- **Superscalar**: за такт декодируется и исполняется несколько инструкций.
- **Out-of-order execution**: инструкции переставляются динамически, лишь бы зависимости соблюдались.
- **Register renaming**: физические регистры подменяются, чтобы убрать ложные зависимости.
- **Branch prediction**: процессор угадывает, куда пойдёт ветвление, и заранее грузит код. Если угадал — нет задержки, если нет — pipeline flush.
- **Speculative execution**: процессор исполняет «на всякий случай» вперёд. Именно это эксплуатировали Spectre/Meltdown.


>**Код может подгружаться с диска не сразу, а по страницам (demand paging):** 

1. Процессор пытается прочитать байт по адресу.
2. MMU не находит страницу в page tables или видит, что она не в памяти.
3. Возникает **page fault**.
4. Управление переходит в ядро.
5. Ядро находит страницу в файле (ELF) или в swap.
6. Загружает её в физическую память.
7. Обновляет page tables.
8. Возвращает управление, процессор повторяет инструкцию.

С точки зрения программы это незаметно. С точки зрения процессора — обычный доступ к памяти после обработки fault.

### Регистры процессора и как программа туда попадает

[[program-compilation_assembler|Компилятор сам решает]], что и где будет лежать. Это не делает операционная система и не делает процессор. Правила взаимодействия функций называются **calling convention**. На Linux x86-64 используется **System V AMD64 ABI**:

В x86-64 есть несколько групп регистров:
- **Регистры общего назначения (GPR)** — 16 штук по 64 бита.
- **Указатель команд** — `rip`.
- **Флаги** — `rflags`.
- **Сегментные** — `cs`, `ds`, `ss`, `es`, `fs`, `gs` (в основном legacy, кроме `fs`/`gs`).
- **Векторные** — `xmm` (128), `ymm` (256), `zmm` (512), плюс `mm` (MMX, legacy).
- **Регистры FPU** — `st0`–`st7` (x87, legacy).
- **Служебные/системные** — `cr0`–`cr8`, `dr0`–`dr7`, `msr` (доступны только из ring 0).

#### Регистры общего назначения

16 регистров по 64 бита. У каждого есть младшие части разного размера — это наследие 8086/80386.

|64|32|16|8 (low)|8 (high)|Традиционное назначение|
|---|---|---|---|---|---|
|rax|eax|ax|al|ah|аккумулятор, возврат из функции, номер syscall|
|rbx|ebx|bx|bl|bh|callee-saved, исторически база для `xlat`|
|rcx|ecx|cx|cl|ch|счётчик циклов `loop`, 4-й аргумент|
|rdx|edx|dx|dl|dh|3-й аргумент, старшая часть при умножении/делении|
|rsi|esi|si|sil|—|source index, 2-й аргумент|
|rdi|edi|di|dil|—|destination index, 1-й аргумент|
|rbp|ebp|bp|bpl|—|base pointer, frame pointer|
|rsp|esp|sp|spl|—|stack pointer|
|r8|r8d|r8w|r8b|—|5-й аргумент|
|r9|r9d|r9w|r9b|—|6-й аргумент|
|r10|r10d|r10w|r10b|—|caller-saved, временный|
|r11|r11d|r11w|r11b|—|caller-saved, временный|
|r12|r12d|r12w|r12b|—|callee-saved|
|r13|r13d|r13w|r13b|—|callee-saved|
|r14|r14d|r14w|r14b|—|callee-saved|
|r15|r15d|r15w|r15b|—|callee-saved|

Особенности:

- `rax`–`rdx` имеют «высокие» 8-битные половины (`ah`, `bh`, `ch`, `dh`). У `r8`–`r15` их нет — только `r8b` и т.д.
- При записи в 32-битный регистр (`eax`) **старшие 32 бита обнуляются**. Это важно: `mov eax, 1` очищает `rax` целиком.
- При записи в 16- или 8-битный регистр старшие биты **не трогаются**.
- `rsp` и `rbp` лучше не использовать для произвольных нужд: `rsp` — стек, `rbp` — кадр стека (если компилятор его не оптимизировал в `-fomit-frame-pointer`).

#### Что значит caller-saved / callee-saved

По System V AMD64 ABI:
- **Caller-saved** (volatile): `rax`, `rcx`, `rdx`, `rsi`, `rdi`, `r8`–`r11`. Вызывающий сам сохраняет их, если они ему нужны после `call`.
- **Callee-saved** (non-volatile): `rbx`, `rbp`, `r12`–`r15`, `rsp`. Функция обязана восстановить их перед `ret`, если она их испортила.
    
Это не аппаратное свойство, а **договорённость** компиляторов и ОС. Процессор разницы между регистрами не делает.

#### Указатель команд и флаги

- **`rip`** — адрес следующей инструкции. Прямо менять нельзя (кроме `jmp`/`call`/`ret`/`iret`). Можно читать через `lea rax, [rip]`.
- **`rflags`** — флаги. Основные:
    - `ZF` (zero) — результат 0;
    - `SF` (sign) — знак;
    - `CF` (carry) — перенос;
    - `OF` (overflow) — переполнение со знаком;
    - `PF` (parity), `AF` (auxiliary carry) — редко;
    - `DF` (direction) — направление для строковых инструкций;
    - `IF` (interrupt enable) — разрешение прерываний;
    - `TF` (trap) — пошаговая отладка.

#### Сегментные регистры

- `cs` — code segment;
- `ds`, `es`, `ss` — data/extra/stack;
- `fs`, `gs` — специальные, используются для thread-local storage и ядра (например, `gs` в Linux x86-64 указывает на per-CPU данные ядра, `fs` — на TLS в user space). В Linux есть макрос `current`, который указывает на структуру текущего выполняющегося процесса (`struct task_struct`, и для этого его привязывают к регистру `gs`)

В long mode сегментация почти отключена: `cs`, `ds`, `es`, `ss` фиксированы, реально работают только `fs` и `gs`.

#### Векторные регистры

- **`xmm0`–`xmm15`** (128 бит) — SSE, скалярные float/double, SIMD.
- **`ymm0`–`ymm15`** (256 бит) — AVX; младшие 128 бит совпадают с `xmm`.
- **`zmm0`–`zmm31`** (512 бит) — AVX-512; младшие 256 бит совпадают с `ymm`.
- **`st0`–`st7`** — x87, почти не используется в новом коде.
- **`mm0`–`mm7`** — MMX, legacy, алиасы x87.

По ABI первые 8 float-аргументов идут в `xmm0`–`xmm7`, возврат — в `xmm0`.

#### Системные регистры (только ring 0)

- **`cr0`** — режимы CPU: paging, protected mode, FPU.
- **`cr2`** — адрес, вызвавший page fault.
- **`cr3`** — физический адрес корня page tables (смена = смена адресного пространства).
- **`cr4`** — расширения: PAE, SSE, VMX и т.д.
- **`cr8`** — TPR (task priority) для APIC.
- **`dr0`–`dr7`** — точки останова (debug).
- **MSR** — model-specific registers, читаются/пишутся через `rdmsr`/`wrmsr`. Пример: `IA32_LSTAR` хранит адрес обработчика `syscall`.

Условные переходы (`je`, `jne`, `jg`, ...) читают именно эти флаги.

Пример:

```c
int add(int a, int b) {
    return a + b;
}
```

Компилируется в:

```asm
add:
    lea  eax, [rdi + rsi]   ; a в edi, b в esi, результат в eax
    ret
```

Вот как данные попадают в регистры: компилятор сгенерировал код, где аргументы приходят в `edi` и `esi`, потому что так велит ABI. Вызывающая сторона перед `call` положила их туда.

Регистры не «закладываются» динамически в момент запуска. Это статическое решение компилятора: «здесь мы используем `rax`, здесь `rdi`». При переключении контекста ОС сохраняет и восстанавливает их.

#### При `call` (машинная инструкция) процессор:

1. Кладёт адрес следующей инструкции (`RIP` после `call`) на стек — это адрес возврата.
2. Загружает в `RIP` адрес вызываемой функции.
3. Всё, дальше процессор продолжает исполнять код уже с нового адреса, всё ещё в user mode.

Функция обычно делает **пролог**:

```asm
push rbp
mov  rbp, rsp
sub  rsp, N     ; место под локальные переменные
```

И **эпилог**:

```asm
leave           ; mov rsp, rbp; pop rbp
ret             ; pop rip
```

Локальные переменные лежат на стеке по смещениям от `rbp`. Компилятор знает эти смещения. Именно поэтому `-O0` код полон обращений вида `mov [rbp-4], eax`.


#### Процессор сам по себе исполняет один поток за раз. Многозадачность делает ОС.

Планировщик (scheduler) — часть ядра. Его задача — решать, какой поток/процесс получит CPU следующим.

Как это работает:
>1. Поток исполняется в user mode.
>2. Происходит **прерывание по таймеру** (обычно каждые 1–10 мс). Аппаратный таймер посылает сигнал.
>3. Процессор переключается в kernel mode, сохраняет текущий `RIP`, `RSP`, `RFLAGS`, регистры на стек ядра.
>4. Ядро вызывает обработчик прерывания, который вызывает планировщик.
>5. Планировщик смотрит:
    - кто готов к запуску (runnable);
    - приоритеты;
    - политику (CFS, real-time, SCHED_IDLE);
    - квант времени;
    - привязку к ядрам (affinity).
>6. Выбирает следующий поток.
>7. Выполняет **context switch**:
    - сохраняет состояние текущего потока в его PCB (process control block) / TCB:
	    - `RIP` — где остановились;
		- `RSP` — стек;
		- `RFLAGS` — флаги;
		- регистры общего назначения: `rax`, `rbx`, `rcx`, `rdx`, `rsi`, `rdi`, `rbp`, `r8`–`r15`;
		- регистры FPU/SSE/AVX, если используются;
		- состояние MMU: указатель на page tables (`CR3` на x86);
		- служебное: приоритет, состояние (running/ready/waiting), счётчики.
		Всё это лежит в структуре ядра: `task_struct` в Linux.
    - загружает состояние следующего;
    - переключает адресное пространство, если это другой процесс (смена `CR3` на x86 — смена page tables);
    - переключает стек ядра.
>8. Возвращается из прерывания.
	После того как планировщик выбрал новый поток:
		1. Ядро восстанавливает его регистры из сохранённого состояния.
		2. Выполняет инструкцию `iret` (x86) или `eret` (ARM).
		3. Процессор возвращается в user mode.
		4. `RIP` указывает на то место, где поток был прерван ранее.
		5. Поток продолжает исполняться, как будто ничего не произошло.
	С точки зрения потока — он просто работал, и вдруг продолжил работать. Всё, что между — invisible.
>9. Процессор продолжает исполнять новый поток.


#### Переключение потоков vs процессов

**Поток (thread)**:
- имеет свой стек, регистры, `RIP`, `RSP`, локальные переменные;
- делит адресное пространство с другими потоками того же процесса;
- context switch дешевле: не нужно менять page tables.

**Процесс**:
- имеет своё адресное пространство;
- смена процесса включает смену `CR3` и, как следствие, сброс TLB (translation lookaside buffer) или его пометку;
- context switch дороже.

На x86-64 состояние задачи хранится в TSS (task state segment) и структурах ядра. Современные ОС не используют аппаратный `task switch` x86, а делают software context switch.


#### Аппаратные прерывания процессора

Это одна из самых фундаментальных и красивых инженерных тем в компьютерных науках — **вытесняющая многозадачность (Preemptive Multitasking)** и аппаратная независимость операционной системы.

Физически "метрономом процессора" **называется системный таймер** (в современных x86-64 процессорах это чаще всего **APIC Timer** или **HPET**).

Чтобы программа (включая код ядра ОС) могла выполнить хоть одно действие (например, проверить время или переключить поток), её код **должен физически выполняться на процессоре прямо сейчас**. В регистре `RIP` должен стоять адрес инструкции этой программы.

Если представить ситуацию: на процессоре запущен бесконечный цикл `while(true) {}`.

- В этот момент регистр `RIP` указывает на код цикла.
- Процессор с огромной скоростью щелкает инструкции.
- **Код ядра ОС в этот момент в процессоре НЕ выполняется.** Операционная система сейчас — это просто пассивный набор байт, лежащий в оперативной памяти.

Если бы не было внешнего «будильника», цикл могл бы захватить процессор навсегда. Ядро ОС физически не смогло бы проснуться, чтобы выбрать к выполнению другой поток. У ядра просто нет своего отдельного параллельного «скрытого сознания», если ядро не запущено на физическом ядре процессора, оно мертвее мертвых.

Чтобы вернуть контроль операционной системе, используется **аппаратное прерывание от таймера**.

1. На материнской плате или внутри самого процессора есть независимый кристалл-таймер. Ядро ОС при старте настраивает его на определенный промежуток (4мс).
2. Программа работает. Проходит 4 мс.
3. Таймер подает физический электрический сигнал на специальную ножку процессора (линейку прерываний).
4. **Процессор аппаратно (на уровне транзисторов) замирает.** Он не спрашивает разрешения у запущенной программы. Он мгновенно сохраняет текущий `RIP` программы и её регистры в системный стек.
5. Процессор принудительно переключает режим работы из User Mode в Kernel Mode (Ring 0) и перезаписывает `RIP`, отправляя его на адрес **Обработчика прерываний таймера (Timer Interrupt Handler)**.

Только в этот момент **ядро ОС просыпается**. И делает оно это благодаря аппаратному «пинку» от процессора и таймера.

Проснувшись от прерывания таймера, ядро ОС запускает свой **Планировщик задач (Scheduler)**. Вот тут-то и вступает в силу **`nice`** — [[processes-jobs|индекс вежливости процесса, от -20 до +19]] ).

1. Планировщик смотрит на текущий поток, который только что прервали.
2. Он уменьшает его доступный квант времени (Time Slice).
3. Он заглядывает в свою таблицу потоков и вычисляет, у кого из них сейчас наивысший приоритет (учитывая `nice` — чем более «вежлив» процесс, тем охотнее он уступает место другим).
4. Если планировщик решает, что пора дать поработать браузеру:
    - Он сохраняет контекст игры (все регистры, включая `RIP`) в структуру данных игры.
    - Он достает сохраненный контекст браузера.
    - Он загружает регистры браузера в физические регистры процессора.
5. Инструкция `iret` (Interrupt Return) возвращает процессор в режим пользователя, и процессор начинает выполнять браузер с того места, где тот когда-то остановился.

### Системные вызовы и «повышение полномочий»

Вот тут важно не ошибиться.

Скомпилированная программа **не повышает себе полномочия произвольно**. Она может выполнить специальную инструкцию `syscall` на x86-64 или `svc` на ARM. Это аппаратный механизм перехода в ядро.

Упрощённо на Linux x86-64:

```asm
mov eax, 1      ; номер syscall: write
mov edi, 1      ; fd = stdout
mov rsi, buf    ; указатель на данные
mov edx, 3      ; длина
syscall
```

Что происходит:

1. Программа в user mode, ring 3.
2. Кладёт номер системного вызова и аргументы в регистры.
3. Выполняет `syscall`.
4. Процессор переключается в kernel mode, ring 0.
5. Управление переходит на заранее заданный обработчик ядра.
6. Ядро проверяет номер вызова, права процесса, аргументы, указатели.
7. Если всё можно — выполняет операцию: пишет в файл, выделяет память, открывает сокет и т.д.
8. Возвращается в user mode.
9. Программа продолжает работу уже снова в ring 3.

То есть `syscall` — это **не «сделай меня root»**. Это «попроси ядро выполнить привилегированную операцию». Ядро остаётся привилегированным. Процесс остаётся непривилегированным. Если ядро разрешит операцию — она выполняется от имени ядра, но права процесса при этом не становятся ring 0.

`root` в Linux — это тоже не ring 0. Это UID 0, то есть учётная запись, которой ядро разрешает больше операций. Но даже root-процесс в user space выполняется в ring 3 и всё равно ходит в ядро через syscall.

#### Syscall — это добровольный переход в ядро. Прерывание — вынужденный.

Оба механизма приводят к одному: ядро получает управление, может решить, что делать, и вернуть управление в user mode.

Syscall часто становится точкой, где планировщик может переключить поток: например, поток заблокировался на чтении с диска, ядро переводит его в состояние waiting и запускает другой.

#### Итог:

1. **Ассемблер — это этап или встроенная часть компилятора**, но концептуально неизбежен: любая нативная программа в итоге — машинные инструкции.
2. **C/C++/Go дают нативный код**, Python/JS — байткод для виртуальной машины.
3. **Syscall есть везде**, просто у нативных языков он внутри бинарника, у интерпретируемых — внутри интерпретатора.
4. **Планировщик ОС** решает, кто исполняется, и делает context switch по таймеру или блокировке.
5. **Регистры** заполняются по calling convention, которое определяет компилятор, а сохраняются/восстанавливаются при переключении контекста ядром.
6. **Процессор** — просто исполнитель байтов. Всё остальное — надстройки ОС и компилятора.

### Архитектура процессора

Это свод правил и стандартов, по которым процессор взаимодействует с программным обеспечением.

Когда говорят об архитектуре процессора, обычно имеют в виду **ISA (Instruction Set Architecture — Архитектура набора инструкций)**. Она определяет «интерфейс» процессора для программиста и включает в себя три главных компонента:

- **Набор команд (Мнемоники / Инструкции):** Список всех базовых операций, которые процессор умеет делать на физическом уровне (например, сложить, сдвинуть биты, сравнить, перейти по адресу). Причем в разных архитектурах даже базовое сложение кодируется совершенно разными байтами.
- **Набор регистров:** Количество, размер и названия внутренних «сверхбыстрых ячеек памяти» процессора. Например, у x86-64 есть регистры `RAX`, `RBX`, `RIP`, а у архитектуры ARM регистры называются `X0`, `X1`, `PC`.
- **Модель памяти и адресация:** Правила того, как процессор видит оперативную память, какими порциями её считывает (по 4, 8 байт) и в каком порядке располагает байты чисел в памяти (сначала младшие или сначала старшие — _Endianness_).

#### Архитектуры x86 и ARM

На сегодняшний день мир технологий держится на двух гигантах. И различия между ними **кардинальны** — они заложены на уровне философии проектирования микросхем.

Архитектура CISC (Complex Instruction Set Computer) — пример: **x86 / x86-64**

- **Где используется:** Персональные компьютеры, ноутбуки (Intel, AMD), серверы.
- **Философия:** «Сделать железо максимально умным». Набор команд огромен (более 1500 инструкций). Одна команда процессора может выполнять сложнейшую цепочку действий (например, за один такт считать данные из памяти, сложить их с регистром и записать обратно).
- **Плюсы и минусы:** Программы получаются компактными по объёму, но само ядро процессора физически становится огромным, сложным и **потребляет очень много энергии** (выделяет много тепла).

Архитектура RISC (Reduced Instruction Set Computer) — пример: **ARM, Apple Silicon (M1/M2/M3), RISC-V**

- **Где используется:** Смартфоны (Android, iPhone), планшеты, современные ноутбуки Mac, микроконтроллеры.
- **Философия:** «Сделать железо максимально простым и быстрым, а всю сложную работу переложить на компилятор». Набор инструкций жестко ограничен и упрощен. Каждая команда делает ровно одно элементарное действие и имеет одинаковую длину.
- **Плюсы и минусы:** Процессор работает фантастически быстро, занимает мало места на кремниевой пластине и **потребляет ничтожно мало энергии** (мобильные телефоны не требуют вентиляторов). Но для выполнения той же задачи программе на RISC требуется написать большее количество строчек кода, чем на CISC.

Как выглядит одна и та же простая операция (сложить два числа и сохранить в память) на ассемблере этих архитектур:

|Критерий|x86-64 (CISC)|ARM64 (RISC)|
|---|---|---|
|**Философия кода**|Можно работать напрямую с памятью.|С памятью работать нельзя, только через промежуточную загрузку в регистры (_Load/Store_).|
|**Пример кода**|`addl %eax, (%rcx)`  <br>_(Взять значение из EAX, найти адрес в памяти по указателю RCX и прямо там прибавить число)._|`ldr w2, [x1]`  <br>`add w2, w2, w0`  <br>`str w2, [x1]`  <br>_(1. Загрузить из памяти в регистр W2. 2. Сложить регистры W2 и W0. 3. Записать результат обратно в память)._|
|**Размер инструкций**|Переменный (от 1 до 15 байт на команду).|Строго фиксированный (каждая команда — ровно 4 байта).|
Если отличия кардинальны, почему мы можем пользоваться одними приложениями и на компьютере (x86), и на телефоне (ARM)? Есть три пути:

1. **Перекомпиляция исходного кода (Native):** Разработчик пишет код на языке высокого уровня (например, на C++). Этот код универсален. Затем разработчик берет два разных компилятора: один компилятор превращает C++ в инструкции x86, а второй — в инструкции ARM. На выходе получаются две разные по байтам программы, выполняющие одну задачу.
2. **Эмуляция / Трансляция (Эмуляторы, Apple Rosetta 2):** Специальная программа-переводчик «на лету» переводит чужие инструкции в родные. Когда Apple перешла на свои процессоры M1 (ARM), старые программы x86 работали через Rosetta 2. Rosetta брала байты x86, пережёвывала их и выдавала процессору M1 понятные ему байты ARM. Это требует огромных ресурсов, но современные процессоры настолько мощные, что пользователь часто не замечает падения скорости.
3. **Виртуальные машины (Java, C#):** Программы компилируются не под реальный процессор, а под вымышленный (байт-код для Java Virtual Machine). А уже на каждом конкретном устройстве установлена своя JVM, которая знает, как этот байт-код перевести в родные команды текущего процессора.

### Основные инструкции x86-64

#### Пересылка данных

|Инструкция|Что делает|
|---|---|
|`mov dst, src`|копирует значение|
|`movzx dst, src`|копирует с расширением нулями|
|`movsx dst, src`|копирует с расширением знака|
|`lea dst, [addr]`|загружает **адрес**, не значение; часто используется как быстрая арифметика|
|`xchg a, b`|обмен значениями|
|`push src`|положить на стек (`rsp -= 8; [rsp] = src`)|
|`pop dst`|снять со стека|
|`cmovcc dst, src`|условная пересылка по флагам|

`lea` — самая недооценённая: `lea rax, [rbx + rcx*4 + 8]` вычислит `rbx + 4*rcx + 8` без обращения к памяти.

#### Арифметика и логика

|Инструкция|Что делает|
|---|---|
|`add dst, src`|сложение|
|`sub dst, src`|вычитание|
|`adc`, `sbb`|сложение/вычитание с учётом CF|
|`inc`, `dec`|±1|
|`neg`|смена знака|
|`mul`, `imul`|умножение (беззнаковое / знаковое)|
|`div`, `idiv`|деление|
|`and`, `or`, `xor`, `not`|логические|
|`shl`, `shr`, `sar`|сдвиги (логический влево/вправо, арифметический вправо)|
|`rol`, `ror`, `rcl`, `rcr`|циклические сдвиги|
|`cmp a, b`|сравнение (вычитает, ставит флаги, результат не сохраняет)|
|`test a, b`|логическое И, ставит флаги, результат не сохраняет|

Частный случай: `xor eax, eax` — идиома для обнуления регистра (короче и быстрее `mov eax, 0`).

#### Управление потоком

|Инструкция|Что делает|
|---|---|
|`jmp target`|безусловный переход|
|`je/jz`, `jne/jnz`|переход по ZF|
|`jg/jge`, `jl/jle`|знаковые сравнения|
|`ja/jae`, `jb/jbe`|беззнаковые сравнения|
|`js`, `jns`|по SF|
|`jo`, `jno`|по OF|
|`jc`, `jnc`|по CF|
|`call target`|вызов функции (кладёт адрес возврата на стек)|
|`ret`|возврат (снимает адрес возврата со стека)|
|`loop target`|декремент `rcx` и переход, если не 0|

#### Стек и кадр

```asm
push rbp          ; сохранить старый frame pointer
mov  rbp, rsp     ; новый frame pointer
sub  rsp, 16      ; место под локальные переменные
...
leave             ; = mov rsp, rbp; pop rbp
ret
```

#### Строковые инструкции

Работают с `rsi`/`rdi`, повторяются с префиксом `rep`:
- `movs`, `stos`, `lods`, `cmps`, `scas` — копирование, запись, чтение, сравнение, поиск.

Пример: `rep movsb` копирует `rcx` байт из `[rsi]` в `[rdi]`.

#### Синхронизация

|Инструкция|Назначение|
|---|---|
|`lock add [mem], 1`|атомарное сложение|
|`xchg [mem], reg`|атомарный обмен (неявно locked)|
|`cmpxchg`|compare-and-swap|
|`mfence`, `lfence`, `sfence`|барьеры памяти|
|`pause`|подсказка для spin-loop|

Префикс `lock` заставляет процессор выполнить операцию атомарно относительно других ядер.

#### Системные

|Инструкция|Что делает|
|---|---|
|`syscall`|переход в ядро (Linux x86-64: номер в `rax`, аргументы в `rdi,rsi,rdx,r10,r8,r9`)|
|`sysret`|возврат из syscall (только ring 0)|
|`int N`|программное прерывание (например, `int 0x80` — старый Linux syscall)|
|`iret`|возврат из прерывания|
|`cpuid`|информация о процессоре|
|`rdtsc`|счётчик тактов|
|`rdmsr`/`wrmsr`|чтение/запись MSR|
|`hlt`|остановить ядро до прерывания|
|`cli`/`sti`|запретить/разрешить прерывания (ring 0)|

#### Расширения: SIMD

SSE/AVX добавляют сотни инструкций:
- `movaps`, `movups`, `vmovdqa` — загрузка/сохранение 128/256/512 бит;
- `addps`, `mulpd` — параллельные операции над float/double;
- `paddd`, `psubw` — целочисленные SIMD;
- `vfmadd` — fused multiply-add.

Одна AVX-512 инструкция может обработать 16 float за такт.

### Основные структуры ядра Linux

`trace_event_raw_sys_enter` — это **универсальный контейнер**, в который подсистема трассировки ядра (`ftrace`) запаковывает параметры _любого_ системного вызова в момент входа в него.

Массив `args` внутри этой структуры содержит ровно **6 элементов (индексы от 0 до 5)**, так как архитектура процессоров x86-64 на аппаратном уровне ограничивает максимальное количество аргументов для одного системного вызова шестью (они передаются через регистры `RDI`, `RSI`, `RDX`, `R10`, `R8`, `R9`). Седьмого аргумента (индекса 6) просто не существует.

`args[6]` — это **безликий слепок регистров процессора**. Что именно будет лежать в `args[0]`, `args[1]` или `args[2]`, полностью зависит от сигнатуры (прототипа) конкретной функции системного вызова в исходном коде ядра Linux.


>**Системный вызов `execve`**

В ядре Linux его прототип выглядит так:

```c
int sys_execve(const char *filename, const char *const argv[], const char *const envp[]);
```

Соответственно, ядро раскладывает его параметры в массив `args` следующим образом:

- **`args[0]`** — `const char *filename` (Указатель на строку с путем к бинарнику, например, `"/usr/bin/ls"`). _Именно поэтому в хуке execve мы читали `args[0]`_.
- **`args[1]`** — `const char **argv` (Указатель на массив строк-аргументов, переданных программе).
- **`args[2]`** — `const char **envp` (Указатель на массив строк с переменными окружения).
- **`args[3]`, `args[4]`, `args[5]`** — не используются (содержат `0` или мусор), так как у `execve` всего 3 аргумента.

>**Системный вызов `openat`**

Его прототип в ядре совершенно другой:

```c
int sys_openat(int dfd, const char *filename, int flags, umode_t mode);
```

Ядро берет эти 4 параметра и раскладывает их по тем же самым регистрам:

- **`args[0]`** — `int dfd` (Дескриптор директории. Часто там лежит число `-100`, что означает макрос `AT_FDCWD` — искать файл относительно текущей папки).
- **`args[1]`** — `const char *filename` (Указатель на строку с путем к файлу, который хотят открыть). _Вот почему в хуке openat нужно читать строго `args[1]`, а не `args[0]`!_
- **`args[2]`** — `int flags` (Флаги открытия файла: например, `O_RDONLY` (чтение), `O_WRONLY` (запись) — закодированные в виде битовой маски).
- **`args[3]`** — `umode_t mode` (Права доступа, например `0644`, если файл создается с нуля).
- **`args[4]`, `args[5]`** — не используются.


Что возвращают остальные индексы для других вызовов?

Массив `args` может хранить абсолютно любые типы данных размером до 64 бит (указатели, числа, дескрипторы сокетов), приведенные к типу `unsigned long`.

Вот примеры для других популярных системных вызовов:

- **`sys_read(int fd, char *buf, size_t count)`**:
    - `args[0]`: `fd` (номер файлового дескриптора, откуда читаем).
    - `args[1]`: `buf` (адрес памяти, куда сложить прочитанные байты).
    - `args[2]`: `count` (сколько байт процесс просит прочитать).
- **`sys_write(int fd, const char *buf, size_t count)`**:
    - Аналогично `read`, но `args[1]` — это адрес строки, которую процесс хочет _записать_ в файл или сокет.
- **`sys_kill(pid_t pid, int sig)`**:
    - `args[0]`: `pid` (целевой ID процесса, который хотят убить).
    - `args[1]`: `sig` (номер сигнала, например, `9` для `SIGKILL` или `15` для `SIGTERM`).
