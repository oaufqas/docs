### Как инструкции попадают к процессору

> Термины:

- **RIP (Relative Instruction Pointer / Указатель Инструкций)** — это один из самых важных регистров процессора в 64-битной архитектуре x86-64.
	Простыми словами, **RIP — это «курсор» процессора**, который указывает на текущее место в программе. В нем всегда хранится **адрес памяти следующей инструкции**, которую процессор должен выполнить.
	
	Когда компьютер работает, он выполняет бесконечный цикл:
	1. Считать инструкцию по адресу, на который указывает **RIP**.
	2. Изменить **RIP** так, чтобы он указывал на _следующую_ инструкцию (сдвинуть курсор на длину только что считанной команды).
	3. Выполнить считанную инструкцию.
	4. Повторить


Процессор — это цифровая схема. У него есть:
- **Регистры**: быстрая память внутри ядра. На x86-64: `rax`, `rbx`, `rcx`, `rdx`, `rsi`, `rdi`, `rbp`, `rsp`, `r8`–`r15`, `rip`, `rflags`, плюс сегментные, плюс векторные `xmm`/`ymm`/`zmm`.
- **Блок выборки (fetch unit)**: читает байты из памяти по адресу `RIP`.
- **Декодер**: превращает байты в микрооперации (µops).
- **Исполнительные блоки**: ALU, FPU, load/store, branch.
- **Кэши**: L1I (инструкции), L1D (данные), L2, L3.
- **MMU**: переводит виртуальные адреса в физические через page tables.
- **Таблицы прерываний**: IDT на x86, vector table на ARM.

Процессор **не понимает** ни C, ни Python, ни «ассемблер». Он понимает только байты, закодированные по его ISA. Процессор не читает файлы с диска. Он читает инструкции из памяти по адресу, который лежит в регистре-указателе команд: `RIP` на x86-64, `PC` на ARM.

```
высокие адреса
+------------------+
|     stack        |  растёт вниз
+------------------+
|        |         |
|      heap        |  растёт вверх
+------------------+
|  .bss            |  нулевые данные
+------------------+
|  .data           |  инициализированные данные
+------------------+
|  .rodata         |  константы
+------------------+
|  .text           |  КОД (read + execute)
+------------------+
низкие адреса
```

`RIP` указывает на точку входа в `.text`.


Что делает ОС, когда вы запускаете программу:
1. Оболочка или GUI просит ядро создать процесс.
2. Ядро открывает исполняемый файл: ELF в Linux, PE в Windows.
3. Загрузчик читает заголовки, смотрит сегменты:
    - `.text` — код, обычно read + execute;
    - `.data` — глобальные данные;
    - `.bss` — нулевые данные;
    - stack, heap.
4. Создаётся виртуальное адресное пространство процесса.
5. Сегменты отображаются в память через [[virtual-memory|page tables]].
6. Если есть динамические библиотеки, запускается динамический линкер: подгружает `libc.so`, `libm.so` и т.п., делает релокации.
7. Ядро устанавливает `RIP` на точку входа: обычно `_start`, которая потом вызывает `__libc_start_main`, а та — `main`.
8. Процессор начинает цикл:
	- **Fetch**: MMU переводит виртуальный `RIP` в физический адрес, кэш L1I отдаёт байты. Процессор читает несколько байт вперёд.
	- **Decode**: определяется, какая это инструкция, какие у неё операнды, длина. x86 — переменная длина (1–15 байт), ARM — фиксированная (4 байта), RISC-V — переменная.
	- **Execute**: инструкция выполняется в соответствующем блоке. Результат пишется в регистр или память.
	- **Update RIP**: либо `RIP += длина`, либо переход по новой ветке.

>**На современных процессорах это не последовательно, а конвейер и out-of-order:**

- **Pipeline**: несколько инструкций одновременно на разных стадиях.
- **Superscalar**: за такт декодируется и исполняется несколько инструкций.
- **Out-of-order execution**: инструкции переставляются динамически, лишь бы зависимости соблюдались.
- **Register renaming**: физические регистры подменяются, чтобы убрать ложные зависимости.
- **Branch prediction**: процессор угадывает, куда пойдёт ветвление, и заранее грузит код. Если угадал — нет задержки, если нет — pipeline flush.
- **Speculative execution**: процессор исполняет «на всякий случай» вперёд. Именно это эксплуатировали Spectre/Meltdown.


>**Код может подгружаться с диска не сразу, а по страницам (demand paging):** 

1. Процессор пытается прочитать байт по адресу.
2. MMU не находит страницу в page tables или видит, что она не в памяти.
3. Возникает **page fault**.
4. Управление переходит в ядро.
5. Ядро находит страницу в файле (ELF) или в swap.
6. Загружает её в физическую память.
7. Обновляет page tables.
8. Возвращает управление, процессор повторяет инструкцию.

С точки зрения программы это незаметно. С точки зрения процессора — обычный доступ к памяти после обработки fault.

### Регистры процессора и как программа туда попадает

[[program-compilation_assembler|Компилятор сам решает]], что и где будет лежать. Это не делает операционная система и не делает процессор. Правила взаимодействия функций называются **calling convention**. На Linux x86-64 используется **System V AMD64 ABI**:

- Целочисленные аргументы (первые 6): `rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9`.
- Остальные — на стек.
- Возврат: `rax` (и `rdx` для 128-битных).
- `rbp` — базовый указатель кадра.
- `rsp` — указатель стека.
- `rbx`, `rbp`, `r12`–`r15` — **callee-saved**: функция обязана их сохранить и восстановить.
- `rax`, `rcx`, `rdx`, `rsi`, `rdi`, `r8`–`r11` — **caller-saved**: вызывающий сам их сохраняет, если нужно.

Пример:

```c
int add(int a, int b) {
    return a + b;
}
```

Компилируется в:

```asm
add:
    lea  eax, [rdi + rsi]   ; a в edi, b в esi, результат в eax
    ret
```

Вот как данные попадают в регистры: компилятор сгенерировал код, где аргументы приходят в `edi` и `esi`, потому что так велит ABI. Вызывающая сторона перед `call` положила их туда.

Регистры не «закладываются» динамически в момент запуска. Это статическое решение компилятора: «здесь мы используем `rax`, здесь `rdi`». При переключении контекста ОС сохраняет и восстанавливает их.

### Системные вызовы и «повышение полномочий»

Вот тут важно не ошибиться.

Скомпилированная программа **не повышает себе полномочия произвольно**. Она может выполнить специальную инструкцию `syscall` на x86-64 или `svc` на ARM. Это аппаратный механизм перехода в ядро.

Упрощённо на Linux x86-64:

```asm
mov eax, 1      ; номер syscall: write
mov edi, 1      ; fd = stdout
mov rsi, buf    ; указатель на данные
mov edx, 3      ; длина
syscall
```

Что происходит:

1. Программа в user mode, ring 3.
2. Кладёт номер системного вызова и аргументы в регистры.
3. Выполняет `syscall`.
4. Процессор переключается в kernel mode, ring 0.
5. Управление переходит на заранее заданный обработчик ядра.
6. Ядро проверяет номер вызова, права процесса, аргументы, указатели.
7. Если всё можно — выполняет операцию: пишет в файл, выделяет память, открывает сокет и т.д.
8. Возвращается в user mode.
9. Программа продолжает работу уже снова в ring 3.

То есть `syscall` — это **не «сделай меня root»**. Это «попроси ядро выполнить привилегированную операцию». Ядро остаётся привилегированным. Процесс остаётся непривилегированным. Если ядро разрешит операцию — она выполняется от имени ядра, но права процесса при этом не становятся ring 0.

`root` в Linux — это тоже не ring 0. Это UID 0, то есть учётная запись, которой ядро разрешает больше операций. Но даже root-процесс в user space выполняется в ring 3 и всё равно ходит в ядро через syscall.

### Архитектура процессора

Это свод правил и стандартов, по которым процессор взаимодействует с программным обеспечением.

Когда говорят об архитектуре процессора, обычно имеют в виду **ISA (Instruction Set Architecture — Архитектура набора инструкций)**. Она определяет «интерфейс» процессора для программиста и включает в себя три главных компонента:

- **Набор команд (Мнемоники / Инструкции):** Список всех базовых операций, которые процессор умеет делать на физическом уровне (например, сложить, сдвинуть биты, сравнить, перейти по адресу). Причем в разных архитектурах даже базовое сложение кодируется совершенно разными байтами.
- **Набор регистров:** Количество, размер и названия внутренних «сверхбыстрых ячеек памяти» процессора. Например, у x86-64 есть регистры `RAX`, `RBX`, `RIP`, а у архитектуры ARM регистры называются `X0`, `X1`, `PC`.
- **Модель памяти и адресация:** Правила того, как процессор видит оперативную память, какими порциями её считывает (по 4, 8 байт) и в каком порядке располагает байты чисел в памяти (сначала младшие или сначала старшие — _Endianness_).

#### Архитектуры x86 и ARM

На сегодняшний день мир технологий держится на двух гигантах. И различия между ними **кардинальны** — они заложены на уровне философии проектирования микросхем.

Архитектура CISC (Complex Instruction Set Computer) — пример: **x86 / x86-64**

- **Где используется:** Персональные компьютеры, ноутбуки (Intel, AMD), серверы.
- **Философия:** «Сделать железо максимально умным». Набор команд огромен (более 1500 инструкций). Одна команда процессора может выполнять сложнейшую цепочку действий (например, за один такт считать данные из памяти, сложить их с регистром и записать обратно).
- **Плюсы и минусы:** Программы получаются компактными по объёму, но само ядро процессора физически становится огромным, сложным и **потребляет очень много энергии** (выделяет много тепла).

Архитектура RISC (Reduced Instruction Set Computer) — пример: **ARM, Apple Silicon (M1/M2/M3), RISC-V**

- **Где используется:** Смартфоны (Android, iPhone), планшеты, современные ноутбуки Mac, микроконтроллеры.
- **Философия:** «Сделать железо максимально простым и быстрым, а всю сложную работу переложить на компилятор». Набор инструкций жестко ограничен и упрощен. Каждая команда делает ровно одно элементарное действие и имеет одинаковую длину.
- **Плюсы и минусы:** Процессор работает фантастически быстро, занимает мало места на кремниевой пластине и **потребляет ничтожно мало энергии** (мобильные телефоны не требуют вентиляторов). Но для выполнения той же задачи программе на RISC требуется написать большее количество строчек кода, чем на CISC.

Как выглядит одна и та же простая операция (сложить два числа и сохранить в память) на ассемблере этих архитектур:

|Критерий|x86-64 (CISC)|ARM64 (RISC)|
|---|---|---|
|**Философия кода**|Можно работать напрямую с памятью.|С памятью работать нельзя, только через промежуточную загрузку в регистры (_Load/Store_).|
|**Пример кода**|`addl %eax, (%rcx)`  <br>_(Взять значение из EAX, найти адрес в памяти по указателю RCX и прямо там прибавить число)._|`ldr w2, [x1]`  <br>`add w2, w2, w0`  <br>`str w2, [x1]`  <br>_(1. Загрузить из памяти в регистр W2. 2. Сложить регистры W2 и W0. 3. Записать результат обратно в память)._|
|**Размер инструкций**|Переменный (от 1 до 15 байт на команду).|Строго фиксированный (каждая команда — ровно 4 байта).|
Если отличия кардинальны, почему мы можем пользоваться одними приложениями и на компьютере (x86), и на телефоне (ARM)? Есть три пути:

1. **Перекомпиляция исходного кода (Native):** Разработчик пишет код на языке высокого уровня (например, на C++). Этот код универсален. Затем разработчик берет два разных компилятора: один компилятор превращает C++ в инструкции x86, а второй — в инструкции ARM. На выходе получаются две разные по байтам программы, выполняющие одну задачу.
2. **Эмуляция / Трансляция (Эмуляторы, Apple Rosetta 2):** Специальная программа-переводчик «на лету» переводит чужие инструкции в родные. Когда Apple перешла на свои процессоры M1 (ARM), старые программы x86 работали через Rosetta 2. Rosetta брала байты x86, пережёвывала их и выдавала процессору M1 понятные ему байты ARM. Это требует огромных ресурсов, но современные процессоры настолько мощные, что пользователь часто не замечает падения скорости.
3. **Виртуальные машины (Java, C#):** Программы компилируются не под реальный процессор, а под вымышленный (байт-код для Java Virtual Machine). А уже на каждом конкретном устройстве установлена своя JVM, которая знает, как этот байт-код перевести в родные команды текущего процессора.
