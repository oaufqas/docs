## Journald (journal daemon) - системный демон, для сохранения и структурирования логов программ

Для того чтобы вывод программы попал в `journald`, ей **не нужно выделять никакой специальный или секретный дескриптор**.

Всё работает на базовых правилах ядра Linux. Любой процесс при рождении автоматически получает три стандартных дескриптора (POSIX-стандарт:

- **`0`** — `stdin` (стандартный ввод)
- **`1`** — `stdout` (стандартный вывод)
- **`2`** — `stderr` (стандартный вывод ошибок)

Когда программа (например `kube-apiserver` или `etcd`) пишется на языках Go, C или Python, разработчики просто используют стандартные функции печати логов в консоль (например, `fmt.Println()` в Go). Эти функции отправляют байты текста в дескрипторы `1` и `2`.

Когда вы описываете программу в виде `systemd`-юнита (как наши файлы `etcd.service` или `kubelet.service`), запуском бинарника управляет главный менеджер процессов ОС — **`systemd` (PID 1)**.

1. Перед тем как сделать системный вызов `execve()` и запустить, например, `etcd`, `systemd` создает в памяти специальный **виртуальный сокет** (`STDOUT`/`STDERR` pipe), соединенный напрямую с демоном логов `systemd-journald`.
2. С помощью системного вызова ядра **`dup2()`** `systemd` насильно подменяет стандартные дескрипторы `1` (`stdout`) и `2` (`stderr`) запускаемой программы, привязывая их к этому сокету.
3. Программа думает, что она просто пишет текст на экран (в консоль), но ядро Linux на лету перенаправляет этот поток байтов прямо в рот демону **`journald`**.


Если программа хочет не просто выплюнуть строчку текста, а передать в `journald` богатые структурированные логи (например, отдельно поле `ERROR_CODE=404`, отдельно имя пользователя, отдельно уровень важности), стандартных дескрипторов `1` и `2` становится мало (ведь это просто текстовая лента).

Для этого программы используют **родной API-протокол `journald`**:

- Вместо `stdout` программа открывает специальный Unix-сокет, который физически живет по пути **`/run/systemd/journal/socket`**.
- Программа шлет туда данные в бинарном структурированном JSON-подобном формате.
- На языке C для этого используется функция `sd_journal_send()`.


Как `journald` обогащает логи (Метаданные ядра)

Когда `journald` получает строку из дескриптора программы, он не просто записывает её на диск. Он совершает микро-запрос к ядру Linux (через структуры `cgroups` и системные таблицы процессов), чтобы узнать подноготную автора пакета:

- Какой **PID** (идентификатор процесса) отправил эту строку?
- От какого **UID** (пользователя) запущена программа?
- Из какого конкретно **systemd-юнита** (`_SYSTEMD_UNIT=etcd.service`) прилетел трафик?

Все эти данные склеиваются в один бинарный зашифрованный блок и сохраняются в папке `/var/log/journal/`.

Как этим управлять в `systemd.service`?

Внутри блока `[Service]` файлов конфигураций можно явно управлять поведением дескрипторов с помощью директив `StandardOutput` и `StandardError`:


```ini
[Service]
ExecStart=/usr/local/bin/etcd ...
# По умолчанию в systemd уже зашиты эти настройки:
StandardOutput=journal
StandardError=journal
```


Если изменить эту строку, например, на `StandardOutput=file:/var/log/etcd.log`, `systemd` перенаправит дескриптор `1` в текстовый файл на диске, и этот поток **перестанет** отображаться в `journalctl`.

## Systemd-resolved - внутренний DNS сервер

**`systemd-resolved`** — это системный демон, встроенный в подсистему инициализации `systemd`. Он выполняет роль **локального кэширующего DNS-резолвера и сетевого диспетчера** для операционной системы Linux. В современных дистрибутивах (Ubuntu Server 20.04+, Debian 12+) он включен по умолчанию.

Зачем нужен `systemd-resolved` и какие задачи он решает?

Раньше в Linux управление DNS было примитивным: операционная система умела читать только один текстовый файл — `/etc/resolv.conf`. Но в мире современных ноутбуков, Wi-Fi сетей и VPN-тоннелей этого файла стало мало.

`systemd-resolved` создавался для решения сложных сетевых задач:

1. **Локальное кэширование:** Если программа запрашивает IP одного и того же сайта (например, `github.com`), `systemd-resolved` запоминает ответ в оперативной памяти хоста. Повторный запрос обрабатывается внутри ОЗУ за 0 миллисекунд без отправки пакетов в интернет.
2. **Разделение DNS-серверов по интерфейсам (Split-DNS):** Это главная фишка демона. Если у вас на виртуалке поднят VPN-тоннель `wg0` и есть физическая карта `eth0`, `systemd-resolved` умеет делать магию: запросы к корпоративным сайтам `*.company.local` он шлет строго внутрь VPN, а запросы к `google.com` — через обычный домашний роутер. Старый `/etc/resolv.conf` так делать не умел.
3. **Современные протоколы:** Из коробки поддерживает шифрование DNS-трафика (**DNS-over-TLS**) и проверку подлинности ответов (**DNSSEC**), защищая систему от подмены IP-адресов хакерами.

Чтобы программы не слали запросы в интернет напрямую, `systemd-resolved` перехватывает сетевой трафик. Он поднимает на локальном loopback-интерфейсе (`lo`) виртуальный DNS-сервер, который слушает IP **`127.0.0.53`** на порту **`53`**.

Затем он совершает захват файла `/etc/resolv.conf`: превращает его в виртуальную символическую ссылку (Symlink), которая жестко указывает на его собственную заглушку:

```bash
/etc/resolv.conf -> /run/systemd/resolve/stub-resolv.conf
```

Анатомия прохождения DNS-запроса сейчас:

1. Программа делает системный вызов `getaddrinfo("node-0")`.
2. Библиотека `glibc` Linux заглядывает в `/etc/resolv.conf`, видит там `nameserver 127.0.0.53`.
3. Запрос летит на localhost. Его ловит демон `systemd-resolved`.
4. Демон заглядывает в свои таблицы (которые он получил от Netplan, DHCP или NetworkManager) и перенаправляет запрос на реальный IP вашего DNS-контейнера `192.168.100.20`.

Почему это ломает Kubernetes (CoreDNS)?

Когда запускается под CoreDNS, он копирует файл `/etc/resolv.conf` с хоста внутрь своего изолированного контейнера. Но внутри сети контейнера адрес `127.0.0.53` указывает **на сам под CoreDNS**, а не на хост! Пакет начинает циркулировать сам в себе, перегружает процессор и под падает с ошибкой `Loop detected`


##### Утилита для взаимодействия с `resolved` - `resolvectl`, основные команды:

- `resolvectl` - Список статусов DNS серверов для всех интерфейсов, 
- `resolvectl status ${interface}` - Статусы DNS конкретного интерфейса
- `resolvectl service ${name} ${type} ${domain}` - Запрос на получение SRV-записей
- `resolvectl statistics` - Выводит статистику работы резолвера, включая объем кэша и количество попаданий/промахов в него
- `resolvectl flush-caches` - Сбросить DNS кэш
- `resolvectl monitor` - Смотреть в realtime запросы к resolved
- `resolvectl query ${domain}` — резолвит (ищет IP) указанного домена.
- `resolvectl dns ${interface} ${server_ip}` — устанавливает DNS-сервер для конкретного сетевого интерфейса (например, `eth0` или `wlan0`).
- `resolvectl domain ${interface} ${domain}` — задает поисковые домены для интерфейса.
- `resolvectl dnsovertls ${interface} <yes/no/opportunistic>` — включает или отключает шифрование DNS-запросов (DNS-over-TLS) для выбранного интерфейса.

Как управлять DNS-серверами локально БЕЗ `systemd-resolved`?

Если мы полностью отключаем этот комбайн, управление DNS возвращается к классическому, прозрачному стандарту UNIX-систем, который существовал последние 40 лет.

Всю работу под капотом в этом случае начинает выполнять **библиотека `glibc` (сетевая подсистема ядра Linux)** напрямую, ориентируясь на два простых файла на диске:

Файл 1. `/etc/nsswitch.conf` (Служба переключения имен)

Это главный диспетчер ядра. Внутри него есть строчка:

```
hosts:          files dns
```


Она указывает ядру жесткий приоритет: Если программа ищет имя сайта, сначала загляни в локальный файл `files` (`/etc/hosts`), и только если там ничего нет, делай сетевой запрос в `dns`.

Файл 2. Статический `/etc/resolv.conf`

Теперь это не виртуальная ссылка, а **обычный текстовый файл**, который вы создаете руками. Внутри него нет никаких заглушек `127.0.0.53`, а записаны **реальные физические IP-адреса**.

Как идет DNS-запрос БЕЗ `systemd-resolved`:

1. Программа запрашивает имя `node-0`.
2. Ядро Linux (`glibc`) читает `/etc/hosts`. Если совпадений нет, оно открывает текстовый файл `/etc/resolv.conf`.
3. Оно считывает первую строчку `nameserver 192.168.100.20`.
4. Сетевой стек ядра Linux **напрямую формирует UDP-пакет** и через физическую сетевую карту `eth0` отправляет его на IP вашего DNS-контейнера.
