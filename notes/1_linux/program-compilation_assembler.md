### Ассемблер, принцип работы компиляции и исполнения программ

>Термины:
- **Язык ассемблера** — это человекочитаемая запись машинных инструкций конкретного процессора: `mov`, `add`, `jmp`, `syscall` и т.п.
- **Ассемблер** — это программа-транслятор, которая превращает текст на языке ассемблера в машинный код / объектный файл. Примеры: GNU Assembler (`as`), NASM, MASM.
- **Машинный код** — байты, которые процессор реально умеет декодировать и исполнять. Например, `mov eax, 1` на x86-64 кодируется как `B8 01 00 00 00`.
- **Процессор не знает** ни C,  ни «ассемблер». Он знает только машинные инструкции своей архитектуры: x86-64, ARM64, RISC-V и т.д.

#### Что такое ассемблер и что он делает

Ассемблер — это не runtime и не часть процессора. Это обычная программа, которую запускает операционная система, как и любой другой компилятор.

Цепочка:

```
текст на ассемблере (.s)
        |
        v
   ассемблер (as/nasm)
        |
        v
объектный файл (.o)
        |
        v
   линкер (ld)
        |
        v
исполняемый файл (ELF/PE)
        |
        v
   загрузчик ОС
        |
        v
   память -> процессор
```

Сравнительная таблица объектного файла (`.o`, `.obj`) и исполняемого (`.exe`/без расширения в Linux)

| Характеристика           | Объектный файл (`.obj`, `.o`)                                                                                               | Исполняемый файл (`.exe`, без расширения в Linux)                                                                          |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| **Что это?**             | Результат работы компилятора или ассемблера из **одного** исходного файла.                                                  | Результат работы линкера (компоновщика) из **всех** объектных файлов и библиотек.                                          |
| **Готовность к запуску** | **Нельзя запустить.** ОС не поймет, с какого места начинать и где искать внешние функции.                                   | **Готов к запуску.** ОС может загрузить его в память и передать управление процессору.                                     |
| **Адресация**            | **Относительная (условная).** Все адреса функций и переменных внутри файла временные и начинаются с нуля.                   | **Абсолютная или смещаемая (виртуальная).** Все адреса настроены для работы в памяти ОС.                                   |
| **Внешние связи**        | **Не разрешены.** Если в коде вызывается функция `printf` или функция из другого файла, вместо адреса там стоит «заглушка». | **Разрешены.** Все «заглушки» заменены на реальные адреса функций в памяти или в динамических библиотеках (`.dll`, `.so`). |
| **Точка входа**          | **Отсутствует.** В нем нет явного указания для ОС, где находится главная функция (например, `main`).                        | **Присутствует.** Содержит четкую точку входа (Entry Point), с которой процессор начинает выполнять инструкции.            |

Сам ассемблер **не исполняет** ассемблерный код. Он читает текст, кодирует инструкции в байты, строит таблицы символов и релокаций, пишет объектный файл. Исполняет потом уже процессор — машинный код, который получился после ассемблера и линкера.

Ассемблер запускается:
- вручную из терминала,
- сборочной системой `make`, `cmake`, `ninja`,
- компилятором, который внутри вызывает `as`,
- IDE.

Сам ассемблер — это тоже машинный код. Его запускает ОС, а выполняет процессор. Но ассемблируемый код в этот момент не выполняется — он просто данные на входе.

Операционная система **в runtime не использует ассемблер как программу**. Ядро ОС уже скомпилировано в машинный код и исполняется процессором. Ассемблер нужен на этапе сборки.

Где реально нужен ассемблер / язык ассемблера:
- загрузчики ОС, firmware, UEFI, boot-сектора;
- вход в ядро, обработчики прерываний и системных вызовов;
- переключение контекста задач;
- низкоуровневые атомарные операции, барьеры памяти;
- драйверы, embedded, микроконтроллеры;
- криптография, DSP, SIMD-оптимизации;
- reverse engineering, анализ malware, CTF, отладка;
- компиляторы и JIT-движки: они генерируют машинный код или ассемблер.

Обычный прикладной программист в 99% случаев ассемблер напрямую не пишет. Но он пользуется результатом работы компилятора, ассемблера и линкера.

>Концептуально — **любой** нативный код в итоге превращается в машинные инструкции конкретной архитектуры. У этих инструкций есть текстовая форма — язык ассемблера. Значит, теоретически любую программу можно написать на ассемблере.


>**Технически** — не всегда есть отдельный этап с файлом `.s` и вызовом внешнего `as`:

- GCC классически делает `.c -> .i -> .s -> .o -> ELF`.
- Clang/LLVM может генерировать объектный файл **напрямую из IR**, минуя текстовый `.s`. Внутри всё равно работает кодогенератор, который кодирует инструкции, но внешний ассемблер не вызывается.
- Go toolchain не вызывает GNU `as`. У него свой ассемблер и свой формат. Более того, Go-ассемблер — это не совсем обычный ассемблер, у него своя нотация.
- Rust через LLVM ведёт себя как Clang.

Правильная мысль такая: **ассемблер как концепция (перевод инструкций в байты) неизбежен**. Ассемблер как отдельная программа — не обязателен, его роль может выполнять сам компилятор.

И да, теоретически любую программу на C/C++/Go можно переписать на ассемблере. На практике это делают только для узких мест: загрузчики, ядро, криптография, SIMD, embedded.

##### Итог:

Ассемблерный код — это текстовая форма машинных инструкций

Каждая строчка ассемблерного кода (мнемоника, например, `MOV AX, BX`) напрямую соответствует определенной бинарной инструкции процессора (например, `10001011 11000011`). Ассемблер — это просто читаемый человеком способ записать единицы и нули, которые понимает процессор.

Из ассемблера можно сделать (слинковать) исполняемый файл в два этапа.
Процесс выглядит так:

1. **Трансляция (Ассемблирование):** Специальная программа-ассемблер (например, NASM) переводит текстовый файл `.asm` в бинарный **объектный файл** (`.obj` / `.o`).
2. **Компоновка (Линковка):** Другая программа — линкер (компоновщик) — берет этот объектный файл, добавляет к нему системные библиотеки и делает его **исполняемым** (`.exe`).

Из исполняемого файла **МОЖНО** получить ассемблерный код. Поскольку ассемблер и машинный код связаны жестко «один к одному», существует обратный процесс. Он называется **дизассемблированием**.

Специальные программы — **дизассемблеры** (например, _IDA Pro_, _Ghidra_, _x64dbg_) — могут открыть любой готовый исполняемый файл (`.exe`), считать оттуда машинные команды (нули и единицы) и **автоматически перевести их обратно в читаемый текстовый ассемблерный код**.

При компиляции в исполняемый файл безвозвратно стирается то, что нужно человеку, но не нужно процессору:

- **Имена переменных и функций.** Вместо `int user_age` в ассемблере после дизассемблирования вы увидите безликое `DWORD PTR [rbp-4]`.
- **Комментарии.** Все ваши пояснения к коду удаляются.
- **Структура логики.** Красивые циклы `for` или `while` превратятся в кашу из переходов `JMP` и меток.

## Путь компиляции C/C++:

- **GCC (GNU Compiler Collection)** — это один из самых популярных и мощных наборов компиляторов с открытым исходным кодом. Он поддерживает языки C, C++, Fortran, Go и другие, и умеет оптимизировать код под сотни различных процессорных архитектур.

>Термины:

- **AST (Abstract Syntax Tree / Абстрактное синтаксическое дерево)** — это древовидное представление структуры исходного кода.
	- **Как это работает:** Когда вы пишете код, компилятор сначала разбивает его на токены, а затем строит из них дерево. В этом дереве нет «лишних» деталей вроде скобок или точек с запятой, но чётко видна логика (например, что оператор `+` применяется к переменной `x` и числу `5`).
	- **Зачем нужно:** На этапе AST компилятор проверяет типы данных, находит синтаксические ошибки и понимает общую структуру программы. В GNU Compiler Collection) для этого долгое время использовалось внутреннее представление, известное как **GENERIC** (высокоуровневое AST для всех языков).


- **IR (Intermediate Representation / Промежуточное представление)** — это независимый от языка программирования и от процессора код, в который компилятор переводит AST для последующей оптимизации.
	- **Зачем нужно:** Если бы компилятор переводил C напрямую в код для Intel (x86), а C++ — напрямую в код для ARM, разработчикам пришлось бы писать сотни разных компиляторов. IR решает эту проблему. Это «универсальный язык» внутри компилятора.
	- **Внутри GCC** используется два основных уровня IR:
	    1. **GIMPLE** — среднеуровневое представление, где сложные выражения разбиваются на простые трехадресные команды (например, `a = b + c`). Именно на этом этапе GCC проводит большинство оптимизаций, не зависящих от процессора (например, удаление мертвого кода).
	    2. **RTL (Register Transfer Language)** — низкоуровневое представление, похожее на универсальный ассемблер. Здесь GCC работает с виртуальными регистрами и готовит код к превращению в реальные инструкции конкретного процессора (x86, ARM, RISC-V).


```c
main.c
  -> препроцессор
  -> компилятор (cc1/clang)
  -> внутреннее IR
  -> оптимизации
  -> генерация ассемблера (.s)
  -> ассемблер (as)
  -> объектный файл (.o)
  -> линкер (ld)
  -> ELF/PE
```

- **Этап 0: Препроцессинг (Preprocess).** Утилита `cc1` (или отдельно `cpp`) берет `second.cpp` и обрабатывает все директивы с решеткой `#`. Она копирует содержимое файлов `#include`, разворачивает макросы `#define` и удаляет комментарии.
    - _Результат:_ Чистый код на C++, который можно выгрузить командой `g++ -E second.cpp -o second.i`.
- **Этап 1: Фронтенд (Парсинг и GENERIC).** На основе текстового файла `.i` строится синтаксическое дерево (**AST**), которое в GCC приводится к единому высокоуровневому формату **GENERIC**.
- **Этап 2: Мидленд (GIMPLE и SSA).** Дерево GENERIC «понижается» (lowering) до **GIMPLE** (простого трехадресного кода). Код переводится в **SSA-форму**, где оптимизируются циклы, удаляется мертвый код и т. д.
- **Этап 3: Бэкенд (RTL).** Оптимизированный GIMPLE переводится в **RTL** (Register Transfer Language). Здесь компилятор распределяет переменные по реальным регистрам процессора.
- **Этап 4: Генерация ассемблера.** Бэкенд выдает текстовый файл ассемблера (`second.s`) уже под конкретную архитектуру процессора.
- **Этап 5: Ассемблер.** Затем внутренний ассемблер (компонент `as`) превращает его в объектный файл (машинный код, но еще не собранный) — `second.o`.
- **Этап 5: Линковка (Linker).** Линкер `ld` собирает ваш `second.o` и системные библиотеки (например, `libstdc++`) в один готовый файл `second.exe`.

#### Подробное описание этапов:

>Этап 0. Исходник

> [!INFO]- Код на c
> ```c
> #include <stdio.h>
> #define N 3
> 
> int main(void) {
>     int x = N;
>     printf("%d\n", x);
>     return 0;
> }
> ```

> Этап 1. Препроцессор (`cpp`)

> [!INFO]- Результат — **translation unit**, обычно `.i` файл. Что делает:
> - **Раскрывает `#include`**: буквально вставляет содержимое `stdio.h` в текст. Именно поэтому большие проекты долго компилируются — заголовки раздувают файл.
> - **Раскрывает макросы `#define`**: текстуальная подстановка. `N` превращается в `3`.
> - **Обрабатывает условную компиляцию** `#if`, `#ifdef`, `#ifndef`, `#else`, `#endif`.
> - **Удаляет комментарии**.
> - **Обрабатывает `#pragma`**, `#line`, `#error`, `#warning`.
> - **Склеивает строки через `\`** в конце строки.
> - **Обрабатывает `#` и `##`** в макросах (stringize и token paste).
> 
> Результат — **translation unit**, обычно `.i` файл. Это всё ещё C-код, но без директив препроцессора. Можно посмотреть:
>
> ```bash
> gcc -E main.c -o main.i
> ```
> 
> Препроцессор ничего не знает о типах, синтаксисе функций, семантике. Он работает с токенами и текстом.

> Этап 2. Компилятор: фронтенд (`cc1`/`clang`)

> [!INFO]- Фронтенд превращает C-код в **AST** (abstract syntax tree) и затем в **IR**.
>Подэтапы:
>
>1. **Лексический анализ (лексер)**: текст разбивается на токены: идентификаторы, ключевые слова, литералы, операторы, скобки.
  >  
>2. **Синтаксический анализ (парсер)**: из токенов строится дерево разбора по грамматике C. Ошибки типа `expected ';'` — это здесь.
  >  
>3. **Семантический анализ**: проверка типов, разрешение имён, проверка сигнатур, вычисление размеров, раскрытие `typedef`, проверка областей видимости, константных выражений.
  >  
>4. **Построение AST**: абстрактное дерево, где уже нет лишних скобок и промежуточных узлов парсинга.
  >  
>5. **Понижение (lowering) в IR**: AST переводится во внутреннее представление компилятора.
  >  
>
>Для GCC это **GIMPLE** и **RTL**. Для Clang — **LLVM IR**. IR — это уже не C и не ассемблер, а нечто среднее: обычно SSA-форма (static single assignment), где каждая переменная присваивается один раз, есть базовые блоки, граф потока управления, вызовы, типы.
>
>Пример LLVM IR (упрощённо):
>
>```llvm
define i32 @main() {
entry:
  %x = alloca i32
  store i32 3, i32* %x
  %0 = load i32, i32* %x
  %call = call i32 @printf(i8* getelementptr(...), i32 %0)
  ret i32 0
}
>```
>
IR **архитектурно-независим**. Один и тот же IR можно потом превратить в x86-64, ARM64, RISC-V.

> Этап 3. Оптимизации

>[!INFO]- Оптимизации идут **в несколько проходов**, и часть — на IR, часть — уже на машинном уровне.
>
>Типичные оптимизации на IR:
>
>- **Constant folding**: `2 + 3` превращается в `5` ещё на компиляции.
>- **Dead code elimination**: недостижимый или неиспользуемый код удаляется.
>- **Inlining**: тело функции вставляется в место вызова.
>- **Loop optimizations**: разворачивание циклов, вынос инвариантов, векторизация.
>- **Common subexpression elimination**: повторяющиеся выражения вычисляются один раз.
>- **Strength reduction**: умножение на 2 заменяется сдвигом.
>- **Scalar replacement of aggregates**: структура разбивается на отдельные переменные.
>- **Devirtualization** (C++): вызов виртуальной функции превращается в прямой.
>- **LTO** (link-time optimization): оптимизации через границы модулей.
>
>Уровни: `-O0` (почти без оптимизаций), `-O1`, `-O2`, `-O3`, `-Os` (размер), `-Ofast` (агрессивно).
>
>Оптимизации **меняют семантику** в разрешённых пределах. Например, компилятор может переставить обращения к памяти, если считает, что они не пересекаются. Именно поэтому в C/C++ `volatile` и атомики — отдельные сущности.

> Этап 4. Бэкенд

> [!INFO]- Генерация ассемблера (.s)
>Теперь IR переводится в инструкции конкретной архитектуры.
>
>Подэтапы:
>
>1. **Instruction selection**: каждая IR-операция отображается в одну или несколько машинных инструкций. Например, `add` в IR -> `add` в x86.
  >  
>2. **Register allocation**: переменных больше, чем регистров. Компилятор решает, кто живёт в регистре, кто — на стеке. Используется раскраска графа или linear scan. Лишнее «спиллится» (spill) в память.
  >  
>3. **Instruction scheduling**: порядок инструкций переставляется так, чтобы процессор меньше простаивал: учитываются задержки, конвейер, зависимости.
  >  
>4. **Peephole optimizations**: локальные замены «две инструкции -> одна».
  >  
>5. **Emit assembly**: печатается текст `.s` в синтаксисе AT&T (GCC) или Intel (NASM).
  >  
>
>```bash
>gcc -S main.c -o main.s
>```
>
>Пример получившегося `.s` (x86-64, упрощённо):
>
>```asm
>main:
>    pushq   %rbp
>    movq    %rsp, %rbp
>    subq    $16, %rsp
>    movl    $3, -4(%rbp)
>    movl    -4(%rbp), %eax
>    movl    %eax, %esi
>    leaq    .LC0(%rip), %rdi
>    movl    $0, %eax
>    call    printf@PLT
   > movl    $0, %eax
   > leave
   > ret
>```
>
>Здесь уже видно: `rbp`, `rsp`, `eax`, `esi`, `rdi` — конкретные регистры x86-64. Это **архитектурно-зависимо**.
>
>Итоговый путь до этого момента: 
>
>Исходный код (Фронтенд) -> Препроцессор -> GENERIC -> GIMPLE (и SSA-оптимизации) -> RTL (Бэкенд) -> Генерация ассемблерного кода.

> Этап 5. Ассемблер (`as`)

> [!INFO]- Ассемблер читает `.s/.asm` и преврещает мнемоники в байты.
>Что он делает:
>1. **Парсит** каждую строку: метка, мнемоника, операнды.
>2. **Определяет размеры и смещения**: `movl $3, -4(%rbp)` знает, что это 4 байта.
>3. **Кодирует инструкции** в байты по таблицам ISA.
>4. **Строит таблицу символов**: какие метки где находятся.
>5. **Строит таблицы релокаций**: «в этом месте нужно подставить адрес символа X, но я его пока не знаю».
>6. **Обрабатывает секции**: `.text`, `.data`, `.bss`, `.rodata`.
>7. **Пишет объектный файл** `.o` в формате ELF (Linux) или COFF/PE (Windows).
>
>```bash
>gcc -c main.s -o main.o
># или
>as main.s -o main.o
>```
>
>Объектный файл — это ещё **не** готовая программа. В нём:
>
>- секции с кодом и данными;
>- неразрешённые ссылки (например, на `printf`);
>- релокации;
>- таблица символов.
>
>Посмотреть:
>
>```bash
>objdump -d main.o        # дизассемблировать
>readelf -a main.o        # все секции и символы
>nm main.o                # символы
>```

> Этап 6. Линкер (`ld`)

> [!INFO]- Линкер собирает один или несколько `.o` в один исполняемый файл.
>Что делает:
>
>1. **Объединяет секции** из всех объектных файлов: все `.text` вместе, все `.data` вместе.
>2. **Разрешает символы**: `printf` был неопределён в `main.o`, но найден в `libc.so` или `libc.a`.
>3. **Применяет релокации**: подставляет реальные адреса в места, где ассемблер оставил заглушки.
>4. **Раскладывает адреса**: присваивает каждой секции виртуальный адрес.
>5. **Обрабатывает статические и динамические библиотеки**:
>    - статические (`.a`) — код копируется прямо в бинарник;
>    - динамические (`.so`, `.dll`) — линкер оставляет ссылку, а реальная загрузка происходит при запуске.
>6. **Строит таблицы**: GOT (global offset table), PLT (procedure linkage table) для динамических вызовов, таблицы экспорта/импорта.
>7. **Пишет ELF/PE** с заголовками, program headers, section headers, точкой входа.
>
>```bash
>gcc main.o -o main
># или явно
>ld main.o -lc -o main
>```
>
>Итог — исполняемый файл ELF на Linux или PE на Windows.
>
>Проверить:
>
>```bash
>file main
>readelf -h main      # заголовок
>readelf -l main      # program headers: какие сегменты куда мапятся
>objdump -d main      # финальный машинный код
>```


Многие компиляторы умеют показывать промежуточный код ассемблера:

```bash
gcc -S main.c   # получится main.s
clang -S main.c
go tool compile -S main.go
```

Некоторые компиляторы, например LLVM/Clang, могут генерировать объектный файл напрямую, без отдельного текстового `.s`. Go тоже имеет собственный toolchain и часто не вызывает внешний `as`. Но концептуально это не отменяет ассемблер: компилятор всё равно должен выбрать инструкции процессора и закодировать их в машинные байты. Просто ассемблер может быть встроен внутрь компилятора как библиотека.

- C/C++/Go обычно компилируются в **машинный код** для конкретной архитектуры.
- Машинный код — это и есть те самые «нули и единицы», но не в виде текста `0101`, а в виде байтов.
- Ассемблер — это либо отдельный этап, либо внутренний этап компилятора.
- «Сразу в нули и единицы без ассемблера» — это упрощение. На уровне ISA всё равно есть инструкции, которые язык ассемблера просто записывает мнемониками.

Пример:

```asm
mov eax, 1      ; B8 01 00 00 00
mov edi, 1      ; BF 01 00 00 00
syscall         ; 0F 05
```

Слева — ассемблер, справа — машинный код. Процессор исполняет то, что справа.

### Высокоуровневые языки

>Python:

```
script.py
  -> парсер
  -> AST
  -> байткод CPython (.pyc)
  -> интерпретатор CPython
  -> функции на C
  -> системные вызовы
```

Байткод Python — это не машинные инструкции. Это инструкции для виртуальной машины CPython. Их исполняет цикл интерпретатора, который сам написан на C и уже скомпилирован в машинный код.

То есть процессор исполняет не ваш `script.py`, а машинный код интерпретатора `python`. Ваш скрипт для него — данные. 

Есть исключения:
- PyPy, Numba и другие JIT-и могут компилировать горячий Python-код в машинный код.
- C-расширения Python — это уже нативный машинный код.

>JavaScript

В V8 / Node.js / браузере:

```
.js
  -> парсер
  -> байткод (Ignition)
  -> интерпретатор
  -> горячие функции
  -> JIT (TurboFan/Maglev)
  -> машинный код в памяти
```

Сначала JS часто исполняется как байткод. Потом горячие участки JIT-компилируются в машинный код. JIT-движок сам генерирует инструкции процессора и кладёт их в исполняемую память.

То есть JS-код тоже не становится ELF-файлом. Его исполняет движок, который уже является нативной программой.

>Java, C#, WebAssembly

Похожая идея:
- Java -> байткод JVM -> интерпретатор/JIT -> машинный код.
- C# -> IL -> CLR/JIT -> машинный код.
- WebAssembly -> байткод -> JIT/AOT -> машинный код.

### Итог

|Язык|Кто делает syscall|
|---|---|
|C/C++|сам бинарник (через libc)|
|Go|сам бинарник (напрямую или через runtime)|
|Rust|сам бинарник (через libc или напрямую)|
|Python|интерпретатор CPython|
|JavaScript|движок V8 / Node.js|
|Java|JVM|
|C#|CLR
