**[[notes/9_infrastructure/terraform/installation|Terraform]]** — это open-source инструмент для автоматизированного управления ИТ-инфраструктурой. Если говорить проще, он позволяет создавать и изменять серверы, базы данных и сети с помощью текстовых файлов, а не через ручную настройку в консоли провайдера. 

В основе Terraform лежит концепция **Infrastructure as Code (IaC)** — инфраструктура как код: 
- **Декларативный подход**: Вы описываете в конфигурационном файле _конечный результат_ (например, «мне нужно 3 сервера и база данных»), а Terraform сам вычисляет, какие действия нужно предпринять, чтобы это реализовать.
- **[[hcl-syntax|Язык HCL]]**: Конфигурации пишутся на языке _HashiCorp Configuration Language_, который легко читать и человеку, и машине.
- **Идемпотентность**: Инструмент проверяет текущее состояние ресурсов и вносит только те изменения, которые необходимы для достижения целевого состояния. 

#### Основные возможности

1. **Мультиоблачность**: Работает с сотнями провайдеров (AWS, Azure, Google Cloud, Yandex Cloud, VK Cloud, Proxmox, GitHub и др.) через специальные плагины — [[providers|провайдеры]].
2. **Управление состоянием (State)**: Terraform запоминает текущую конфигурацию инфраструктуры в специальном файле `terraform.tfstate`, что позволяет отслеживать изменения и безопасно их обновлять.
3. **Безопасность изменений**: С помощью команды `terraform plan` можно заранее увидеть список всех изменений (что будет создано, изменено или удалено), прежде чем применять их на практике. 
4. **[[workspaces|Workspaces]]:** Использование одного и того же кода в разных средах.

Часто Terraform используют вместе с инструментами вроде **[[notes/7_configuration/ansible/basics|Ansible]]**: Terraform создает «железо» (виртуальные машины, сети), а Ansible настраивает внутри них ПО и операционную систему. В отличие от Ansible, Terraform сохраняет состояние (в файле Tfstate).

#### Основные сущности (Логика)

- **[[providers|Провайдеры (Providers)]]**: плагины для взаимодействия с API облаков (AWS, Yandex Cloud, Azure и др.).
- **[[hcl-syntax|Ресурсы (Resources)]]**: конкретные объекты инфраструктуры, которыми мы управляем (виртуальная машина, диск, DNS-запись).
- **[[notes/9_infrastructure/terraform/modules|Модули (Modules)]]**: контейнеры для группы ресурсов, которые позволяют повторно использовать один и тот же код в разных проектах.

#### State (Состояние)

Это файл `terraform.tfstate` (в формате JSON). Это «память» Terraform, связующее звено между вашим кодом и реальностью.

- **Зачем нужен:** Terraform должен знать, что именно он создал. Если вы удалите строку из кода, Terraform посмотрит в State, увидит, что этот ресурс раньше был, и поймет, что его нужно удалить в облаке.
- **Безопасность:** В State могут храниться пароли в открытом виде, поэтому его нельзя выкладывать в публичные репозитории.
- **Backend:** В серьезных проектах State хранят не на компьютере, а в удаленном хранилище (S3, Terraform Cloud, GitLab), чтобы несколько инженеров могли работать над одной инфраструктурой одновременно (используя блокировки/locking).

`terraform.tfstate` - Актуальный файл состояния
`terraform.tfstate.backup` - Автомастический бэкап, созданный командой apply, для того, чтобы была возможность вернуться к текущему состонию инфраструктуры.

После установки нужно создать файловую структуру проекта:

- `main.tf` - Основной файл (описание провайдеров, ресурсов, datasource)
- `variables.tf` - Хранение обычных переменных:

```hcl
variable "proxmox_api_token" {}
variable "gateway" {}
...
```

- `outputs.tf` - Описание данных, которые Terraform выведет после завершения работы (например, IP-адрес созданного сервера).

```hcl
output "vm_public_ip" {
  value = yandex_compute_instance.vm-1.network_interface.0.nat_ip_address
}
```

- `provider.tf`: настройки подключения к провайдерам (токены, регионы).

```hcl
terraform {
  required_providers {
    proxmox = {
      source = "bpg/proxmox"
    }
  }
}  

provider "proxmox" {
    endpoint = "https://192.168.100.1:8006/"
    api_token = var.proxmox_api_token
    insecure = true
}
```

- `\*.tfvars` - Можно указать значение переменных из variables (самостоятельно не подхватывает, нужно указать при `terraform apply`) Для того, чтобы использовать переменные с файлов `\*.tfvars`, необходимо их объявить в `variables.tf`

```hcl
proxmox_api_token = ""
gateway = ""
...
```

Терраформ съедает все файлы из директории вызова.


Terraform оперирует двумя главными источниками, **Resources (Ресурсы для изменения)** **Data Sources (Источники данных)**.

Если **Resources (Ресурсы)** создают, изменяют и удаляют инфраструктуру, то **Data Sources** предназначены исключительно для чтения и получения информации о уже существующей инфраструктуре.


1. Resources (Ресурсы) — Блок `resource`

Это **созидательный** компонент. Он объявляет элемент инфраструктуры, которым Terraform должен управлять: создавать, обновлять настройки или уничтожать.

- **Как это выглядит в коде:** Начинается со слова `resource`, далее идет тип ресурса и ваше внутреннее имя.
- **Логика работы:** Terraform проверяет свой файл состояния (_state_). Если ресурса там нет, он отправляет `POST`-запрос к API провайдера (например, Proxmox или Yandex Cloud) на создание. Если ресурс изменился в коде, Terraform шлет `PATCH/PUT`-запрос на обновление.
- **Пример (Создание новой ВМ в Proxmox):**


```hcl
resource "proxmox_virtual_environment_vm" "web_server" {
	name      = "prod-web-01"
	node_name = "pve-node-1"
# ... другие параметры для создания ...
}
```

2. Data Sources (Источники данных) — Блок `data`

Это **читающий** компонент. Он позволяет Terraform запросить данные у API провайдера о том, что _уже существует_ вне текущего кода Terraform (было создано вручную, другой командой или другим стейтом Terraform).

- **Как это выглядит в коде:** Начинается со слова `data`, далее идет тип источника (обычно совпадает по префиксу с ресурсом) и внутреннее имя.
- **Логика работы:** Terraform делает исключительно `GET`-запросы к API. Он ничего не создает и не меняет. Он просто "подглядывает" параметры объекта, чтобы вы могли использовать их в блоках `resource`.
- **Пример (Узнать ID существующего диска или шаблона в Proxmox):**


```hcl
# Находим ISO-образ, который уже лежит на сервере
data "proxmox_virtual_environment_file" "ubuntu_iso" {
node_name    = "pve-node-1"
datastore_id = "local"
content_type = "iso"
filename     = "ubuntu-24.04-live-server-amd64.iso"
}

# Используем полученные данные (data.proxmox_virtual_environment_file...) 
# для создания новой виртуалки
resource "proxmox_virtual_environment_vm" "web_server" {
name      = "prod-web-01"
node_name = "pve-node-1"

cdrom {
# Передаем ID файла, который Terraform нашел через блок data выше
file_id = data.proxmox_virtual_environment_file.ubuntu_iso.id
}
```
