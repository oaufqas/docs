**Proxmox Virtual Environment (Proxmox VE)** — это полноценная open-source платформа виртуализации корпоративного уровня, основанная на дистрибутиве **Debian Linux**. Это **гипервизор типа 1 (Bare-Metal)**, который устанавливается напрямую на «голое железо» сервера, полностью заменяя собой обычную операционную систему. 

Proxmox завоевал мировую популярность благодаря тому, что объединил сложнейшие низкоуровневые технологии ядра Linux в единую, красивую и бесплатную веб-панель управления.

**ProxmoxVE относится к Гипервизорам 1-го типа (Bare-Metal).

- _Почему, ведь под ним Debian?_ Модуль **KVM** интегрирован прямо в ядро Linux. При загрузке компьютера Linux запускается как тончайшая прослойка, и процессор сразу переходит в режим аппаратной виртуализации. Виртуалки работают на физической скорости процессора, минуя эмуляцию пространства пользователя, что делает Proxmox полноценной "голой" промышленной ОС-гипервизором. НО, если на чистой ubuntu запустить связку KVM/QEMU то это будет аналогично считаться гипервизором **1 типа**. Поэтому proxmox не уникальный гипервизор, а просто удобные утилиты и графическая оболочка.

#### Proxmox оперирует двумя методами Виртуализацей и Контейнеризацей

А. Полноценные виртуальные машины (**[[hardware-virtualization|KVM/QEMU]]**)

Используются для запуска тяжелых, полностью изолированных ОС (Windows, FreeBSD, другие ядра Linux).
- **Под капотом:** Работает тандем модуля ядра `KVM` и эмулятора `QEMU`. Каждая ВМ имеет свое виртуальное железо, свой BIOS/UEFI и свое ядро в памяти.


Б. Системные контейнеры (LXC — Linux Containers)

Альтернатива виртуалкам, когда нужно запустить какой-то Linux-сервис (базу данных, VPN-сервер, веб-сайт), не тратя ресурсы на эмуляцию железа.
- **Под капотом:** Работают механизмы **[[cgroups-namespaces|Namespaces и Cgroups v2]]**. У LXC-контейнера _нет своего ядра_, он делит ядро Debian-хоста Proxmox со всеми остальными.
- **В чем разница с Docker:** Docker изолирует _одно конкретное приложение_ (процесс), а LXC изолирует _целую операционную систему_ (внутри LXC работает свой systemd, свой syslog и т.д., но на общем ядре)

### Сетевая подсистема

По умолчанию сеть в Proxmox организуется через встроенный в ядро Linux механизм **Linux Bridge (Сетевой мост)**. В панели Proxmox этот мост называется **`vmbr0`**.

```text
 ДОМАШНИЙ РОУТЕР <───> [ Физическая карта nic0 ]
                                 │
                                 ▼
                       [ Сетевой мост vmbr0 ]
                                 │
         ┌───────────────────────┴───────────────────────┐
         ▼                                               ▼
 [ Виртуалка Master ]                             [ Виртуалка Worker ]
 (Получает IP от роутера)                         (Получает IP от роутера)
```

Мост `vmbr0` привязывается к реальной физической сетевой карте. Он работает как виртуальный неуправляемый коммутатор (свитч). 

При создавании виртуалок, их виртуальные сетевые карты будут «втыкаться» в этот мост `vmbr0`. В итоге роутер будет видеть каждую виртуалку как отдельный независимый компьютер, подключенный по кабелю, и выдаст им нормальные IP-адреса из пулла подсети (например, `192.168.1.50`, `192.168.1.51`).

#### API-Tokens

Зачем они нужны:

1. **Вход без пароля:** Токен заменяет собой связку «логин + пароль». Terraform отправляет этот ключ в каждом сетевом HTTP-запросе к админке Proxmox, подтверждая, что он — это он.
2. **Защита основного пароля (Безопасность):** Если вы пропишете в коде Terraform ваш реальный пароль от `root`, и этот код случайно утечет в публичный Git, хакеры получат полный контроль над всем моноблоком. Токен же можно в любой момент отозвать (аннулировать) в панели Proxmox одной кнопкой, не меняя системные пароли.
3. **Ограничение прав (Разделение доступов):** Вы можете выпустить токен и жестко ограничить его права (например, разрешить ему _только_ создавать виртуалки, но запретить удалять диски, менять настройки Wi-Fi или читать логи хоста). Если Terraform взломают, ущерб будет минимальным.

Чтобы можно было взаимодействовать с proxmox из других источников, например terrafom, нужно создать токены подключения 

```
Datacenter -> Permissions -> API Tokens
```

В Proxmox VE токен всегда жестко привязан к конкретному пользователю и состоит из двух частей, разделенных знаком равенства или двоеточием:

- **Идентификатор (Token ID):** Открытая часть. Показывает, какому юзеру принадлежит ключ. Выглядит так: `terraform-user@pve!tf-token-name`.
- **Секрет (Secret Custom Value):** Закрытая часть (пароль токена). Генерируется сервером **ровно один раз** при создании. Выглядит как длинный хэш: `9b8452-f404-4789-80dd-bfdef`.

Создание пользователя и генерирование пароля через pve-cli:

```bash
# 1. Создаем нового пользователя в пространстве Proxmox (pve)
pveum user add terraform-user@pve -comment "User for Terraform IaC"

# 2. Создаем для него роль с правами администратора виртуалок (PVEVMAdmin)
# и привязываем её к корню хранилища, чтобы TF мог нарезать диски и сети
pveum aclmodify / -user terraform-user@pve -role PVEVMAdmin

# 3. Генерируем сам API-токен для этого пользователя
pveum user token add terraform-user@pve tf-token --privsep 0
```

По умолчанию Proxmox создает токены с флагом `privsep 1` (разделение привилегий). Это значит, что токен имеет _еще меньше_ прав, чем сам создавший его пользователь. В ручных сборках это часто приводит к тому, что Terraform падает с ошибкой `Permission Denied` при попытке создать Cloud-Init диск. Флаг `--privsep 0` говорит системе: _«Этот токен имеет точно такие же права, как и сам юзер terraform-user»_.
