**Сокет** — это абстракция для сетевого взаимодействия или межпроцессного обмена. С точки зрения программиста это **файловый дескриптор** (на Linux) или **handle** (на Windows), через который можно читать и писать данные. Ядро берёт на себя всю работу с сетевыми протоколами, буферизацией, ретрансмиссией.

Когда вы работаете с TCP, сокет последовательно проходит через цепочку состояний. Посмотреть их вживую в Linux можно командой `ss -ant` или `netstat -ant`.

1. Стадия инициализации и ожидания

- **`CLOSED`** — сокет создан (через вызов `socket()`), но он полностью пассивен, сетевого соединения нет.
- **`LISTEN`** — состояние **только для сервера** (после вызовов `bind()` и `listen()`). Сервер открыл порт и ждет, когда клиент начнет Handshake.

2. Стадия установления соединения (TCP 3-Way Handshake)

- **`SYN_SENT`** — состояние **клиента**. Клиент отправил первый пакет `SYN` (хочу подключиться) через вызов `connect()` и ждет ответа от сервера.
- **`SYN_RECEIVED` (или `SYN_RECV`)** — состояние **сервера**. Сервер получил `SYN` от клиента, отправил в ответ `SYN-ACK` и ждет финального подтверждения.
- **`ESTABLISHED`** — соединение успешно установлено! Обе стороны (и клиент, и сервер) перешли в этот режим после вызова `accept()` на сервере. Теперь можно вызывать `read()` и `write()`.

3. Стадия закрытия соединения (TCP 4-Way Close)

Закрытие TCP — процесс сложный, так как одна сторона может закончить передачу, а вторая еще продолжать слать данные (полузакрытое соединение).

- **`FIN_WAIT_1`** — процесс (например, клиент) решил закрыть сокет и вызвал `close()`. Он отправил пакет `FIN` и ждет ответа.
- **`CLOSE_WAIT`** — противоположная сторона (сервер) получила `FIN` от клиента. Ядро Linux перевело сокет сервера в этот режим. Это означает: _«Клиент больше ничего не пришлет, но я (сервер) еще могу отправить ему остатки данных перед тем, как сам вызову close()»_
- **`FIN_WAIT_2`** — клиент получил подтверждение (`ACK`) от сервера на свой `FIN`, но сам сервер свой `FSN` еще не прислал. Клиент ждет.
- **`LAST_ACK`** — сервер наконец вызвал `close()`, отправил свой `FIN` и ждет финального `ACK` от клиента.
- **`TIME_WAIT`** — **самое коварное состояние.** Тот, кто первым инициировал закрытие сокета, на 1–2 минуты (в зависимости от настроек ядра `2 * MSL`) зависает в `TIME_WAIT`.
    - _Зачем это нужно:_ Гарантировать, что финальный пакет `ACK` долетел до сервера, и старые пакеты, заблудившиеся в интернете, не прилетят в новое соединение, открытое на этом же порту.
    - _Проблема:_ Если сервер упадет, его порт `8080` зависнет в `TIME_WAIT`. Если его сразу перезапустить, вы получите ошибку `Address already in use`. Именно поэтому в коде нужно опцию **`SO_REUSEADDR`**, чтобы заставить ядро Linux игнорировать `TIME_WAIT`.

#### Основные 8 операций с сокетами

Стандартный жизненный цикл сокета — это примерно 8 ключевых системных вызовов. У сервера и клиента порядок отличается.

|#|Операция|Сервер|Клиент|Назначение|
|---|---|---|---|---|
|1|`socket()`|✓|✓|Создать сокет, получить fd|
|2|`bind()`|✓|редко|Привязать к адресу и порту|
|3|`listen()`|✓|✗|Перевести в режим приёма соединений|
|4|`accept()`|✓|✗|Принять входящее соединение|
|5|`connect()`|✗|✓|Установить соединение с сервером|
|6|`send()` / `recv()`|✓|✓|Передача и приём данных|
|7|`shutdown()`|✓|✓|Корректно закрыть одну сторону|
|8|`close()`|✓|✓|Освободить дескриптор|

Дополнительно:

- `setsockopt()` / `getsockopt()` — настройка параметров (таймауты, буферы, `SO_REUSEADDR`, `TCP_NODELAY`).
- `getaddrinfo()` / `getnameinfo()` — резолв имён и адресов.
- `select()` / `poll()` / `epoll()` — мультиплексирование (один поток на много сокетов).
- `sendto()` / `recvfrom()` — для UDP с указанием адреса.
- `sendmsg()` / `recvmsg()` — scatter/gather I/O, передача вспомогательных данных.

### Каждая операция подробно

#### `socket()` — создание

```cpp
#include <sys/socket.h>

int fd = socket(AF_INET, SOCK_STREAM, 0);
if (fd < 0) {
    perror("socket");
    // обработка
}
```

Возвращает файловый дескриптор или -1. После этого сокет существует в ядре, но ещё не привязан ни к какому адресу. 

`int socket(int address, int type, int protocol);`

Домен определяет пространство адресов, в котором располагается сокет, и множество протоколов, которые используются для передачи данных. Чаще других используются домены Unix и Internet, задаваемые константами **AF_UNIX** и **AF_INET** соответственно (префикс AF означает "address family" - "семейство адресов"). При задании **AF_UNIX** для передачи данных используется файловая система ввода/вывода Unix. В этом случае сокеты используются для межпроцессного взаимодействия на одном компьютере и не годятся для работы по сети. Константа **AF_INET** соответствует Internet-адресу. Сокеты, размещённые в этом адресе, могут использоваться для работы в любой IP-сети. Существуют и другие домены (**AF_IPX** для протоколов Novell, **AF_INET6** для новой модификации протокола IP - IPv6 и т. д.).

Тип сокета определяет способ передачи данных по сети. Чаще других применяются:

- **`SOCK_STREAM`** (TCP). Передача потока данных с предварительной установкой соединения. Обеспечивается надёжный канал передачи данных, при котором фрагменты отправленного блока не теряются, не переупорядочиваются и не дублируются. Поскольку этот тип сокетов является самым распространённым, до конца раздела мы будем говорить только о нём. Остальным типам будут посвящены отдельные разделы.

- **`SOCK_DGRAM`** (UDP). Передача данных в виде отдельных сообщений (датаграмм). Предварительная установка соединения не требуется. Обмен данными происходит быстрее, но является ненадёжным: сообщения могут теряться в пути, дублироваться и переупорядочиваться. Допускается передача сообщения нескольким получателям (multicasting) и широковещательная передача (broadcasting).

- **`SOCK_RAW`**. Этот тип присваивается низкоуровневым (т. н. "сырым") сокетам. Их отличие от обычных сокетов состоит в том, что с их помощью программа может взять на себя формирование некоторых заголовков, добавляемых к сообщению.

- **`SOCK_SEQPACKET`**. Cообщения с сохранением границ.

Обратите внимание, что не все домены допускают задание произвольного типа сокета. Например, совместно с доменом Unix используется только тип **SOCK_STREAM**. С другой стороны, для Internet-домена можно задавать любой из перечисленных типов. В этом случае для реализации **SOCK_STREAM** используется протокол TCP, для реализации **SOCK_DGRAM** - протокол UDP, а тип **SOCK_RAW** используется для низкоуровневой работы с протоколами IP, ICMP и т. д.

Наконец, последний атрибут определяет протокол, используемый для передачи данных. Как мы только что видели, часто протокол однозначно определяется по домену и типу сокета. В этом случае в качестве третьего параметра функции **socket** можно передать 0, что соответствует протоколу по умолчанию. Тем не менее, иногда (например, при работе с низкоуровневыми сокетами) требуется задать протокол явно. Числовые идентификаторы протоколов зависят от выбранного домена; их можно найти в документации.


#### `bind()` — привязка к адресу

```cpp
#include <netinet/in.h>
#include <arpa/inet.h>

sockaddr_in addr{};
addr.sin_family = AF_INET;
addr.sin_port = htons(8080);              // порт в сетевом порядке байт
addr.sin_addr.s_addr = htonl(INADDR_ANY); // слушать все интерфейсы

if (bind(fd, reinterpret_cast<sockaddr*>(&addr), sizeof(addr)) < 0) {
    perror("bind");
}
```

Прежде чем передавать данные через сокет, его необходимо связать с адресом в выбранном домене (эту процедуру называют именованием сокета). Иногда связывание осуществляется неявно (внутри функций **`connect()`** и **`accept()`**), но выполнять его необходимо во всех случаях. Вид адреса зависит от выбранного вами домена. В Unix-домене это текстовая строка - имя файла, через который происходит обмен данными. В Internet-домене адрес задаётся комбинацией IP-адреса и 16-битного номера порта. IP-адрес определяет хост в сети, а порт - конкретный сокет на этом хосте. Протоколы TCP и UDP используют различные пространства портов.

Для явного связывания сокета с некоторым адресом используется функция **bind**. Её прототип имеет вид:

`int bind(int sockfd, struct sockaddr *addr, int addrlen);`

В качестве первого параметра передаётся дескриптор сокета, который мы хотим привязать к заданному адресу. Второй параметр, **addr**, содержит указатель на структуру с адресом, а третий - длину этой структуры. Посмотрим, что она собой представляет.

```cpp
struct sockaddr {
    unsigned short    sa_family;    // Семейство адресов, AF_xxx
    char              sa_data[14];  // 14 байтов для хранения адреса
};
```

Поле **sa_family** содержит идентификатор домена, тот же, что и первый параметр функции **socket**. В зависимости от значения этого поля по-разному интерпретируется содержимое массива **sa_data**. Разумеется, работать с этим массивом напрямую не очень удобно, поэтому вы можете использовать вместо **sockaddr** одну из альтернативных структур вида **sockaddr_XX** (XX - суффикс, обозначающий домен: "un" - Unix, "in" - Internet и т. д.). При передаче в функцию **bind** указатель на эту структуру приводится к указателю на **sockaddr**. Рассмотрим для примера структуру **sockaddr_in**.

```cpp
struct sockaddr_in {
    short int          sin_family;  // Семейство адресов
    unsigned short int sin_port;    // Номер порта
    struct in_addr     sin_addr;    // IP-адрес
    unsigned char      sin_zero[8]; // "Дополнение" до размера структуры sockaddr
};
```

Здесь поле **sin_family** соответствует полю **sa_family** в **sockaddr**, в **sin_port** записывается номер порта, а в **sin_addr** - IP-адрес хоста. Поле **sin_addr** само является структурой, которая имеет вид:

```cpp
struct in_addr {
    unsigned long s_addr;
};
```

Зачем понадобилось заключать всего одно поле в структуру? Дело в том, что раньше **in_addr** представляла собой объединение (union), содержащее гораздо большее число полей. Сейчас, когда в ней осталось всего одно поле, она продолжает использоваться для обратной совместимости.

`reinterpret_cast<sockaddr*>(&addr)` — это **приведение указателя одного типа к другому без изменения самих байтов**. В функциях сокетов (`bind`, `connect`, `accept`, `sendto`, `recvfrom`) API исторически требует указатель на **обобщённый** тип `sockaddr*`. Но реально вы всегда передаёте указатель на **конкретный** тип: `sockaddr_in` (IPv4), `sockaddr_in6` (IPv6), `sockaddr_un` (Unix-сокет). Все эти структуры начинаются с общего поля `sa_family_t sa_family`, поэтому ядро может по первым байтам понять, какой это тип, и корректно прочитать остальное.

```
&addr (sockaddr_in*)         reinterpret_cast (sockaddr*)
+---------------------+      +---------------------+
| sin_family (2 байта)|      | sa_family (2 байта) |  <- те же байты,
| sin_port   (2 байта)|      | sa_data  (14 байт)  |     просто другое имя
| sin_addr   (4 байта)|      +---------------------+
| padding    (8 байт) |
+---------------------+
```

- `static_cast<sockaddr*>(&addr)` — **не скомпилируется**: типы не связаны наследованием, компилятор не знает, как их преобразовать.
- `reinterpret_cast` разрешён для любых указателей и говорит: «переинтерпретируй биты».
- В C это же делается неявным приведением `(sockaddr*)&addr` или явным — суть та же.

**Итог**:

- `reinterpret_cast<sockaddr*>(&addr)` — это «посмотри на те же байты как на обобщённый адрес сокета».
- Нужен, потому что API сокетов старый и использует общий тип `sockaddr`.
- Данные не меняются, меняется только тип указателя.
- Всегда передавайте `sizeof` конкретной структуры, а не `sizeof(sockaddr)`.

И ещё одно важное замечание. Существует два порядка хранения байтов: в слове и двойном слове. Один из них называется _порядком хоста_ (host byte order), другой - _сетевым порядком_ (network byte order) хранения байтов. При указании IP-адреса и номера порта необходимо преобразовать число из порядка хоста в сетевой. Для этого используются функции **`htons`** (Host TO Network Short) и **`htonl`** (Host TO Network Long). Обратное преобразование выполняют функции **`ntohs`** и **`ntohl`**.

| **ПРИМЕЧАНИЕ**                                                                                                                                                                                                                                                                                                                                                                                        |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| На некоторых машинах (к PC это не относится) порядок хоста и сетевой порядок хранения байтов совпадают. Тем не менее, функции преобразования лучше применять и там, поскольку это улучшит переносимость программы. Это никак не скажется на производительности, так как препроцессор сам уберёт все "лишние" вызовы этих функций, оставив их только там, где преобразование действительно необходимо. |

**Порядок байт**: сеть работает в big-endian, x86 — little-endian. Поэтому `htons` (host to network short) и `htonl` (host to network long). Для 64-битных — `htobe64`.

Полезные константы:
- `INADDR_ANY` = 0.0.0.0 — все интерфейсы.
- `INADDR_LOOPBACK` = 127.0.0.1 — только локально.


#### `listen()` — перевод в режим сервера

```cpp
if (listen(fd, SOMAXCONN) < 0) {
	perror("listen");
}
```

Установка соединения на стороне сервера состоит из четырёх этапов, ни один из которых не может быть опущен. Сначала сокет создаётся и привязывается к локальному адресу. Если компьютер имеет несколько сетевых интерфейсов с различными IP-адресами, вы можете принимать соединения только с одного из них, передав его адрес функции **bind**. Если же вы готовы соединяться с клиентами через любой интерфейс, задайте в качестве адреса константу **INADDR_ANY**. Что касается номера порта, вы можете задать конкретный номер или 0 (в этом случае система сама выберет произвольный неиспользуемый в данный момент номер порта).

На следующем шаге создаётся очередь запросов на соединение. При этом сокет переводится в режим ожидания запросов со стороны клиентов. Всё это выполняет функция **listen**.

`int listen(int sockfd, int backlog);`

Первый параметр - дескриптор сокета, а второй аргумент — размер очереди ожидающих соединений (backlog). Каждый раз, когда очередной клиент пытается соединиться с сервером, его запрос ставится в очередь, так как сервер может быть занят обработкой других запросов. `SOMAXCONN` — системный максимум (обычно 128 или 4096). Соединения, не успевшие попасть в очередь, отвергаются или игнорируются в зависимости от `tcp_abort_on_overflow`. Когда сервер готов обслужить очередной запрос, он использует функцию **`accept()`**. 


#### `accept()` — прием соединения

```cpp
sockaddr_in client_addr{};
socklen_t client_len = sizeof(client_addr);

int client_fd = accept(fd,
                       reinterpret_cast<sockaddr*>(&client_addr),
                       &client_len);
if (client_fd < 0) {
    perror("accept");
}
```

**`accept` блокирующий**: если нет входящих соединений, поток спит. Возвращает **новый** fd для общения с конкретным клиентом. Исходный fd продолжает слушать.

`int accept(int sockfd, void *addr, int *addrlen);`

Функция **accept** создаёт для общения с клиентом _новый_ сокет и возвращает его дескриптор. Параметр **sockfd** задаёт слушающий сокет. После вызова он остаётся в слушающем состоянии и может принимать другие соединения. В структуру, на которую ссылается **addr**, записывается адрес сокета клиента, который установил соединение с сервером. В переменную, адресуемую указателем **addrlen**, изначально записывается размер структуры; функция **accept** записывает туда длину, которая реально была использована. Если вас не интересует адрес клиента, вы можете просто передать NULL в качестве второго и третьего параметров.

Чтобы получить ip и порт клиента:

```cpp
char ip[INET_ADDRSTRLEN];
inet_ntop(AF_INET, &client_addr.sin_addr, ip, sizeof(ip));
std::cout << "Client: " << ip << ":" << ntohs(client_addr.sin_port);
```

Обратите внимание, что полученный от **accept** новый сокет связан с тем же самым адресом, что и слушающий сокет. Сначала это может показаться странным. Но дело в том, что адрес TCP-сокета не обязан быть уникальным в Internet-домене. Уникальными должны быть только _соединения_, для идентификации которых используются _два_ адреса сокетов, между которыми происходит обмен данными.


#### `connect()` — установка соединения

```cpp
sockaddr_in server{};
server.sin_family = AF_INET;
server.sin_port = htons(8080);
inet_pton(AF_INET, "127.0.0.1", &server.sin_addr);

if (connect(fd, reinterpret_cast<sockaddr*>(&server), sizeof(server)) < 0) {
    perror("connect");
}
```

На стороне клиента для установления соединения используется функция **connect**, которая имеет следующий прототип.

`int connect(int sockfd, struct sockaddr *serv_addr, int addrlen);`

Здесь **sockfd** - сокет, который будет использоваться для обмена данными с сервером, **serv_addr** содержит указатель на структуру с адресом сервера, а **addrlen** - длину этой структуры. Обычно сокет не требуется предварительно привязывать к локальному адресу, так как функция **connect** сделает это за вас, подобрав подходящий свободный порт. Вы можете принудительно назначить клиентскому сокету некоторый номер порта, используя **bind** перед вызовом **connect**. Делать это следует в случае, когда сервер соединяется с только с клиентами, использующими определённый порт (примерами таких серверов являются rlogind и rshd). В остальных случаях проще и надёжнее предоставить системе выбрать порт за вас.

`inet_pton` = **p**resentation **to** **n**etwork. Преобразует IP-адрес из **текстового** вида (`"127.0.0.1"`, `"192.168.1.1"`, `"::1"`) в **бинарный сетевой** формат и записывает его по указателю в третьем аргументе, указывается **адрес самой вложенной структуры `in_addr`** (то есть `&server.sin_addr`), а не её поле `s_addr`. `inet_ntop` наоборот преобразует из бинарного в текстовый вид.

Для TCP выполняет трёхстороннее рукопожатие (SYN, SYN-ACK, ACK). Для UDP просто запоминает адрес назначения.

Для неблокирующего сокета `connect` вернёт `-1` с `errno == EINPROGRESS`, и надо ждать готовности через `poll`/`epoll`.


#### `send()` и `recv()` — обмен данными

```cpp
const char* msg = "hello";
ssize_t sent = send(fd, msg, strlen(msg), 0);
if (sent < 0) {
    perror("send");
}

char buf[1024];
ssize_t n = recv(fd, buf, sizeof(buf), 0);
if (n < 0) {
    perror("recv");
} else if (n == 0) {
    // соединение закрыто удалённой стороной
} else {
    // обработать n байт
}
```

После того как соединение установлено, можно начинать обмен данными. Для этого используются функции **send** и **recv**. В Unix для работы с сокетами можно использовать также файловые функции **read** и **write**, но они обладают меньшими возможностями, а кроме того не будут работать на других платформах (например, под Windows), поэтому не рекомендуется ими пользоваться.

Функция **send** используется для отправки данных и имеет следующий прототип.

`int send(int sockfd, const void *msg, int len, int flags);`

Здесь **sockfd** - это, как всегда, дескриптор сокета, через который мы отправляем данные, **msg** - указатель на буфер с данными, **len** - длина буфера в байтах, а **flags** - набор битовых флагов, управляющих работой функции (если флаги не используются, передайте функции 0). Вот некоторые из них (полный список можно найти в документации):

- **MSG_OOB**. Предписывает отправить данные как _срочные_ (out of band data, OOB). Концепция срочных данных позволяет иметь два параллельных канала данных в одном соединении. Иногда это бывает удобно. Например, Telnet использует срочные данные для передачи команд типа Ctrl+C. В настоящее время использовать их не рекомендуется из-за проблем с совместимостью (существует два разных стандарта их использования, описанные в RFC793 и RFC1122). Безопаснее просто создать для срочных данных отдельное соединение.
- **MSG_DONTROUTE**. Запрещает маршрутизацию пакетов. Нижележащие транспортные слои могут проигнорировать этот флаг.

Функция **send** возвращает число байтов, которое на самом деле было отправлено (или -1 в случае ошибки). Это число может быть меньше указанного размера буфера. Если вы хотите отправить весь буфер целиком, вам придётся написать свою функцию и вызывать в ней **send**, пока все данные не будут отправлены. Она может выглядеть примерно так.

```cpp
int sendall(int s, char *buf, int len, int flags)
{
    int total = 0;
    int n;

    while(total < len)
    {
        n = send(s, buf+total, len-total, flags);
        if(n == -1) { break; }
        total += n;
    }

    return (n==-1 ? -1 : total);
}
```

Использование **sendall** ничем не отличается от использования **send**, но она отправляет весь буфер с данными целиком.
Цикл в функции `sendall` начнет дробить вызовы `send()`, если возникнет одна из двух ситуаций:
1. **Буфер ядра переполнен:** Если вы начнете отправлять огромный файл (например, 500 Мегабайт) в очень медленный сетевой канал, ядро не успеет отправлять пакеты в сеть. Буфер сокета забьется, и очередной вызов `send()` вернет, например, только `4096` байт (сколько осталось места в буфере), а не весь размер. Вот тогда ваш цикл сделает следующую итерацию `total += sent` и дошлет остаток.
2. **Неблокирующие сокеты (`O_NONBLOCK`):** Если перевести сокет в неблокирующий режим, ядро никогда не ждет. Оно берет ровно столько байт, сколько может принять в буфер прямо в эту микросекунду, и возвращает это число. В таком режиме ваш цикл будет работать постоянно.

#### Возвращаемые значения `send()`

|`n`|Что значит|Что делать|
|---|---|---|
|`n > 0`|Отправлено `n` байт|Учесть и продолжить с `buf + n`|
|`n == 0`|Практически не бывает для TCP. Возможен на некоторых системах при `len == 0`|Считать как «ничего не отправлено», обработать как частичную отправку|
|`n == -1`, `errno == EAGAIN`/`EWOULDBLOCK`|Буфер отправки полон, сокет неблокирующий|Ждать `POLLOUT` через `poll`/`epoll` и повторить|
|`n == -1`, `errno == EINTR`|Прерван сигналом до отправки хоть чего-то|Повторить `send`|
|`n == -1`, `errno == EPIPE`|Удалённая сторона закрыла соединение|Прекратить отправку, `close`. **Также приходит `SIGPIPE`**, если не отключён|
|`n == -1`, `errno == ECONNRESET`|Соединение сброшено (RST)|`close`, прекратить|
|`n == -1`, `errno == ENOTCONN`|Сокет не подключён|Программная ошибка|
|`n == -1`, `errno == EBADF`|Невалидный fd|Программная ошибка|
|`n == -1`, `errno == ENOBUFS` / `ENOMEM`|Нет памяти/буферов в ядре|Подождать и повторить|
|`n == -1`, `errno == EMSGSIZE`|Сообщение слишком велико (для UDP)|Разбить на части или уменьшить|
|`n == -1`, `errno == EACCES`|Нет прав (broadcast без `SO_BROADCAST` для UDP)|Настроить сокет|
|`n == -1`, `errno == EDESTADDRREQ`|Не указан адрес назначения (для UDP без `connect`)|Использовать `sendto`|

**Главное отличие от `recv`:** `n == 0` для `send` — это **не** EOF и **не** нормальное завершение. `send` не сигнализирует о закрытии соединения через 0. Закрытие ты узнаёшь через `-1` с `EPIPE` или через последующий `recv == 0`.


Для чтения данных из сокета используется функция **recv**.

`int recv(int sockfd, void *buf, int len, int flags);`

В целом её использование аналогично **send**. Она точно так же принимает дескриптор сокета, указатель на буфер и набор флагов. Флаг **MSG_OOB** используется для приёма срочных данных, а **MSG_PEEK** позволяет "подсмотреть" данные, полученные от удалённого хоста, не удаляя их из системного буфера (это означает, что при следующем обращении к **recv** вы получите те же самые данные). Полный список флагов можно найти в документации. По аналогии с **send** функция **recv** возвращает количество прочитанных байтов, которое может быть меньше размера буфера. Вы без труда сможете написать собственную функцию **recvall**, заполняющую буфер целиком. Существует ещё один особый случай, при котором **recv** возвращает 0. Это означает, что соединение было разорвано.

- **`recv` возвращает 0 при EOF** — это не ошибка, это закрытие.
- **TCP — поток байт, а не сообщения.** Границы сообщений не сохраняются. Нужно самим придумывать протокол: либо длина в заголовке, либо разделитель (`\n`).
- **Флаги**: `MSG_NOSIGNAL` (не посылать SIGPIPE при разрыве), `MSG_PEEK` (прочитать без удаления), `MSG_WAITALL` (ждать полный буфер).

#### Возвращаемые значения `recv`

```cpp
ssize_t n = recv(fd, buf, len, flags);
```

| `n`                                        | Что значит                                  | Что делать                           |
| ------------------------------------------ | ------------------------------------------- | ------------------------------------ |
| `n > 0`                                    | Прочитано `n` байт                          | Обработать                           |
| `n == 0`                                   | Соединение закрыто удалённой стороной (EOF) | Прекратить чтение, `close(fd)`       |
| `n == -1`, `errno == EAGAIN`/`EWOULDBLOCK` | Данных нет, сокет неблокирующий             | Повторить позже через `poll`/`epoll` |
| `n == -1`, `errno == EINTR`                | Вызов прерван сигналом                      | Повторить `recv`                     |
| `n == -1`, другие `errno`                  | Ошибка соединения                           | `perror`, закрыть сокет              |

Для UDP:

```cpp
sockaddr_in from{};
socklen_t from_len = sizeof(from);
ssize_t n = recvfrom(fd, buf, sizeof(buf), 0,
                     reinterpret_cast<sockaddr*>(&from), &from_len);
ssize_t sent = sendto(fd, msg, len, 0,
                      reinterpret_cast<sockaddr*>(&from), from_len);
```

UDP сохраняет границы датаграмм: одна отправка = одна приёмка (или потеря).

#### `shutdown()` — половинное закрытие

```cpp
shutdown(fd, SHUT_WR);  // больше не отправляем
shutdown(fd, SHUT_RD);  // больше не принимаем
shutdown(fd, SHUT_RDWR);
```

Вы можете запретить передачу данных в каком-то одном направлении, используя **shutdown**.

`int shutdown(int sockfd, int how);`

Параметр **how** может принимать одно из следующих значений:

- 0 - запретить чтение из сокета
- 1 - запретить запись в сокет
- 2 - запретить и то и другое

Хотя после вызова **shutdown** с параметром **how**, равным 2, вы больше не сможете использовать сокет для обмена данными, вам всё равно потребуется вызвать **close**, чтобы освободить связанные с ним системные ресурсы.

Отличие от `close`: `shutdown` немедленно уведомляет удалённую сторону (отправляет FIN для `SHUT_WR`), но fd остаётся открытым. `close` уменьшает счётчик ссылок на дескриптор и может не закрыть сокет, если есть дубликаты.

Типичный сценарий: клиент закончил отправку, вызывает `shutdown(fd, SHUT_WR)`, продолжает читать ответ, потом `close`.

#### `close()` — освобождение

Закончив обмен данными, закройте сокет с помощью функции **close**. Это приведёт к разрыву соединения.

```cpp
close(fd);
```

Освобождает дескриптор. Для TCP ядро отправляет FIN, ждёт ACK, переводит сокет в `TIME_WAIT` (2*MSL, обычно 60 сек). Это нормально, но при массовых коротких соединениях может забить порты — тогда используют `SO_REUSEADDR`.

#### `setsockopt()` — настройка сокета

```cpp
int opt = 1;
// Разрешить повторное использование адреса (важно для серверов при рестарте)
setsockopt(fd, SOL_SOCKET, SO_REUSEADDR, &opt, sizeof(opt));
// Отключить алгоритм Нейгла (снижает задержку для мелких пакетов)
setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &opt, sizeof(opt));
// Таймаут на recv/send
timeval tv{ .tv_sec = 5, .tv_usec = 0 };
setsockopt(fd, SOL_SOCKET, SO_RCVTIMEO, &tv, sizeof(tv));
setsockopt(fd, SOL_SOCKET, SO_SNDTIMEO, &tv, sizeof(tv));
// Размер буферов
int bufsize = 1 << 20;
setsockopt(fd, SOL_SOCKET, SO_RCVBUF, &bufsize, sizeof(bufsize));
setsockopt(fd, SOL_SOCKET, SO_SNDBUF, &bufsize, sizeof(bufsize));
// Не посылать SIGPIPE при разрыве (альтернатива MSG_NOSIGNAL)
setsockopt(fd, SOL_SOCKET, SO_NOSIGPIPE, &opt, sizeof(opt));  // только macOS/BSD
```

На Linux `SO_NOSIGPIPE` нет — используйте `MSG_NOSIGNAL` или `signal(SIGPIPE, SIG_IGN)`.

#### Обработка ошибок

Eсли что-то пошло не так, все рассмотренные функции возвращают -1, записывая в глобальную переменную **errno** код ошибки. Соответственно, вы можете проанализировать значение этой переменной и предпринять действия по восстановлению нормальной работы программы, не прерывая её выполнения. А можете просто выдать диагностическое сообщение (для этого удобно использовать функцию **perror**), а затем завершить программу с помощью **exit**. Именно так я буду поступать в демонстрационных примерах.

Типичные ошибки:

1. **Забыть `htons`/`htonl`** — соединение уйдёт не на тот порт.
2. **Не проверять возврат `send`** — часть данных потеряется.
3. **Считать, что `recv` вернёт всё сообщение за раз** — TCP режет по-своему.
4. **Не обрабатывать `EINTR`** — сигнал прерывает системный вызов, надо повторять.
5. **Игнорировать `SIGPIPE`** — процесс убьётся при разрыве. Ставьте `MSG_NOSIGNAL` или `signal(SIGPIPE, SIG_IGN)`.
6. **Не вызывать `shutdown`** — удалённая сторона не узнает, что вы закончили отправку, и может ждать вечно.

#### Отладка программ

Начинающие программисты часто спрашивают, как можно отлаживать сетевую программу, если под рукой нет сети. Оказывается, можно обойтись и без неё. Достаточно запустить клиента и сервера на одной машине, а затем использовать для соединения адрес _интерфейса внутренней петли_ (loopback interface). В программе ему соответствует константа INADDR_LOOPBACK (не забудьте применять к ней функцию **htonl**!). Пакеты, направляемые по этому адресу, в сеть не попадают. Вместо этого они передаются стеку протоколов TCP/IP как только что принятые. Таким образом моделируется наличие виртуальной сети, в которой вы можете отлаживать ваши сетевые приложения.

**Листинг 1. Полный пример TCP-сервера.**

```cpp
#include <arpa/inet.h>
#include <netinet/in.h>
#include <sys/socket.h>
#include <unistd.h>

#include <cstring>
#include <iostream>
#include <thread>

void handle_client(int client_fd) {
    char buf[1024];
    while (true) {
        ssize_t n = recv(client_fd, buf, sizeof(buf) - 1, 0);
        if (n < 0) { perror("recv"); break; }
        if (n == 0) { std::cout << "client disconnected\n"; break; }
        buf[n] = '\0';
        std::cout << "recv: " << buf << "\n";

        // эхо обратно
        size_t sent = 0;
        while (sent < static_cast<size_t>(n)) {
            ssize_t s = send(client_fd, buf + sent, n - sent, MSG_NOSIGNAL);
            if (s <= 0) break;
            sent += s;
        }
    }
    close(client_fd);
}

int main() {
    int server_fd = socket(AF_INET, SOCK_STREAM, 0);
    if (server_fd < 0) { perror("socket"); return 1; }

    int opt = 1;
    setsockopt(server_fd, SOL_SOCKET, SO_REUSEADDR, &opt, sizeof(opt));

    sockaddr_in addr{};
    addr.sin_family = AF_INET;
    addr.sin_port = htons(8080);
    addr.sin_addr.s_addr = INADDR_ANY;

    if (bind(server_fd, reinterpret_cast<sockaddr*>(&addr), sizeof(addr)) < 0) {
        perror("bind");
        return 1;
    }

    if (listen(server_fd, SOMAXCONN) < 0) {
        perror("listen");
        return 1;
    }

    std::cout << "listening on 8080\n";

    while (true) {
        sockaddr_in client{};
        socklen_t len = sizeof(client);
        int client_fd = accept(server_fd, reinterpret_cast<sockaddr*>(&client), &len);
        if (client_fd < 0) { perror("accept"); continue; }

        char ip[INET_ADDRSTRLEN];
        inet_ntop(AF_INET, &client.sin_addr, ip, sizeof(ip));
        std::cout << "connection from " << ip << ":" << ntohs(client.sin_port) << "\n";

        std::thread(handle_client, client_fd).detach();
    }

    close(server_fd);
}
```

**Листинг 2. Полный пример TCP-клиента.**

```cpp
#include <arpa/inet.h>
#include <netinet/in.h>
#include <sys/socket.h>
#include <unistd.h>

#include <cstring>
#include <iostream>

int main() {
    int fd = socket(AF_INET, SOCK_STREAM, 0);
    if (fd < 0) { perror("socket"); return 1; }

    sockaddr_in server{};
    server.sin_family = AF_INET;
    server.sin_port = htons(8080);
    inet_pton(AF_INET, "127.0.0.1", &server.sin_addr);

    if (connect(fd, reinterpret_cast<sockaddr*>(&server), sizeof(server)) < 0) {
        perror("connect");
        return 1;
    }

    //const char* msg = "hello, server";
    std::cout << "Enter message: "
    std::string msg;
    std::getline(std::cin, msg)
    
    if (msg == "") continue;
    
    send(fd, msg.data(), msg.size(), MSG_NOSIGNAL);

    char buf[1024];
    ssize_t n = recv(fd, buf, sizeof(buf) - 1, 0);
    if (n > 0) {
        buf[n] = '\0';
        std::cout << "echo: " << buf << "\n";
    }

    shutdown(fd, SHUT_WR);
    close(fd);
}
```

>Буфер в цикле — это нормально. `buf` создается на стеке при каждом входе в тело цикла. Это не `malloc`/`new`, не выделение в куче. Компилятор просто резервирует место в стековом кадре функции — обычно **один раз** на всю функцию, а не на каждую итерацию. С точки зрения производительности стоимость нулевая: указатель стека сдвигается на 1024 байта при вызове функции, и всё.
- **Локальность**: буфер живёт ровно там, где используется. Читающему код сразу ясно, что это временное хранилище для одного `recv`.
- **Безопасность**: между итерациями не остаётся старых данных — каждая итерация получает свежий буфер (пусть и с мусором, но вы его не читаете, потому что пишете `buf[n] = '\0'`).
- **Оптимизатор** всё равно поднимет выделение на уровень функции, если сочтёт нужным. Писать `char buf[1024]` внутри цикла — идиоматично и не медленнее.

#### `buf[n] = '\0'` — нуль-терминатор

`recv` возвращает **количество прочитанных байт**, но **не добавляет** `'\0'` в конце. Это просто сырые байты. `std::cout << buf` для `char*` ожидает **C-строку** — массив, оканчивающийся `'\0'`. Он читает байты, пока не встретит нуль.

Если нуля нет:
- `cout` продолжит читать память **за пределами** прочитанных данных;
- там может быть что угодно: остатки старых данных, мусор стека, чужие данные;
- получишь «сломанные символы» в выводе или вообще segfault.

`buf[n] = '\0'` ставит нуль сразу после последнего прочитанного байта. Для этого буфер должен иметь **минимум `n+1`** байт — вот почему в `recv` передают `sizeof(buf) - 1`, а не `sizeof(buf)`. Один байт резервируется под терминатор.

```text
buf:  [ H ][ e ][ l ][ l ][ o ][ \0 ][ мусор... ]
       0    1    2    3    4    5
       ^---- recv вернул 5 ----^  ^--- этот байт перезаписан
```

#### `sizeof(buf) - 1` — резерв под `'\0'`

```cpp
ssize_t n = recv(client_fd, buf, sizeof(buf) - 1, 0);
```

- `sizeof(buf)` = 1024.
- `sizeof(buf) - 1` = 1023 — максимум байт, которые `recv` может записать.
- После `buf[n] = '\0'` при `n = 1023` запись идёт в `buf[1023]` — последний допустимый индекс.
- Итого в буфере всегда есть место под нуль-терминатор.

Если передать `sizeof(buf)` без `-1`, то при `n = 1024` запись `buf[1024] = '\0'` — это **выход за пределы массива**, undefined behavior.

#### `sendall`: почему `buf + total` и `sz - total`

```cpp
int sendall(int fd, const char* buf, size_t sz, int flags) {
    size_t total = 0;
    while (total < sz) {
        ssize_t sent = send(fd, buf + total, sz - total, flags);
        if (sent == -1) break;
        total += sent;
    }
    return static_cast<int>(total);
}
```

Ключевая идея: `send` может отправить **меньше**, чем попросили

TCP не гарантирует, что один `send` запишет весь буфер. Ядро может отправить:
- всё сразу;
- половину;
- 1 байт;
- 0 (редко, но бывает при переполнении буфера);
- 1 при ошибке.

Это называется **partial write**. Поэтому нужен цикл.

`buf + total` — арифметика указателей. `buf` — это `const char*`, то есть **адрес первого байта** массива. `buf + total` — это адрес байта с индексом `total`.

```text
buf:  [ H ][ e ][ l ][ l ][ o ]
       ^
       buf
после total = 2:
buf + 2:  [ l ][ l ][ o ]
           ^
           buf + 2
```

Арифметика указателей в C++ работает в **элементах типа**, а не в байтах. Так как `char` — 1 байт, `buf + 2` — это ровно 2 байта вперёд. Если бы это был `int*`, то `ptr + 2` сдвинуло бы на 8 байт `(2 * sizeof(int))`.

Смысл: на каждой итерации мы отправляем **оставшуюся часть** буфера, начиная с того места, где остановились.

`sz - total` — оставшееся количество
- `sz` — сколько всего надо отправить.
- `total` — сколько уже отправили.
- `sz - total` — сколько осталось.

#### Полный пример

Допустим, `sz = 10`, буфер `"helloworld"`.

|Итерация|`total`|`buf + total`|`sz - total`|`send` вернул|Новый `total`|
|---|---|---|---|---|---|
|1|0|`"helloworld"`|10|4|4|
|2|4|`"oworld"`|6|3|7|
|3|7|`"rld"`|3|3|10|
|цикл завершён||||||

Если бы мы всегда передавали `buf` и `sz`, то на второй итерации отправили бы `"helloworld"` снова — дублирование.


>Как `std::string` хранит данные внутри памяти?

Класс `std::string` — это сложная умная обертка (контейнер) над обычным динамическим массивом символов в памяти.

Когда пользователь вводит текст (например, `"Hello from console"`) и `std::getline` записывает его в `msg`, происходит следующее:

1. Вызывается менеджер памяти C++. Он запрашивает у операционной системы Linux кусок памяти в **Куче (Heap)** — области памяти для динамических данных.
2. В куче выделяется непрерывный массив байт нужного размера.
3. В этот массив копируются символы из консоли, а в самый конец автоматически дописывается нулевой символ `\0`.
4. Сам объект `msg` на стеке хранит внутри себя всего три вещи (по 8 байт каждая): указатель на этот кусок памяти в куче, текущую длину строки и её емкость (capacity).

Что делает метод `msg.data()`?

Функция `sendall` (и системный вызов `send`) — это функции, написанные на чистом Си. Они понятия не имеют, что такое класс `std::string` из C++. Им, как мы выяснили в прошлом вопросе, нужен просто **адрес первой ячейки памяти**, откуда начинать читать байты, и размер `sz`.

Когда вы пишете:

```cpp
sendall(fd, msg.data(), msg.size(), 0);
```

Метод **`.data()`** (в C++ он полностью аналогичен методу `.c_str()`) делает очень простую вещь: он лезет внутрь объекта `std::string` и **возвращает «сырой» указатель типа `const char*`**, который физически содержит адрес начала того самого динамического массива символов, лежащего в куче.

Цепочка событий для `send()`:

1. `msg.data()` возвращает адрес памяти (например, `0x5555557a2140`).
2. Этот адрес передается в `sendall`, а оттуда в системный вызов `send`.
3. Ядро Linux берет этот адрес, легально заглядывает по нему в кучу вашего процесса, считывает указанное количество байт (`msg.size()`) и копирует их в буфер сокета.
    
В чем ключевая разница с `.rdata`?

Модификатор **`const`** в типе `const char*`, который возвращает метод `msg.data()`, здесь нужен **не для операционной системы, а для компилятора C++**.

- Когда вы использовали `"Hello"` из секции `.rdata`, память была защищена _аппаратно самой ОС_ (попытка записи вызывала `Segmentation Fault`).
- В случае с `msg.data()`, память в куче _физически открыта для записи_. Но тип `const char*` говорит компилятору: _«Пожалуйста, следи, чтобы внутри функции `sendall` никто случайно не попытался изменить этот буфер, так как мы передали его только для чтения»_. Если вы внутри `sendall` попытаетесь изменить символ через этот указатель, компилятор C++ просто откажется собирать проект ещё на этапе компиляции.

Резюме:

Для системного вызова `send` нет никакой разницы, где лежат байты — в защищенной секции `.rdata` (как константа) или в динамической куче (как введенная строка `std::string`). Главное, что метод **`.data()` превращает умный объект C++ в понятный для ядра Linux «сырой» адрес памяти**.


### Работа с несколькими клиентами ([[CPP-Sockets|многопоточность]])

Есть несколько способов:

1) `std::thread(handle_client, fd).detach()`. На каждого клиента создается свой поток, который выполняет переданную функцию. Минус — при тысячах клиентов тысячи потоков, дорого.

2) `select()` / `poll()`:

```cpp
#include <poll.h>

std::vector<pollfd> fds;
fds.push_back({server_fd, POLLIN, 0});

while (true) {
    int ready = poll(fds.data(), fds.size(), -1);
    if (ready < 0) { perror("poll"); break; }

    for (auto& p : fds) {
        if (p.revents & POLLIN) {
            if (p.fd == server_fd) {
                // accept нового
            } else {
                // recv от клиента
            }
        }
    }
}
```

3) `epoll()` — безупречный фаворит на Linux:

```cpp
#include <sys/epoll.h>

int ep = epoll_create1(0);

epoll_event ev{};
ev.events = EPOLLIN;
ev.data.fd = server_fd;
epoll_ctl(ep, EPOLL_CTL_ADD, server_fd, &ev);

constexpr int MAX_EVENTS = 64;
epoll_event events[MAX_EVENTS];

while (true) {
    int n = epoll_wait(ep, events, MAX_EVENTS, -1);
    for (int i = 0; i < n; ++i) {
        int fd = events[i].data.fd;
        if (fd == server_fd) {
            // accept
        } else {
            // recv
        }
    }
}
```

`epoll` не требует перебирать все fd при каждом вызове, как `select`/`poll`. Сложность O(готовых), а не O(всех).

#### `getaddrinfo()` — резолв имён

```cpp
#include <netdb.h>

addrinfo hints{};
hints.ai_family = AF_UNSPEC;      // IPv4 или IPv6
hints.ai_socktype = SOCK_STREAM;

addrinfo* res = nullptr;
int err = getaddrinfo("example.com", "80", &hints, &res);
if (err != 0) {
    std::cerr << gai_strerror(err);
    return 1;
}

for (addrinfo* p = res; p != nullptr; p = p->ai_next) {
    int fd = socket(p->ai_family, p->ai_socktype, p->ai_protocol);
    if (fd < 0) continue;
    if (connect(fd, p->ai_addr, p->ai_addrlen) == 0) {
        // подключились
        break;
    }
    close(fd);
}

freeaddrinfo(res);
```

Плюс: работает и с IPv4, и с IPv6, и с именами. Рекомендуется вместо устаревшего `gethostbyname`.
