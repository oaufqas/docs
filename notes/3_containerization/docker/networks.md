Сетевой стек Docker — это элегантная обёртка над встроенными технологиями ядра Linux. Docker не создаёт виртуальные сетевые карты с нуля, он комбинирует **Network Namespaces**, **виртуальные пары интерфейсов (veth)**, **Linux Bridges** и правила **iptables/nftables**.

В Linux всё изолируется через пространства имён (`namespaces`). Ядро Linux позволяет создать изолированные копии сетевого стека.

- Когда ОС загружается, в ней есть **Root Network Namespace** — это физическая сеть вашего сервера (ваша основная карта `eth0`/`ens3`, таблица маршрутизации хоста, правила firewall).
- Когда Docker запускает контейнер, он вызывает системный вызов ядра `clone()` или `unshare()` с флагом `CLONE_NEWNET`.
- В результате создаётся новое, полностью пустое **Network Namespace** для этого контейнера. Внутри него нет ничего, кроме интерфейса локальной петли `lo` (localhost). Контейнер заперт и не видит сеть хоста.

Когда вы делаете `docker run` без указания сети, запускается сеть типа `bridge`. Вот как Linux связывает изолированный контейнер с внешним миром шаг за шагом:

Шаг А: Виртуальный коммутатор (Linux Bridge)

При старте Docker-демона в Root-пространстве хоста создаётся виртуальный программный коммутатор (свитч) — интерфейс **`docker0`** (вы можете увидеть его через команду `ip link` или `brctl show`). Ему присваивается IP-адрес (обычно `172.17.0.1`). Все создаваемые позже пользовательские сети в Compose создают аналогичные интерфейсы, например `br-f8d234...`.

Шаг Б: Виртуальный кабель (veth-пары)

Чтобы связать контейнер со свитчем `docker0`, ядро Linux создаёт **veth-пару (Virtual Ethernet)**. Это аналог двустороннего патч-корда, у которого два конца.

1. Один конец кабеля Docker «запихивает» внутрь Network Namespace контейнера и переименовывает его в привычный **`eth0`**. Внутри контейнера ему выдается IP (например, `172.17.0.2`).
2. Второй конец кабеля остаётся в Root-пространстве хоста и называется как-то вроде **`veth1a2b3c4`**.
3. Этот хостовый конец `veth` жестко привязывается к свитчу `docker0` (`ip link set veth1a2b3c... master docker0`).

**Как идет пакет:** Когда приложение из контейнера шлет пакет наружу, он входит в `eth0` контейнера, моментально «вылетает» из `veth...` на хосте и попадает на свитч `docker0`.

#### Принцип работы маршрутизации и связь с хостом (И почему работает `host-gateway`)

Теперь у нас есть пакет на интерфейсе `docker0`. Как он понимает, куда идти дальше? Здесь в силу вступает **таблица маршрутизации ядра Linux** и **iptables**.

Если у вас создано две разные сети в Docker Compose (`net_A` и `net_B`), под капотом создаются два разных свитча (`br-A` и `br-B`). Контейнеры из разных сетей не могут общаться, потому что Docker прописывает в `iptables` (в цепочку `FORWARD`) железное правило: _«Если пакет идёт из интерфейса br-A в интерфейс br-B — DROP (выбросить)»_.

Как контейнер выходит в интернет (MASQUERADE / NAT)

У контейнера IP вида `172.17.0.2`. Внешний интернет про этот IP ничего не знает. Когда пакет из контейнера летит на условный `google.com`, ядро хоста подхватывает его и прогоняет через таблицу `iptables NAT` (цепочка `POSTROUTING`):

```bash
-A POSTROUTING -s 172.17.0.0/16 ! -o docker0 -j MASQUERADE
```

Ядро стирает внутренний IP контейнера (`172.17.0.2`), записывает туда реальный публичный IP вашего сервера (`eth0` хоста) и отправляет в сеть. Когда приходит ответ, хост вспоминает, кому он принадлежал, и перенаправляет обратно в контейнер.

Как работает `host-gateway` и `extra_hosts`

Когда вы указали `host.docker.internal:host-gateway`, Docker подставил туда IP `172.17.0.1` (адрес свитча `docker0`).  
Почему контейнер может достучаться до вашего eBPF-монитора на хосте по этому IP? Потому что для контейнера `172.17.0.1` — это его **Default Gateway (шлюз по умолчанию)**. Любой пакет, идущий не в локальную подсеть контейнера, отправляется на этот шлюз. Хост принимает этот пакет на интерфейсе `docker0`, видит, что порт назначения принадлежит локальному бинарнику, и передаёт его вашему C++ приложению.

#### Драйвер `host` (Полный отказ от изоляции)

Когда вы пишете `network_mode: "host"`, Docker делает финт ушами: он **НЕ создаёт** новое Network Namespace для контейнера. Контейнер запускается прямо в **Root Network Namespace** хоста.

- Контейнер видит все интерфейсы хоста (`eth0`, `lo`, `docker0`).
- Он слушает порты прямо на хосте.
- Скорость работы сети в режиме `host` максимальна (она равна скорости физического сервера), так как отсутствуют накладные расходы на veth-пары, мосты и NAT-трансляцию пакетов.

#### Драйвер `macvlan` (Контейнер как физический ПК)

Это продвинутый драйвер, который часто используют в высоконагруженных системах или enterprise-сетях.

- Под капотом Docker берёт вашу реальную физическую карту `eth0` на хосте и генерирует на ней под-интерфейсы с **уникальными виртуальными MAC-адресами** для каждого контейнера.
- Роутер в вашем офисе начинает думать, что к нему в свитч воткнули ещё 5 реальных компьютеров. Им выдаются IP-адреса из вашей офисной подсети (например, `192.168.1.155`).
- Пакеты идут в обход `iptables` хоста и свитча `docker0` напрямую в сетевой кабель.

#### Архитектура Проброса Портов (`-p 9090:9090`)

Когда вы пробрасываете порты из контейнера наружу в режиме `bridge`, Docker использует два механизма под капотом, чтобы доставить трафик снаружи в контейнер:

1. **Инструмент `docker-proxy`:** Для каждого проброшенного порта Docker запускает на хосте крошечный фоновый процесс (вы можете увидеть его в `ps aux | grep docker-proxy`). Он слушает порт на хосте (например, 9090) и тупо перенаправляет байты через сокет внутрь контейнера. Это резервный и медленный путь.
2. **DNAT в `iptables`:** Это основной и быстрый путь. Docker прописывает правило в ядро: _«Если на физический интерфейс хоста на порт 9090 пришел TCP-пакет, измени адрес назначения (Destination NAT) на 172.17.0.2:9090»_. Ядро перенаправл

#### Как `extra_hosts` работает под капотом

Когда Docker запускает контейнер, он изолирует его файловую систему и сетевой стек. Однако контейнеру всё равно нужно как-то разрешать (резолвить) доменные имена. Для этого Docker динамически создает и монтирует внутрь каждого контейнера системные файлы: `/etc/resolv.conf`, `/etc/hostname` и **/etc/hosts**.

Когда вы указываете в настройках `extra_hosts` (или в CLI через флаг `--add-host`), Docker Daemon выполняет следующие шаги:

1. **Создает контейнер:** Формирует изолированное пространство.
2. **Модифицирует `/etc/hosts`:** Перед самым стартом процесса Docker берет внутренний файл `/etc/hosts` контейнера и дописывает в самый конец ваши строки.
3. **Выполняет резолв:** Когда приложение (например, Prometheus) пытается отправить запрос на `host.docker.internal`, библиотека `glibc`/`musl` внутри контейнера сначала заглядывает в `/etc/hosts`. Она мгновенно находит там жестко прописанный IP-адрес, минуя любые DNS-серверы.

Что такое `host-gateway`? Например `host.docker.internal:host-gateway`.

- `host-gateway` — это **специальное ключевое слово**, добавленное в Docker engine (начиная с версии 20.10).
- Под капотом Docker Daemon автоматически определяет IP-адрес главного сетевого интерфейса моста (обычно это интерфейс `docker0` на хосте с IP `172.17.0.1`). Это и является ip адресом машины-хоста.
- Во время старта контейнера Docker подставляет этот реальный IP-адрес вместо слова `host-gateway`.

Если вы зайдете внутрь запущенного контейнера (`docker exec -it prometheus cat /etc/hosts`), вы увидите там строку:

```
172.17.0.1   host.docker.internal
```

В классическом CLI-интерфейсе Docker за эту функцию отвечает флаг **`--add-host`**. Вы можете передавать его сколько угодно раз при запуске контейнера.

Синтаксис флага: `--add-host=ИМЯ:IP_ИЛИ_КЛЮЧ`

Пример 1: Проброс хост-машины 

Если вам нужно запустить Prometheus в обычном Docker так, чтобы он видел экспортер на хосте по стабильному имени:

```bash
docker run -d \
  --name prometheus \
  -p 9090:9090 \
  -v ./prometheus.yml:/etc/prometheus/prometheus.yml \
  --add-host=host.docker.internal:host-gateway \
  prom/prometheus:latest
```

Пример 2: Подмена реального DNS на конкретный IP (для тестов)

Представьте, что ваше приложение внутри контейнера обращается к какому-то внешнему API по адресу `://mycompany.com`. Вы хотите протестировать его локально, направив трафик на свой тестовый сервер `192.168.1.50`, не меняя код приложения:

```bash
docker run -d --add-host=://mycompany.com.168.1.50 my-app-image
```

Внутри контейнера любой запрос к `://mycompany.com` теперь гарантированно уйдет на `192.168.1.50`.
