**Докер контейнер (Container)**: Запущенный экземпляр образа (процесс). Это изолированная среда, которая потребляет минимум ресурсов, так как использует ядро основной операционной системы.
Докер добавляет поверх неизменяемого образа "тонкий" слой для записи, что позволяет приложению работать и сохранять данные во время сессии (работы контейнера).

Запуск и установка контейнеров происходит командой `docker run [FLAGS] IMAGE [COMMAND]`, не путать с (`docker start`, который запускает уже существующий, но остановленный контейнер). 

Запускать можно образы, которые есть локально и с docker registry, если нужного образа локально нет, докер установит его с dockerhub. 


#### Основные флаги при запуске:

- `-d (Detached)`: Запускает контейнер в фоновом режиме. Вы вводите команду, и терминал остается свободным.

- `-it`: Связка двух флагов (-i и -t). Позволяет взаимодействовать с контейнером (войти внутрь консоли)

- `--name:` Позволяет задать контейнеру понятное имя (например, --name my-web-server). Если не указать, Docker придумает случайное имя вроде flamboyant_hopper

- `--rm`: Автоматически удаляет контейнер сразу после его остановки. Очень полезно для тестов, чтобы не копить «мусор».

- `-p [host_port]:[container_port]`: Проброс портов.  

- `--network [network_name]`: Подключает контейнер к определенной сети (например, чтобы база данных и сайт видели друг друга).

- `-v [host_path]:[container_path]`: Монтирует папку с вашего диска в контейнер

- `-e`(Env): Установка переменных окружения. Пример: -e MYSQL_ROOT_PASSWORD=12345.

- `-m или --memory`: Лимит оперативной памяти (например, --memory="512m").

 - `--cpus`: Сколько ядер процессора может использовать контейнер (например, --cpus="1.5").

 - `sleep infinity`: После указания образа, заменяет точку входа в контейнер, он просто засывает. Нужно например для того, чтобы скопировать что то из контейнера


### Команды для управления контейнерами:

- `docker ps` - Список запущенных контейнеров (добавьте -a, чтобы увидеть и остановленные).
- `docker stop my-app` - Мягкая остановка контейнера (сигнал SIGTERM).
- `docker start my-app` - Запуск ранее остановленного контейнера.
- `docker restart my-app` - Перезагрузка контейнера
- `docker kill my-app` - Принудительная остановка
- `docker exec -it my-app [bash]` - Выполнение команды внутри запущенного контейнера.
- `docker logs -f my-app` - Просмотр вывода (логов) приложения (-f для слежения в реальном времени).
- `docker inspect my-app` - Получение всей детальной информации (IP, конфиги, пути).
- `docker rm my-app` - Удаление остановленного контейнера (добавьте -f для принудительного удаления запущенного)
- `docker container prune` - Быстрая очистка всех контейнеров
- `docker top my-container` - Показать процессы контейнера

### Хороший паттерн сборки статических исполняемых файлов в контейнерах Alpine Linux

Почему Docker + Alpine (`-static`) работает на ВСЕХ серверах

Главный секрет успеха первого варианта — **полная статическая линковка на базе Musl libc**.

- **Флаг `-static` и явный выбор `.a` файлов:** Команда `g++` берет статические библиотеки (`libbpf.a`, `libelf.a`, `libz.a`, `libzstd.a`) и «намертво» вшивает их код внутрь итогового файла `ebpf-monitor`.
- **Musl libc вместо GLIBC:** Alpine Linux использует легковесную стандартную библиотеку C — `musl`. В отличие от тяжелой `glibc` (которая используется в Ubuntu/Debian/CentOS и очень плохо поддается статической сборке), `musl` изначально проектировалась для идеальной статической линковки.
- **Итог:** Полученный бинарник **вообще не имеет внешних зависимостей** (`ldd ebpf-monitor` покажет `not a dynamic executable`). Ему не важен дистрибутив хоста, версия его библиотек или установленный пакетный менеджер. Нужен только процессор той же архитектуры (x86_64) и ядро Linux, поддерживающее eBPF.

Если сравнивать например с CMake на Ubu/Deb, то второй вариант страдает от классической проблемы «динамической зависимости».

- **Динамическая линковка (Dynamic Linking):** Строка `target_link_libraries(ebpf-monitor PRIVATE bpf elf)` заставляет CMake искать файлы `libbpf.so` и `libelf.so` в локальной системе. На хост-машине они будут связаны динамически. При переносе бинарника на другой сервер, где версии `libbpf.so` отличаются (или их вообще нет), программа упадет с ошибкой `error while loading shared libraries`.
- **Привязка к GLIBC:** По умолчанию на Ubuntu CMake соберет бинарник, завязанный на конкретную версию `glibc` вашего хоста (например, `GLIBC_2.35`). Стоит перенести этот бинарник на чуть более старый сервер (например, с `GLIBC_2.31`), и он выдаст ошибку `version GLIBC_... not found`.

Плюсы паттерна (Преимущества):

- **Воспроизводимость сборки (Idempotency):** Не важно, собираете вы код на MacBook с Apple Silicon (через эмуляцию), на старом сервере или в CI/CD-пайплайне. Результат (бинарник) всегда будет абсолютно одинаковым, потому что окружение зафиксировано в образе Alpine.
- **Идеальная безопасность и размер (Multi-stage):** Финальный образ не тащит с собой тяжелые компиляторы (`clang`, `g++`, `make`), которые весят под 600 МБ и могут содержать уязвимости. Финальный слой содержит чистый Alpine и ваш бинарник весом в несколько мегабайт.
- **Автономность приложения:** Конечный файл можно просто скопировать через `docker cp` и запускать как обычную службу `systemd` прямо на хосте — контейнер на проде держать не обязательно.


```dockerfile
FROM alpine:3.18 AS builder

RUN apk update && apk add --no-cache clang15 g++ make bpftool libbpf-dev libelf-static elfutils-dev zlib-dev zlib-static zstd-static linux-headers musl-dev
  
WORKDIR /src

COPY . .

RUN \
    clang-15 -g -O2 -target bpf -D__TARGET_ARCH_x86 -I. -c src/monitor.bpf.c -o monitor.bpf.o && \
    \
    bpftool gen skeleton monitor.bpf.o > monitor.skel.h && \
    \
    g++ -std=c++20 src/main.cpp src/app_context.cpp src/prometheus-exporter.cpp -I. \
        -static \
        -l:libbpf.a -l:libelf.a -l:libz.a -l:libzstd.a \
        -o ebpf-monitor

FROM alpine:3.18
WORKDIR /app

COPY --from=builder /src/ebpf-monitor .

CMD ["sleep", "infinity"]
```

[[eBPF#Создание статического (переносимого) исполняемого файла|Объяснение с точки зрения компиляции eBPF кода]]

>Этап 1: Builder (Строки 1–19)

```dockerfile
FROM alpine:3.18 AS builder
```

1) **Изолированная мастерская:** Docker создает временный контейнер на базе дистрибутива Alpine Linux 3.18 и дает ему имя `builder`.
2) **Тяжелые инструменты:** Команда `RUN apk add ...` скачивает компиляторы (`g++`, `clang`), утилиты сборки (`make`, `bpftool`) и статические версии библиотек (`zlib-static`, `libelf-static`, `zstd-static`). Этот слой весит **около 600 МБ**.
3) **Сборка:** Docker копирует ваши исходники (`COPY . .`) и выполняет компиляцию бинарника.

>Этап 2: Финальный образ (Строки 21–26)

```dockerfile
FROM alpine:3.18
```

1) **Стирание памяти:** Docker берет абсолютно чистый образ Alpine 3.18. Все установленные на первом этапе компиляторы, исходные `.cpp` и `.c` файлы, кэш пакетного менеджера — **все это выбрасывается**.
2) **Точечный перенос:**

```dockerfile
COPY --from=builder /src/ebpf-monitor .
```

Docker заглядывает внутрь файловой системы контейнера `builder`, забирает **только один файл** (`ebpf-monitor`) и вставляет его в новый чистый контейнер.

- **Итог:** Итоговый Docker-образ весит всего **около 15–20 МБ** (7 МБ сам чистый Alpine + вес вашего бинарника). В нем нет лишнего софта, что делает его максимально безопасным (злоумышленник не сможет запустить `make` или `clang` внутри контейнера, если взломает его).

```bash
# 1. Создаем контейнер без запуска (он просто существует на диске)
docker create --name extract-container my-ebpf-app
# Либо
docker run -d --name my_container my-ebpf-app sleep infinity

# 2. Копируем файл
docker cp extract-container:/app/ebpf-monitor ./ebpf-monitor

# 3. Удаляем контейнер
docker rm extract-container
```
