В cpp нет привычных для высокоуровневых языков языков `export` и `import`. Есть заголовочный файл `.h`/`.hpp` и файл реализации `.cpp`.

Компилятор C++ работает очень прямолинейно: он компилирует каждый файл `.cpp` **строго по отдельности и в один поток**. Он ничего не знает о существовании других `.cpp` файлов, пока компилирует текущий.

- **`.h` (заголовочный файл) — это чертеж или технический паспорт.** В нем написано: _«В нашем проекте существует вот такое здание (структура) с такими-то комнатами (переменными)»_. Сам по себе чертеж кирпичи в физическом мире не создает.
- **`.cpp` (файл реализации) — это сама стройка.** Здесь выделяется реальная память на жестком диске/в ОЗУ и пишется тяжелый исполняемый код функций.

Если файлу `main.cpp` нужно использовать переменную или функцию из `metrics.cpp`, мы не можем заставить его заглянуть в `metrics.cpp`. Но мы можем дать ему чертеж — `metrics.h`. Посмотрев на чертеж, компилятор скажет: _«Ага, я понял, как выглядит эта структура, я подготовлю под нее место»_. Позже линкер склеит эти файлы вместе.

Почему объявление переменных в `.h`, а не в `.cpp`?

В `.h` файле мы пишем **объявление (Declaration)** — то есть описываем _форму_ данных. Мы говорим: «Любой файл, который подключит этот чертеж, будет знать, что внутри `AppContext` есть переменная `PORT`».  
Если бы мы объявили структуру внутри конкретного `.cpp`, то другие `.cpp` файлы физически не смогли бы узнать, какие переменные в ней есть.


Файл `metrics.h` (Объявление / Интерфейс). _Здесь мы только рассказываем компилятору, какие функции и переменные существуют._

```cpp
#pragma once // Защита: файл не применится дважды, если его заинклюдят в разных местах
#include <atomic>
#include <string>

// Описываем структуру данных
struct AppMetrics {
    std::atomic<uint64_t> total_requests{0};
    void increment();
};

// Объявляем функцию, которую смогут вызывать другие файлы
std::string serialize_to_prometheus(AppMetrics& metrics);

```


Файл `metrics.cpp` (Реализация). _Здесь пишется сама логика. Этот файл обязательно должен «знать» свой заголовочный файл._

```cpp
#include "metrics.h" // Подключаем локальный заголовочник через двойные кавычки

void AppMetrics::increment() {
    total_requests.fetch_add(1, std::memory_order_relaxed);
}

std::string serialize_to_prometheus(AppMetrics& metrics) {
    uint64_t reqs = metrics.total_requests.load(std::memory_order_relaxed);
    return "# TYPE http_requests_total counter\n"
           "http_requests_total " + std::to_string(reqs) + "\n";
}
```

Файл `main.cpp` (Главная точка входа). _Использует логику из модуля метрик._

```cpp
#include <iostream>
#include "metrics.h" // Теперь main знает, что такое AppMetrics и serialize_to_prometheus

int main() {
    AppMetrics my_metrics;
    my_metrics.increment();
    
    std::string response = serialize_to_prometheus(my_metrics);
    std::cout << response;
    
    return 0;
}
```


Как компилятор понимает связь файлов `.h` и `.cpp`, по названию? **Нет, компилятор вообще не смотрит на названия файлов.** Вы можете назвать заголовочный файл `apple.h`, а его реализацию — `banana.cpp`. Программа всё равно скомпилируется.

Связь между ними строится исключительно на двух вещах:

1. **Директива `#include`:** Когда вы пишете `#include "my_file.h"` в каком-то `.cpp`, препроцессор (первый этап компиляции) буквально берет весь текст из `.h` файла и физически копирует его в этот `.cpp` вместо строчки инклюда.
2. **Имена функций и классов:** Когда компилятор обрабатывает файлы, он ориентируется по **сигнатуре (имени и параметрам)**.
    - В `.h` написано: `void do_something();` (компилятор запомнил: такая функция где-то есть).
    - В `.cpp` написано: `void do_something() { /* код */ }` (компилятор создал этот код).
    - Позже программа-линкер берет все откомпилированные файлы, видит, что один файл просил функцию `do_something()`, а второй её предоставил, и просто соединяет их по имени.

Для переноса каких-либо данных с одного файла в другой, нужно объявить (инициализация происходит в `.cpp` файле) данные в `.h`, то что не было объявлено - не перенесется, останется в том файле, где и инициализировано.

- Если вы внутри структуры (как в `AppContext`) укажете `int x = 5;`, это нормально. Это не создание переменной, это просто правило для компилятора: _«когда кто-то создаст этот объект, заполни это поле пятеркой»_.
- Но если вы напишете обычную глобальную переменную типа `int global_var = 10;` прямо в `.h` файле (вне структуры/класса), программа **не скомпилируется**, как только этот `.h` файл будет подключен больше чем в один `.cpp`. Линкер скажет, что переменная создана дважды. Глобальные переменные объявляют в `.h` через `extern int global_var;`, а инициализируют в `.cpp`: `int global_var = 10;`.
- Если вы просто напишете `int secret_number = 42;` внутри `metrics.cpp`, файл `main.cpp` никогда о ней не узнает. Для `main.cpp` этой переменной физически не существует, потому что у него нет «чертежа» (`.h` файла), описывающего её. И это отлично — так файлы изолируются друг от друга!


#### Для чего нужен `static` вне структур и классов

Когда ключевое слово `static` пишется на самом верхнем уровне файла (вне любых функций и классов), оно имеет **совершенно другое значение**, чем внутри функций или структур. В этом контексте `static` означает **внутреннее связывание (Internal Linkage)**.  
Проще говоря: оно делает переменную **«невидимой» для всех остальных файлов `.cpp`**.

>Пример без `static`:

Если вы напишете в файле `metrics.cpp` на самом верху:

```cpp
int global_counter = 0; // Обычная глобальная переменная
```

А затем в файле `main.cpp` на самом верху напишете то же самое:

```cpp
int global_counter = 0; 
```

При сборке программы линкер (склеиватель файлов) выдаст ошибку: **`duplicate symbol / multiple definition`**. Он увидит две глобальные переменные с одинаковым именем во всем проекте и не поймет, какую использовать.

>Пример со `static`:

Если вы добавите `static`:

```cpp
static int global_counter = 0; // Локальная глобальная переменная!
```

Вы можете написать эту строчку и в `main.cpp`, и в `metrics.cpp`. Ошибки не будет. Компилятор создаст **две абсолютно разные переменные** в памяти, которые просто случайно называются одинаково. За пределами своего `.cpp` файла эту переменную никто не увидит.

>Что будет, если написать `static` к функции и передать её в `.h`?

Если вы напишете `static void my_func();` на уровне файла и засунете её в `.h`, то **использовать её в `main.cpp` нормально не получится**, возникнет путаница. `static` для функции/переменной вне классов означает _«сделать этот элемент строго локальным для текущего файла»_.  
Если вы засунете `static void my_func();` в `.h` файл, а потом подключите его в `main.cpp` и `metrics.cpp`, то произойдет следующее:

1. Компилятор создаст локальную копию `my_func` для `main.cpp`.
2. Компилятор создаст **другую** локальную копию `my_func` для `metrics.cpp`.

Они не будут связаны между собой. Если `metrics.cpp` должен предоставить функцию для `main.cpp`, она обязана быть **не-static**.


---

Если в подключаемом файле нужны данные из главного, делать `.h` файл для `main.cpp` **категорически не нужно**. Файл `main.cpp` — это высшая точка входа в программу, его самого никто никогда не должен инклюдить.

Если файлу `metrics.cpp` нужны какие-то данные из `main.cpp`, создание круговых импортов (`main` инклюдит `metrics`, а `metrics` инклюдит `main`) — это классическая архитектурная ловушка (circular dependency), которая приводит к ошибкам компиляции.

>Вариант 1. Передача данных через параметры функций (Самый чистый путь)

Если `main.cpp` считает какие-то данные (например, количество обработанных байт или ID текущего пользователя) и их нужно записать в метрики, он просто **вызывает метод** из `metrics.h` и передает эти данные аргументом.

_Структура проекта остается прежней:_ **`main.cpp`**, **`metrics.h`**, **`metrics.cpp`** _(всего 2 cpp и 1 h)_.

Изменения в `metrics.h`:

```cpp
#pragma once
#include <atomic>

struct AppMetrics {
    std::atomic<uint64_t> processed_bytes{0};

    // Объявляем метод, принимающий данные извне
    void add_bytes(uint64_t bytes);
};
```

Изменения в `metrics.cpp`:

```cpp
#include "metrics.h"

void AppMetrics::add_bytes(uint64_t bytes) {
    // Безопасно прибавляем данные, пришедшие из main.cpp
    processed_bytes.fetch_add(bytes, std::memory_order_relaxed);
}
```

Изменения в `main.cpp`:

```cpp
#include "metrics.h"

int main() {
    AppMetrics metrics;

    // Какая-то логика в main...
    uint64_t network_data_chunk = 1024; 

    // Передаем данные из main внутрь метрик
    metrics.add_bytes(network_data_chunk); 
    
    return 0;
}
```


>Вариант 2. Что делать, если в `main` есть функция, которую `metrics` должен вызвать?

Если вам действительно нужно вызвать из файла `metrics.cpp` какую-то общую функцию (например, функцию логирования или конфигурации, которая написана в `main.cpp`), то эту функцию **нельзя оставлять в `main.cpp`**.

Её нужно вынести в **третий независимый модуль** (например, `utils.h` и `utils.cpp`). Тогда структура станет: _3 cpp файла и 2 h_.

- И `main.cpp`, и `metrics.cpp` будут делать `#include "utils.h"`.
- Никакой циклической зависимости не возникнет: стрелки импортов будут идти сверху вниз, а не по кругу.

И в этом файле лучше всего создать структуру данных. Можно было бы просто создать 10 обычных глобальных переменных в воздухе. Но структура решает две критические проблемы:

1. **Группировка (Инкапсуляция):** Она собирает разрозненные данные в один понятный контейнер. В коде сразу видно: `ctx.PORT` — это не просто какая-то случайная переменная, это часть настроек нашего приложения (`AppContext`).
2. **Контроль доступа:** Если переменные лежат просто в воздухе, любой программист в любой части кода может случайно создать переменную с таким же именем или перезаписать её. Структура защищает от этого.


#### Файл `app_context.h` (Объявление центрального хранилища)

```cpp
#pragma once // Защита. Если этот чертеж случайно заинклюдят 5 раз в разных файлах,
             // компилятор применит его только 1 раз, чтобы не было ошибок дублирования.

#include <string>       // Подключаем стандартный чертеж для работы со строками
#include <atomic>       // Подключаем чертеж для атомарных типов данных
#include <netinet/in.h> // Системный чертеж Linux, где живут типы вроде in_addr_t и константа INADDR_ANY

struct AppContext { // Создаем контейнер-структуру
    volatile bool keep_running = true; // Флаг работы циклов (запрещен к кэшированию)
    const int PORT = 4444;             // Константа порта (не меняется, атомик не нужен)
    const in_addr_t ADDR = INADDR_ANY; // Константа адреса (0.0.0.0 — слушать все интерфейсы)

    // 5 атомарных счетчиков для метрик Prometheus. 
    // Благодаря std::atomic разные файлы и потоки могут безопасно делать им ++ одновременно.
    std::atomic<uint64_t> metrics_exec_total{0};
    std::atomic<uint64_t> metrics_open_total{0};
    std::atomic<uint64_t> metrics_sudo_actions{0};
    std::atomic<uint64_t> metrics_root_actions{0};
    std::atomic<uint64_t> sensitive_files_opened{0};

    // Объявление единственной "двери" доступа к хранилищу
    static AppContext& get();

private:
    // Прячем конструктор, чтобы никто во всей программе не смог написать `AppContext x;`
    AppContext() = default; 
};

```

Что делает `static AppContext& get()` и зачем блокировать конструктор?

Это классический паттерн **Singleton (Одиночка)**. Его задача — сделать так, чтобы в вашей программе физически существовал **только один экземпляр** этого хранилища.

Представь, что `AppContext` — это паспортный стол. Паспортный стол в городе должен быть один, иначе начнется путаница с документами. Если каждый поток или файл создаст себе по копии `AppContext`, у каждого будут свои собственные счетчики метрик, и общая картина сломается.

Зачем блокировать конструктор (`private: AppContext() = default;`)?

По умолчанию в C++ любой программист может написать в коде:

```cpp
AppContext my_context; // Создали еще одно хранилище в памяти
```

Перемещая конструктор `AppContext()` в секцию `private`, мы буквально бьем по рукам любого, кто попытается создать копию структуры. Компилятор выдаст ошибку.

Зачем тогда нужен `static AppContext& get()`?

Поскольку создавать структуру напрямую запрещено, мы делаем **единственную официальную дверь** для доступа к ней — статическую функцию `get()`.  
Слово `static` означает, что эту функцию можно вызвать, даже если у нас еще нет готового объекта структуры. Мы пишем `AppContext::get()` из любой точки программы и гарантированно получаем доступ к нашему единственному хранилищу.


>`volitate` Это очень важный флаг для компилятора, защищающий код от «слишком умной» оптимизации.

Современные компиляторы пытаются ускорить код. Если компилятор видит цикл:

```cpp
while (keep_running) {
    // какой-то код, который НЕ меняет переменную keep_running
}
```

Он думает: _«Раз внутри цикла переменная `keep_running` не меняется. Зачем мне каждый раз ходить в медленную оперативную память и проверять её значение? Скопирую её один раз в быстрый регистр процессора и буду крутить цикл бесконечно»_.

Но в многопоточном приложении это приводит к катастрофе. Если главный поток (main) изменит `keep_running = false` в оперативной памяти, сетевой поток этого не увидит, потому что он крутит цикл, глядя в свой внутренний регистр процессора. Поток зависнет навсегда.

Слово `volatile` переводится как «летучий/нестабильный». Оно жестко приказывает компилятору: _«Каждый раз, когда этот цикл проверяет переменную, ты обязан физически идти в оперативную память и читать её заново. Не смей её оптимизировать или кэшировать!»_.


#### Файл `app_context.cpp` (Реализация)

Благодаря механизму _Meyers Singleton_ (начиная с C++11), статическая локальная переменная инициализируется абсолютно потокобезопасно при первом вызове.

```cpp
#include "app_context.h"

AppContext& AppContext::get() {
    static AppContext instance;
    return instance;
}
```

1. Когда ваша программа **в самый первый раз** (например, в `main.cpp`) вызывает `AppContext::get()`, управление заходит в эту функцию.
2. Ключевое слово `static` перед `AppContext instance;` дает команду операционной системе: _«Выдели память под этот объект один раз и заблокируй её. Эта переменная не должна уничтожаться, когда функция завершится»_.
3. Происходит создание объекта `instance`. С этого момента он вечно живет в памяти программы.
4. Функция возвращает ссылку (`&`) на этот объект.
5. Когда программа вызывает `AppContext::get()` **во второй, третий или тысячный раз** (например, из потока Prometheus), строка `static AppContext instance;` просто **игнорируется**. Компилятор видит, что объект уже создан, и сразу переходит к строке `return instance;`, отдавая ссылку на тот же самый объект.

#### Использование в `main.cpp`

```cpp
#include <iostream>
#include "app_context.h"

int main() {
    // Получаем ссылку на наш контекст
    auto& ctx = AppContext::get();

    std::cout << "Starting server on " << ctx.server_ip << ":" << ctx.server_port << std::endl;

    // Главный цикл использует флаг из контекста
    while (ctx.keep_running.load(std::memory_order_relaxed)) {
        
        // Имитируем бизнес-логику: пришел запрос, инкрементируем атомик в контексте
        ctx.http_requests_total.fetch_add(1, std::memory_order_relaxed);
        
        if (/* произошла ошибка */ false) {
            ctx.http_errors_total.fetch_add(1, std::memory_order_relaxed);
        }
    }
    return 0;
}
```

### Сборка исполняемых файлов

>Сборка через CMake (Современный стандарт)

В CMake вам достаточно просто перечислить **все** созданные `.cpp` файлы внутри команды `add_executable`. Файлы `.h` указывать не обязательно (компилятор сам найдет их по директивам `#include`), но их часто добавляют туда для красоты отображения в IDE (например, в CLion/VS Code).

Файл `CMakeLists.txt`

```cmake
cmake_minimum_required(VERSION 3.15)
project(PrometheusApp CXX)

# Устанавливаем стандарт C++
set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

# Перечисляем ВСЕ cpp файлы, которые участвуют в сборке приложения
add_executable(my_program 
    main.cpp 
    metrics.cpp
)
```

**Команды для сборки через CMake:**

```bash
mkdir build && cd build
cmake ..
cmake --build .
# На выходе получаем бинарник: ./my_program
```


>Сборка напрямую через `g++` (Консольные команды)

Если вы компилируете проект в один шаг без CMake, вам нужно передать компилятору `g++` **все `.cpp` файлы** через пробел. Компилятор скомпилирует каждый из них отдельно в объектный код, а затем линкер (linker) соберет их в один исполняемый файл.

Команда сборки:

```bash
g++ -std=c++17 main.cpp metrics.cpp -o my_program
```

Как это работает под капотом (Пошагово):

Если файлов станет слишком много, компилировать их каждый раз долго. Правильный путь для `g++` — сначала скомпилировать каждый файл в объектный файл (`.o`), а потом объединить их:

```bash
# 1. Компилируем metrics.cpp в объектный код metrics.o (флаг -c означает "только компиляция")
g++ -std=c++17 -c metrics.cpp

# 2. Компилируем main.cpp в объектный код main.o
g++ -std=c++17 -c main.cpp

# 3. Линкуем (склеиваем) объектные файлы в один готовый бинарник
g++ main.o metrics.o -o my_program
```

Золотые правила разделения кода на файлы:

1. **Кавычки vs Угловые скобки:**
    - `#include "metrics.h"` — в двойных кавычках подключаются ваши **локальные** файлы проекта (компилятор ищет их в текущей папке).
    - `#include <iostream>` — в угловых скобках подключаются файлы **системных или внешних библиотек** (компилятор ищет их в системных путях вроде `/usr/include`).
2. **Никогда не инклюдьте `.cpp` файлы:** Строчка `#include "metrics.cpp"` — грубейшая ошибка. Это приведет к дублированию кода и ошибкам линковки (`duplicate symbol`). Инклюдить можно только `.h`/`.hpp` файлы.
