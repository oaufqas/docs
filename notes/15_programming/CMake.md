**CMake** — это **генератор систем сборки**. Он читает специальные файлы-инструкции (обычно `CMakeLists.txt`), в которых описано, из каких исходных файлов и библиотек нужно собрать проект, и на основе этих инструкций создает стандартные файлы для сборки, принцип работы:
1. Вы пишете `CMakeLists.txt`.
2. Запускаете `cmake ..(расположение директории с файлом CMakeLists.txt)` в папке сборки, и CMake генерирует файлы сборки, можно сказать первично инициализирует директорию.
3. Запускаете `make` (или другой инструмент), который непосредственно компилирует код, уже после инициализации, сборка будет проходить одной командой.

CMake устроен как **мета-генератор**. Он сам не компилирует код. Вместо этого он исследует вашу операционную систему, собирает информацию обо всех компиляторах, путях и флагах, а затем на основе `CMakeLists.txt` генерирует «родной» для Linux скрипт сборки — **`Makefile`**.

#### Способы build проекта:

1) In-source Builds - при таком способе организации, у нас в директории с исходниками появляются бинарники, способ устарел и не рекомендуется к использованию.
2) Out-Of-Source Builds - исходники в одной директории, допустим `src/`, бинарники в `build/`, подход чистый, вторую директорию можно спокойно удалять, она сгенерируется при build по новой. Сгенерированная директория обычно не отслеживается гитом.

Если вы зайдете в папку `build`, вы увидите папки `CMakeFiles`, файл `CMakeCache.txt`, `cmake_install.cmake` и `Makefile`. Они решают три важнейшие задачи:

- **Кэширование (Скорость):** CMake опрашивает систему (проверяет, где лежит `g++`, где `clang`, поддерживают ли они стандарт C++20, установлена ли библиотека `libbpf`). Это долгий процесс (занимает пару секунд). Чтобы не делать этого при каждом вызове команды `make`, CMake записывает все ответы в файл **`CMakeCache.txt`**. При повторной сборке он мгновенно считывает данные оттуда.
- **Изоляция окружения (Чистота проекта):** Именно поэтому мы всегда создаем отдельную папку `mkdir build && cd build`. Весь этот сборочный «мусор» создается внутри нее. Ваш исходный код в папке `src/` остается идеально чистым. Если сборка сломалась или вы хотите начать с нуля, достаточно просто удалить папку `build` (`rm -rf build`), и проект вернется в исходное состояние.
- **Отслеживание изменений:** Папка `CMakeFiles` хранит точные временные метки (timestamps) каждого вашего файла. Благодаря этому `make` точно знает: если вы изменили `main.cpp`, нужно перекомпилировать _только_ его, а eBPF-код ядра трогать не нужно. Это экономит колоссальное количество времени на больших проектах.


#### Что хранят в себе переменные из CMakeLists.txt

Встроенные (системные) переменные CMake:

- **`${CMAKE_CURRENT_SOURCE_DIR}`** — хранит **абсолютный путь** к папке, где лежит текущий `CMakeLists.txt`. (Например: `/home/user/projects/ebpf-monitor`). Нужен, чтобы компилятор всегда точно знал, где искать `vmlinux.h` и исходники, независимо от того, из какой папки вы запустили сборку.
- **`${CMAKE_CURRENT_BINARY_DIR}`** — хранит **абсолютный путь** к папке, где происходит сборка. (Например: `/home/user/projects/ebpf-monitor/build`). Именно туда CMake приказывает складывать временные файлы `monitor.bpf.o` и `monitor.skel.h`, чтобы они не путались под руками в папке с кодом.

Кастомные переменные (которые можно создавать через `set`):

- **`${CLANG_EXT}`** и **`${BPFTOOL_EXT}`** — после того как отработала функция `find_program`, в эти переменные записываются **полные пути к исполняемым файлам в вашей ОС Linux**. Обычно это `/usr/bin/clang` и `/usr/sbin/bpftool` (или `/usr/bin/bpftool`). CMake подставляет эти пути вместо абстрактных имен, гарантируя, что вызовется именно та утилита, которая установлена в системе.
- **`${BPF_SRC}`**, **`${BPF_OBJ}`**, **`${BPF_SKEL}`** — это просто текстовые строки-макросы, в которых склеены пути к файлам. Мы создали их исключительно для удобства, чтобы не писать в коде кастомных команд длинные конструкции вроде `${CMAKE_CURRENT_BINARY_DIR}/monitor.skel.h` по несколько раз.



Компиляция **никогда не начинается в процессе чтения (конфигурации) файла `CMakeLists.txt`**.

Процесс сборки проекта всегда жестко разделен на два совершенно независимых этапа:

Этап 1. Конфигурация (Чтение сверху вниз)

Когда вы запускаете команду `cmake ..`, программа CMake просто читает ваш файл `CMakeLists.txt` как текстовый документ от первой до последней строчки.

- В этот момент **компиляторы (g++, clang) вообще не запускаются**.
- CMake на этом этапе работает как архитектор: он просто рисует в памяти чертеж (граф зависимостей).
- Если вы написали `add_executable` на 5-й строчке, а `target_link_libraries` и `add_dependencies` на 105-й строчке — для CMake это абсолютно нормально. Он дочитает файл до конца, увидит все свойства, привязанные к этой цели, и зафиксирует их на чертеже.
- В самом конце этого этапа CMake генерирует файлы сборки (например, `Makefile`) в вашей папке `build`. На этом работа утилиты `cmake` закончена.

Этап 2. Сборка (Компиляция)

Компиляция начинается только тогда, когда вы вводите в терминале команду:

```bash
make  # или cmake --build .
```

Утилита `make` открывает сгенерированный на Этапе 1 файл `Makefile`, видит там **готовый, полностью сформированный чертеж** проекта и начинает запускать компиляторы в том порядке, который продиктован зависимостями.

#### Разбор синтаксиса `CMakeLists.txt`

Этот файл управляет сборкой всего проекта. Давайте разберем его ключевые блоки:


```cmake
cmake_minimum_required(VERSION 3.20)
project(ebpf-monitor C CXX)
```

- Указываем минимальную версию CMake и объявляем имя проекта. Флаги `C CXX` говорят, что в проекте будут использоваться одновременно два языка: Си (для ядра) и C++ (для агента).


```cmake
find_program(CLANG_EXT executable NAMES clang REQUIRED)
find_program(BPFTOOL_EXT executable NAMES bpftool REQUIRED)
```

- Ищем в операционной системе Linux пути к установленным утилитам `clang` и `bpftool`. Если CMake их не найдет, он остановит конфигурацию и выдаст ошибку.


```cmake
add_custom_command(
    OUTPUT ${BPF_OBJ}
    COMMAND ${CLANG_EXT} -g -O2 -target bpf -D__TARGET_ARCH_x86 -c ${BPF_SRC} -o ${BPF_OBJ}
    DEPENDS ${BPF_SRC} ${CMAKE_CURRENT_SOURCE_DIR}/vmlinux.h
)
```

- **Самая важная часть для eBPF.** CMake по умолчанию не знает, как собирать код для ядра. Этим блоком мы создаем **кастомное правило сборки**.
- Мы говорим: «Чтобы получить файл `${BPF_OBJ}` (`monitor.bpf.o`), нужно запустить компилятор `clang` с флагом `-target bpf` (компилировать под виртуальную машину ядра). Процесс зависит от файлов `monitor.bpf.c` и `vmlinux.h`. Если они изменятся — перекомпилируй».


```cmake
add_custom_command(
    OUTPUT ${BPF_SKEL}
    COMMAND ${BPFTOOL_EXT} gen skeleton ${BPF_OBJ} > ${BPF_SKEL}
    DEPENDS ${BPF_OBJ}
)
```

- Второе кастомное правило. Оно берет получившийся объектный файл ядра и с помощью утилиты `bpftool` генерирует **"скелет"** (`monitor.skel.h`). Это обычный C-заголовок, внутри которого наш eBPF-байткод зашит в виде огромного массива байт. Благодаря этому наш C++ агент сможет загрузить его в ядро одной строчкой кода.

```cmake
add_executable(ebpf-monitor src/main.cpp)
add_dependencies(ebpf-monitor bpf_target)
```

- Создаем финальный исполняемый файл `ebpf-monitor` из кода `main.cpp`. Команда `add_dependencies` жестко указывает: _«Не смей компилировать main.cpp, пока робот CMake не выполнит кастомные команды выше и не сгенерирует для нас скелет `monitor.skel.h`»_.

```cmake
target_link_libraries(ebpf-monitor PRIVATE bpf elf)
```

- Приказываем линкеру привязать к нашему C++ агенту две системные бинарные библиотеки: `libbpf` (чтобы общаться с eBPF) и `libelf` (чтобы уметь парсить структуры скомпилированных файлов ядра).

Эта автоматизация заменяет ручной ввод команд:

```bash
clang -g -O2 -target bpf -D__TARGET_ARCH_x86 -I. -c src/monitor.bpf.c -o monitor.bpf.o

bpftool gen skeleton monitor.bpf.o > src/monitor.skel.h

g++ -std=c++20 src/main.cpp -lbpf -lelf -o ebpf-monitor

```

Заменяя их на ввод одной команды `make`.

### Основные команды CMake

Переменные и Поиск

>`set()` — создание и изменение переменных. Используется для создания локальных переменных (строк, путей, списков) или изменения системных флагов.

- **Синтаксис:** `set(<имя_переменной> <значение1> [<значение2> ...])`

```cmake
set(CMAKE_CXX_STANDARD 20)                 # Системная переменная: включить C++20
set(BPF_SRC ${CMAKE_CURRENT_SOURCE_DIR}/src/monitor.bpf.c) # Путь к файлу
set(MY_SOURCES main.cpp utils.cpp)          # Список файлов (разделитель — пробел)
```

- _Как читать:_ Чтобы получить значение переменной позже, её имя оборачивают в конструкцию `${...}`, например `${BPF_SRC}`.

>`find_program()` — поиск исполняемых файлов в ОС. Ищет утилиты (компиляторы, генераторы) в системных папках (из переменной окружения `PATH`) вашей операционной системы.

- **Синтаксис:** `find_program(<переменная_результата> NAMES <имя1> [<имя2> ...] [REQUIRED])`
- **Аргументы:**
	- `NAMES`: список возможных имен программы.
	- `REQUIRED`: если программа не найдена, CMake сразу остановит конфигурацию с ошибкой.

- **Пример:** `find_program(CLANG_EXT NAMES clang REQUIRED)` — найдет, где в Linux лежит `clang` (например, `/usr/bin/clang`) и запишет этот абсолютный путь в переменную `${CLANG_EXT}`.


>`add_executable()` — создание исполняемого файла. Определяет бинарную цель (программу), которую нужно скомпилировать из исходных файлов.

- **Синтаксис:** `add_executable(<имя_цели> [исходный_файл1 ...])`

- **Пример:** `add_executable(ebpf-monitor src/main.cpp)` — создаст цель сборки с именем `ebpf-monitor`. На выходе компилятора (`g++` или `clang++`) получится исполняемый файл `ebpf-monitor`.

>`add_dependencies()` — ручное управление порядком сборки

Связывает две цели жестким правилом: «цель А нельзя начинать собирать, пока полностью не собрана цель Б».

- **Синтаксис:** `add_dependencies(<цель_А> <цель_Б>)`

- **Пример:** `add_dependencies(ebpf-monitor bpf_target)` — запрещает компилировать `main.cpp`, пока не отработает кастомная цель `bpf_target`, генерирующая файл `monitor.skel.h`. Если этого не сделать, C++ компилятор ругнется на отсутствие инклуда.

**Команда `add_dependencies` умеет работать ТОЛЬКО с логическими целями (Targets), но не умеет работать напрямую с файлами.**

>`target_link_libraries()` — линковка (привязка) библиотек

Указывает компоновщику (линкеру), какие внешние библиотеки нужно привязать к вашему исполняемому файлу или другой библиотеке.

- **Синтаксис:** `target_link_libraries<имя_цели> <PRIVATE|PUBLIC|INTERFACE> <библиотека1> ...)`
- **Ключевые слова области видимости:**
	- `PRIVATE`: Библиотека нужна только этой цели. Те, кто будут использовать вашу цель в будущем, эту библиотеку не унаследуют (для исполняемых файлов `.exe` всегда выбирают `PRIVATE`).
	- `PUBLIC`: Библиотека нужна и вашей цели, и тем проектам, которые будут подключать вашу цель к себе.

- **Пример:** `target_link_libraries(ebpf-monitor PRIVATE bpf elf)` — при сборке подставит флаги `-lbpf -lelf`.

>`target_include_directories()` — добавление путей для поиска инклудов (`#include`)

Говорит компилятору, в каких дополнительных папках искать заголовочные файлы (`.h`, `.hpp`). Это аналог флага компилятора `-I`.

- **Синтаксис:** `target_include_directories(<имя_цели> <PRIVATE|PUBLIC> <путь1> ...)`

- **Пример:** `target_include_directories(ebpf-monitor PRIVATE ${CMAKE_CURRENT_BINARY_DIR})` — приказывает компилятору заглядывать в папку сборки (`build`), чтобы C++ код мог найти автоматически сгенерированный скелет `monitor.skel.h`.


Поскольку CMake изначально «из коробки» умеет компилировать только стандартные C/C++/Fortran файлы под ваш процессор, для сборки eBPF (где нужен Clang с флагом `-target bpf`) мы используем кастомные механизмы.

>`add_custom_command()` — генерация файла по правилу (Низкий уровень)

Эта команда описывает рецепт: **как из файла Х получить файл Y** с помощью вызова сторонней утилиты. Сама по себе она не запустится, пока её результат кто-то не потребует.

- **Синтаксис:**

```cmake
add_custom_command(
OUTPUT <целевой_файл>
COMMAND <команда_и_аргументы>
DEPENDS <файлы_от_которых_зависит_сборка>
COMMENT "Текст сообщения для вывода в консоль при сборке"
)
```

- **Пример:**

```cmake
add_custom_command(
OUTPUT ${BPF_OBJ}
COMMAND ${CLANG_EXT} -g -O2 -target bpf -c ${BPF_SRC} -o ${BPF_OBJ}
DEPENDS ${BPF_SRC}
COMMENT "Компиляция кода ядра в eBPF байт-код..."
)
```

>`add_custom_target()` — создание абстрактной цели (Высокий уровень)

Создает «абстрактную» цель (просто команду для `make`), которая не создает исполняемый файл сама по себе, но группирует кастомные команды, чтобы их можно было встроить в цепочку зависимостей проекта через `add_dependencies`.

- **Синтаксис:** `add_custom_target(<имя_цели> [ALL] DEPENDS <файлы_которые_нужно_создать>)`
- **Аргументы:**
- `ALL`: Означает, что эта цель будет выполняться всегда при вызове обычной команды `make` (по умолчанию).
- **Пример:** `add_custom_target(bpf_target DEPENDS ${BPF_SKEL})` — создает цель `bpf_target`. Когда CMake запускает её, он видит, что она зависит от файла `${BPF_SKEL}`. Он идет искать `add_custom_command(OUTPUT ${BPF_SKEL} ...)` и запускает генерацию скелета.


- **`cmake_minimum_required(VERSION 3.20)`** — проверяет версию CMake у пользователя. Если у разработчика стоит старая версия (например, 3.10), CMake выдаст ошибку и не позволит сломать сборку.
- **`project(<имя_проекта> [LANGUAGES C CXX])`** — инициализирует проект, задает его имя и включает поддержку компиляторов для указанных языков (`C` и `CXX` (C++)).
- **`message([STATUS|WARNING|FATAL_ERROR] "Текст")`** — аналог `print` для CMake. Используется для отладки скрипта сборки. `FATAL_ERROR` мгновенно прерывает конфигурацию.
- **`add_library(<имя> [STATIC|SHARED] исходники...)`** — вместо исполняемого файла собирает статическую (`.a` / `.lib`) или динамическую (`.so` / `.dll`) библиотеку из вашего кода, которую потом можно подключить к другим проектам.
