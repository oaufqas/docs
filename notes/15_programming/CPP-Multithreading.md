## Что такое поток на уровне ОС

**Поток (thread)** — это независимая последовательность выполнения инструкций внутри процесса. У потока есть:
- **Свой стек** (обычно 1–8 МБ) для локальных переменных, адресов возврата, аргументов.
- **Свой набор регистров**: `RIP`, `RSP`, `RBP`, `RAX`–`R15`, `RFLAGS`.
- **Свой TLS** (thread-local storage) — переменные, уникальные для каждого потока.
- **Свой идентификатор** (`tid` в ядре, `pthread_t` в user space).
- **Своё состояние**: running, ready, blocked, sleeping.

**Общее с другими потоками того же процесса:**
- адресное пространство (код, куча, глобальные данные, открытые файлы);
- таблица файловых дескрипторов;
- обработчики сигналов;
- текущий рабочий каталог;
- `uid`/`gid` (на Linux — да, на некоторых системах есть per-thread credentials).

В ядре Linux поток — это **задача (task)**. Процесс и поток отличаются только тем, какие ресурсы они делят с другими задачами. В Linux системный вызов `clone()` создаёт и то, и другое — разница в передаваемых флагах:
- `CLONE_VM` — общая память (общее адресное пространство).
- `CLONE_FILES` — общая таблица fd.
- `CLONE_THREAD` — считать это потоком того же процесса.
- `CLONE_FS` — общий рабочий каталог.
- `CLONE_SIGHAND` — общие обработчики сигналов.

`fork()` = `clone(SIGCHLD)` без `CLONE_VM` — новый процесс с копией памяти.  
`pthread_create()` = `clone(CLONE_VM | CLONE_FILES | CLONE_FS | CLONE_THREAD | ...)` — новый поток в том же процессе.

На уровне ядра Linux (в исходном коде `kernel/fork.c`) **не существует** двух разных механизмов для создания процессов и потоков. И `fork()`, и `vfork()`, и библиотека потоков `pthread_create()` (которую использует `std::thread`) под капотом вызывают одну и ту же универсальную ядерную функцию — **`kernel_clone()`**.

Флаг `CLONE_VM` (Virtual Memory) — это главный переключатель между потоком и процессом:

- **Если флаг включен (`clone` с `CLONE_VM`):** Новый поток будет делить с родителем **ту же самую память** (одну таблицу страниц MMU). Они видят переменные друг друга.
- **Если флаг выключен:** Ядро Linux создает для нового процесса **абсолютно новое, изолированное адресное пространство**. Память родителя копируется для ребенка (с помощью механизма оптимизации _Copy-On-Write_). Они становятся изолированными государствами.

Флаг `SIGCHLD`

В Linux родителю важно знать, когда его ребенок умер, чтобы очистить ресурсы и не плодить процессы-зомби.

- Передавая сигнал **`SIGCHLD`** в системный вызов `clone`, мы приказываем ядру Linux: _«Когда этот новый процесс завершит работу и вызовет `exit()`, автоматически отправь мне (родителю) стандартный сигнал `SIGCHLD`»_.
- Именно этот сигнал будит функцию `wait(NULL)` или `waitpid()`, сообщая, что ребенок отработал.

---

>**Для создания задач используются два разных системных вызова:**

`fork()` — Создание процесса
Когда вызывается `fork()`, ядро Linux делает **дубликат** текущей задачи.
- **Изоляция:** Создается _новая_ таблица страниц памяти (MMU), копия дескрипторов файлов, копия сетевых сокетов. Память нового процесса полностью изолирована от старого.
- **Взаимозаменяемость:** `fork()` и `clone()` **НЕ взаимозаменяемы**. `fork()` физически не может создать поток внутри текущего процесса — он всегда порождает нового независимого «ребенка» со своим собственным адресным пространством.

`clone()` — Создание потока
Когда вы пишете в C++ `std::thread t(func);`, библиотека `libstdc++` вызывает функцию `pthread_create`, которая внутри себя делает системный вызов **`clone()` с огромным количеством флагов**.
Основные флаги `clone()` при создании потока:
- `CLONE_VM`: Новый поток использует **ту же самую виртуальную память**, что и родитель. Они делят общую Кучу (Heap) и глобальные переменные.
- `CLONE_FILES`: Новый поток делит с родителем **таблицу файловых дескрипторов**. Если один поток открыл сокет, второй может сразу из него читать.
- `CLONE_SIGHAND`: Общая таблица обработчиков сигналов (Ctrl+C).

Как распределяется память потока?

Так как память (`CLONE_VM`) общая, где тогда поток хранит свои локальные переменные?  
При вызове `clone()` библиотека `pthread` выделяет внутри кучи процесса фиксированный кусок памяти (по умолчанию в Linux это **8 Мегабайт**) и отдает его новому потоку в качестве его **персонального Стека (Thread Stack)**. Туда складывается регистр `RIP` (указатель команд потока) и его локальные переменные.

#### `std::thread`

`std::thread` — это **тонкая обёртка над POSIX-потоками** (`pthread_create`, `pthread_join`) на Linux/macOS, и над Windows API (`CreateThread`) на Windows.

```cpp
std::thread t(func, arg1, arg2);
```

Конструктор `std::thread` принимает **вызываемый объект (Callable)** и необязательный список аргументов для него. Это может быть:
- Обычная функция.
- Лямбда-выражение.
- Указатель на метод класса (вместе с указателем на объект класса).
- Функтор (объект класса с перегруженным оператором `()`).
Аргументы передаются по значению. Если нужно передать аргумент по ссылке, его обязательно оборачивают в макрос `std::ref()` (иначе компилятор выдаст ошибку).

Внутри себя объект `std::thread` на стеке вашего C++ процесса занимает очень мало места (обычно **8 или 16 байт**). Он хранит:
- **Идентификатор потока (`std::thread::id`)** — уникальный номер, по которому C++ отличает один поток от другого.
- **Системный дескриптор потока (`pthread_t`)** — числовой ID, который используется для вызова низкоуровневых функций ядра Linux.

Если вам нужно получить результат вычислений из потока, у вас есть три пути:
1. Передать в поток указатель/ссылку на переменную, куда дочерний поток запишет результат перед смертью (требует синхронизации).
2. Использовать глобальные атомарные переменные (как мы делали с метриками).
3. Использовать механизм **`std::async`** и **`std::future`**

Под капотом:

1. **Аллокация ресурсов.** libstdc++/libc++ создаёт внутреннюю структуру состояния (shared_ptr на state, где лежат: указатель на функцию, скопированные аргументы, флаг `joinable`, идентификатор потока, результат).
2. **Копирование/перемещение аргументов.** Аргументы **копируются** в эту структуру, если переданы lvalue. Можно передавать rvalue и `std::move`, чтобы избежать копий.
3. **Создание стека.** `pthread_create` просит ядро выделить стек для нового потока. Размер по умолчанию — 8 МБ на Linux (можно менять через `pthread_attr_setstacksize`).
4. **clone().** Ядро создаёт новую задачу. Новый поток начинает выполнение не с `func` напрямую, а с внутренней обёртки `thread_proxy`, которая:
    - сохраняет указатель на state в TLS или регистре;
    - вызывает `func(args...)`;
    - ловит исключения;
    - сохраняет результат в state;
    - помечает поток как завершённый;
    - вызывает `pthread_exit`.
5. **Возврат управления.** Родительский поток получает `std::thread t` — объект, содержащий идентификатор и handle.

#### Что делает `join()` и `detach()`

Когда вы запускаете поток, в системе рождается параллельная задача. Вы обязаны явно сказать C++ компилятору, как ваш главный поток должен поступить с дочерним перед тем, как объект `std::thread` выйдет из зоны видимости (destructor). Если этого не сделать, программа мгновенно упадет в Runtime с вызовом `std::terminate()`.

```cpp
t.join();
```

Блокирует вызывающий поток (обычно `main`) на этой строчке до тех пор, пока дочерний поток (`t`) физически не завершит выполнение своей функции и не умрет. Вызывается системная функция `pthread_join`. Ядро Linux убирает родительский поток из очереди планировщика задач процессора. Как только дочерний поток выполняет последнюю инструкцию и вызывает системный вызов `exit`, ядро Linux очищает его стек, будит родительский поток, и тот продолжает идти дальше по коду. Если `join` не вызывать при разрушении `std::thread` программа терминируется через `std::terminate()`. Это защита от утчеки потоков.

Нужно, когда главному потоку процесса (`main`), для продолжения работы критически важен результат или завершение работы дочернего.


```cpp
t.detach();
```

Разрывает связь между объектом `std::thread` на стеке и реальным потоком в ядре Linux. Дочерний поток становится «самостоятельным». Он продолжает работать в фоне, а главный поток идет дальше, вообще не заботясь о его судьбе. Вызывается `pthread_detach`. Ядро Linux помечает этот поток специальным флагом. Теперь, когда этот поток умрет, ядро самостоятельно сотрет его из памяти, не сообщая родителю. Ресурсы освобождаются автоматически при завершении. **Опасно**: если поток обращается к объектам, которые уничтожатся раньше его завершения, — UB (Undefined Behavior).

- Если главный поток `main()` завершится раньше, чем отсоединенный поток успеет дописать свои данные, операционная система **принудительно убьет всю программу целиком вместе со всеми отсоединенными потоками**. Из-за этого отсоединенный поток может оставить файлы недописанными или сокеты некорректно закрытыми.


#### Другие методы у `std::thread`

Их очень мало, так как класс спроектирован лаконичным:

- **`joinable()`** — возвращает `true` или `false`. Позволяет проверить, можно ли применить к потоку `join()` или `detach()`. (Если поток уже отсоединен или зажойнен, повторный вызов приведет к краху программы, поэтому проверка `if (t.joinable()) t.join();` — это стандарт безопасности).
- **`get_id()`** — возвращает уникальный ID потока в рамках C++.
- **`native_handle()`** —  возвращает «сырой» дескриптор `pthread_t` ядра Linux. С его помощью вы можете обойти ограничения C++ и применить к потоку чистые низкоуровневые функции Linux. Например, с помощью `pthread_setaffinity_np` вы можете жестко привязать ваш C++ поток к конкретному физическому ядру процессора (CPU Affinity), чтобы повысить производительность.

### Другие способы многопоточности


Создание потоков через `std::thread` — не единственный способ делать несколько дел одновременно. В зависимости от задач инженеры используют альтернативные подходы:

#### POSIX threads (`pthreads`)

То, во что превращается `std::thread`. Низкоуровневый C API:

```cpp
#include <pthread.h>

void* worker(void* arg) {
    int* n = static_cast<int*>(arg);
    // ...
    return nullptr;
}

pthread_t tid;
int x = 42;
pthread_create(&tid, nullptr, worker, &x);
pthread_join(tid, nullptr);
```

Плюсы: полный контроль (атрибуты, scheduling policy, affinity, размер стека).  
Минусы: ручное управление, unsafe API, нет RAII. `std::thread` в libstdc++/libc++ — это обёртка над pthreads. Ты получаешь переносимость и RAII бесплатно.

#### Высокоуровневые задачи: `std::async` и `std::future`

Если вам нужно просто запустить функцию в фоне и **получить из неё результат**, `std::thread` неудобен. Лучше использовать `std::async`:

```cpp
#include <future>
// Запускает функцию параллельно и возвращает "обещание" результата
std::future<int> result = std::async(std::launch::async, calculate_something);

// Код главного потока идет дальше...

// Когда результат действительно понадобился — вызываем .get(). 
// Если поток еще не досчитал, main подождет его на этой строчке.
int final_value = result.get(); 
```

- `std::launch::async` — запустить в новом потоке.
- `std::launch::deferred` — отложить до `get()` (ленивое вычисление в вызывающем потоке).
- Без указания политики — реализация сама решает.

Плюсы: не надо думать о join, результат и исключения передаются автоматически.  
Минусы: нет контроля над пулом потоков, каждый `async` может создать новый поток. Для многих задач — дорого.


#### Пул потоков (`Thread Pool`)

Создание потока через `clone()` — это относительно дорогая для ОС операция (нужно выделить 8 МБ под стек, настроить дескрипторы). Если у вас на веб-сервер прилетает 10 000 коротких запросов в секунду, создавать под каждый запрос `std::thread` нельзя — сервер захлебнется.
- **Решение:** При старте программы создается фиксированное количество потоков (например, 4 потока по числу ядер CPU). Они спят. Когда прилетает задача, она падает в очередь, свободный поток просыпается, выполняет её и снова ложится спать. Память на `clone()` тратится всего один раз при старте.

В стандарте C++ **нет** `std::thread_pool`. Используют:
- **`std::execution`** (C++17): параллельные алгоритмы, но не пул в явном виде.
- **Своя реализация** на `std::thread` + `std::queue` + `std::condition_variable`.
- **Сторонние**: Intel TBB, Boost.Asio, `libuv` (для асинхронного I/O), `folly`, `Taskflow`.

```cpp
class ThreadPool {
    std::vector<std::thread> workers_;
    std::queue<std::function<void()>> tasks_;
    std::mutex mtx_;
    std::condition_variable cv_;
    bool stop_ = false;

public:
    explicit ThreadPool(size_t n) {
        for (size_t i = 0; i < n; ++i) {
            workers_.emplace_back([this] {
                while (true) {
                    std::function<void()> task;
                    {
                        std::unique_lock lk(mtx_);
                        cv_.wait(lk, [this] { return stop_ || !tasks_.empty(); });
                        if (stop_ && tasks_.empty()) return;
                        task = std::move(tasks_.front());
                        tasks_.pop();
                    }
                    task();
                }
            });
        }
    }

    void enqueue(std::function<void()> task) {
        {
            std::lock_guard lk(mtx_);
            tasks_.push(std::move(task));
        }
        cv_.notify_one();
    }

    ~ThreadPool() {
        {
            std::lock_guard lk(mtx_);
            stop_ = true;
        }
        cv_.notify_all();
        for (auto& w : workers_) w.join();
    }
};
```


### Синхронизация

Когда потоки начинают работать в одном адресном пространстве (делят общую память через `CLONE_VM`), возникает хаос. Если два потока одновременно попытаются изменить одну и ту же переменную или файл, данные будут безвозвратно испорчены.

Для наведения порядка используется **синхронизация потоков** — набор инструментов и абстракций, которые заставляют потоки «договариваться» об очередности доступа к ресурсам.

Состояние гонки (Race Condition) и Критическая секция. Прежде чем синхронизировать, нужно понять, _что_ мы защищаем:
- **Критическая секция** — это участок кода, в котором происходит обращение к общему ресурсу (переменной, массиву, сокету, файлу).
- **Состояние гонки (Race Condition)** — ситуация, когда результат работы программы зависит от того, какой из потоков быстрее добежал до критической секции и выполнил инструкции процессора

#### `std::mutex` — Базовая блокировка.

Внутри — `pthread_mutex_t`, поверх — futex в ядре.

Это самый популярный инструмент. Он как **единственный ключ от переменной**. Тот поток, который взял ключ, запирает ее. Остальные потоки выстраиваются в очередь и «засыпают», пока ключ не вернется на место.

- **Как работает под капотом Linux:** Вызов `std::mutex::lock()` обращается к системной библиотеке `pthread_mutex_lock`. На глубоком уровне ядро Linux использует механизм **futex (fast userspace mutex)**. Поток сначала пытается захватить мьютекс в User Space с помощью быстрой атомарной инструкции. Если мьютекс уже занят, ядро Linux усыпляет поток (убирает его из планировщика CPU), чтобы он не тратил такты процессора на бесконечное ожидание.

```cpp
#include <mutex>
#include <thread>

std::mutex mtx;
int counter = 0;

void increase_counter() {
    // lock() захватывает замок. Если он занят, поток ждет здесь.
    mtx.lock(); 
    // КРИТИЧЕСКАЯ СЕКЦИЯ (безопасно меняем общую переменную)
    counter++; 
    // Освобождаем замок для других потоков
    mtx.unlock(); 
}

```

- `lock()` — блокируется, пока мьютекс занят.
- `try_lock()` — не блокируется, возвращает `false`, если занят.
- `unlock()` — освобождает.

**Никогда** не вызывай `lock`/`unlock` вручную, так как это опасно — используй RAII (`lock_guard`, `unique_lock`, `scoped_lock`).

```cpp
// Замок закроется тут, а откроется сам при выходе из функции 
void safe_increase() { std::lock_guard<std::mutex> lock(mtx); 
	counter++; 
}
```


#### Условные переменные (`std::condition_variable`)

Мьютекс защищает данные, но он не умеет передавать сигналы. Представьте, что Поток А ждет, пока Поток Б положит новые данные в очередь. Если A будет в бесконечном цикле проверять `if (queue.empty())`, он сожрет 100% CPU.

- **Решение:** Условная переменная позволяет потоку-приемщику **заснуть и полностью освободить CPU**, пока поток-производитель не «пихнет» его специальным сигналом `notify_one()` или `notify_all()`.


```cpp
#include <mutex>
#include <condition_variable>

std::mutex mtx;
std::condition_variable cv;
bool ready = false; // Условие

void worker_thread() {
    std::unique_lock<std::mutex> lock(mtx);
    
    // Поток засыпает на этой строчке, отдавая замок mtx другим.
    // Он проснется только когда ready станет true И прилетит сигнал notify
    cv.wait(lock, []{ return ready; });
    
    // Работаем с данными...
}

void publisher_thread() {
    {
        std::lock_guard<std::mutex> lock(mtx);
        ready = true; // Меняем условие
    }
    cv.notify_one(); // Будим один спящий поток!
}
```

#### `std::atomic<T>` — атомарные операции без блокировок

Если вам нужно просто увеличивать счетчик или менять флаг `true/false`, мьютекс слишком тяжел (смена контекста, усыпление потока ядром).

- **Как работает под капотом:** `std::atomic` вообще не использует системные вызовы ядра. Он дает компилятору Clang/GCC команду вставить специальные ассемблерные инструкции процессора с префиксом **`LOCK`** (например, `lock xadd` на x86). Процессор на уровне транзисторов блокирует шину памяти для этой ячейки на один такт. Это работает в десятки раз быстрее мьютексов.

```cpp
std::atomic<int> counter{0};
counter.fetch_add(1, std::memory_order_relaxed);
counter.store(42, std::memory_order_release);
int x = counter.load(std::memory_order_acquire);
```

- `memory_order_relaxed` — атомарность без упорядочивания. Быстро, но без гарантий порядка.
- `memory_order_acquire` — при загрузке: все записи до соответствующего `release` видны после этой загрузки.
- `memory_order_release` — при записи: все предыдущие записи видны потоку, который сделал `acquire`.
- `memory_order_acq_rel` — и то, и другое.
- `memory_order_seq_cst` — по умолчанию, самый строгий, самый медленный.


#### Низкоуровневые инструменты Linux (POSIX)

Если вы выйдете за рамки стандартного C++ и начнете писать чистый системный код для Linux, вы встретите еще два инструмента:

- **Семафоры (`sem_t` из `<semaphore.h>`)**: Отличаются от мьютекса тем, что это **счетчик**. Мьютекс может держать только 1 поток (ключ один). Семафор может быть настроен, например, на число `5`. Это значит, что в критическую секцию могут одновременно зайти 5 потоков (например, ограничение на 5 одновременных скачиваний файлов), а 6-й поток начнет ждать.
- **Блокировки чтения-записи (`pthread_rwlock_t`)**: Идеально для баз данных и кэша. Часто бывает так, что 100 потоков хотят просто _читать_ данные одновременно (это безопасно), и только 1 поток хочет данные _записать_. Обычный мьютекс заставил бы читающие потоки ждать друг друга. `RW-Lock` разрешает одновременное чтение бесконечному числу потоков, но полностью блокирует всех, как только приходит поток-писатель.


 Главный кошмар синхронизации: Взаимная блокировка (Deadlock)

Взаимная блокировка происходит, когда Поток 1 удерживает Замок А и пытается захватить Замок Б, а Поток 2 в эту же наносекунду удерживает Замок Б и пытается захватить Замок А. Они замирают вечно, ожидая друг друга.

**Как бороться:**

1. **Строгий порядок захвата:** Потоки всегда и везде должны захватывать замки в абсолютно одинаковом порядке (сначала А, потом Б, и никак иначе).
2. Использовать современный C++ метод **`std::lock(mtx1, mtx2)`**, который умеет безопасно захватывать несколько мьютексов за раз, избегая дедлоков на уровне алгоритма библиотеки.

## Системный вызов `epoll()`

**`epoll` (Event Poll)** — это масштабируемый механизм уведомления о событиях ввода-вывода в ядре Linux . Это главный инструмент для решения **проблемы C10K**.

Позволяет избежать проблемы 10000 соединений = 10000 потоков. И второй, уже более продвинутой, это перебора всех 10000 fd (как делает `poll()`) и проверки, готов ли каждый.
10000 системных вызовов в секунду при 10000 соединений идут впустую, потому что у 9999 из них, нет данных.

`epoll()` решает 2 эти проблемы, он позволяет ядру самому отслеживать готовность fd и сообщать только о тех, которые реально готовы к операциям `I/O`. Сложность `O(1)`, а не `O(N)` на все.

```
       ПРОСТРАНСТВО ЯДРА LINUX (Kernel Space)
       ┌────────────────────────────────────────────────┐
       │ Экземпляр epoll (управляется через epoll_fd)   │
       │                                                │
       │  1. КРАСНО-ЧЕРНОЕ ДЕРЕВО (RB-Tree)             │
       │     (Хранит ВСЕ сокеты, за которыми следим)    │
       │        [fd:4] ─── [fd:5] ─── [fd:9]            │
       │                                                │
       │  2. СПИСОК ГОТОВЫХ СОБЫТИЙ (Ready List)        │
       │     (Очередь сокетов, где РЕАЛЬНО что-то       │
       │      произошло. Наполняется аппаратно)         │
       │        [fd:5 (EPOLLIN)] ─── [fd:9 (EPOLLOUT)]  │
       └───────────────────────┬────────────────────────┘
                               │ epoll_wait()
                               ▼
       ПРОСТРАНСТВО ПОЛЬЗОВАТЕЛЯ (User Space / C++)
       [ Массив struct epoll_event events[100] ]
       (Сюда ядро за 1 такт копирует ТОЛЬКО готовые сокеты)
```

1. **Красно-черное дерево (Red-Black Tree):**  
    В нем хранятся все файловые дескрипторы (сокеты), которые вы попросили отслеживать. Дерево идеально подходит для этого: добавление сокета, его удаление или изменение флагов происходят за фантастически быстрое время — \(O(\log N)\). Вы добавляете сокет в это дерево всего **один раз** при подключении клиента.
2. **Список готовых событий (Ready List / Очередь):**  
    Это обычный двусвязный список. В него попадают _только те сокеты, на которых прямо сейчас произошло событие_ (прилетели байты, освободился буфер).  
    **Как он наполняется:** Когда в сетевую карту прилетает TCP-пакет, срабатывает аппаратное прерывание ядра Linux. Ядро обрабатывает пакет, видит, к какому сокету он относится, и если этот сокет зарегистрирован в `epoll`, ядро **мгновенно и автоматически добавляет этот сокет в Ready List**. Никакого перебора со стороны вашей C++ программы нет — всё делает само железо и прерывания ядра.

#### Историческая эволюция такова: `select()` -> `poll()` -> `epoll()`.

### `select()`:

```c
fd_set readfds;
FD_ZERO(&readfds);
FD_SET(fd1, &readfds);
FD_SET(fd2, &readfds);

struct timeval tv = {5, 0};
int n = select(max_fd + 1, &readfds, NULL, NULL, &tv);
if (n > 0) {
    if (FD_ISSET(fd1, &readfds)) { /* готов */ }
    if (FD_ISSET(fd2, &readfds)) { /* готов */ }
}
```

Проблемы:
- **`FD_SETSIZE` = 1024.** Больше — не влезет без хаков.
- **Каждый вызов копирует `fd_set` в ядро** и обратно. При 1000 fd это 2 копии по 128 байт на каждый вызов.
- **`O(N)`**: ядро проверяет все fd. Пользователь тоже.
- **`max_fd + 1`** — надо помнить максимальный номер.

### `poll()`

```c
struct pollfd fds[2];
fds[0].fd = fd1; fds[0].events = POLLIN;
fds[1].fd = fd2; fds[1].events = POLLIN;

int n = poll(fds, 2, 5000);  // таймаут 5 сек
for (int i = 0; i < 2; ++i) {
    if (fds[i].revents & POLLIN) { /* готов */ }
}
```

Лучше: нет лимита 1024, структура понятнее. Но всё ещё **`O(N)`** и копирование массива туда-обратно.

### `epoll()`

Разделяет регистрацию и ожидание:
1. Ты **один раз** регистрируешь интересующие fd в ядре.
2. Ядро само отслеживает их состояние.
3. Ты вызываешь `epoll_wait` и получаешь **только готовые** fd.

Ядро хранит список fd в **red-black tree** (для быстрого поиска при регистрации/удалении) и **ready list** (для быстрой выдачи готовых). Никакого перебора всех fd при ожидании.

Вся работа с `epoll` строится строго на трех функциях из заголовочного файла `<sys/epoll.h>`.

#### `epoll_create1()` 

Всё вращается вокруг одного файлового дескриптора — **epoll instance**, который создаётся `epoll_create1`.

```c
int epfd = epoll_create1(0);
// или
int epfd = epoll_create1(EPOLL_CLOEXEC);  // закрыть при exec
```

- **Что принимает:** Флаги (обычно передают `0` или `EPOLL_CLOEXEC` для безопасности при `fork`).
- **Что возвращает:** `int epoll_fd` (дескриптор самого epoll) или `-1` при ошибке. Этот fd ссылается на структуру в ядре, где хранится список отслеживаемых дескрипторов и очередь готовых.

Старый `epoll_create(size)` принимал размер — подсказку для хэш-таблицы. Игнорируется с ядра 2.6.8, оставлен для совместимости. Сейчас используется только `epoll_create1`.


#### `epoll_ctl()`

Регистрирует, изменяет или удаляет fd в epoll instance.

```c
int epoll_ctl(int epfd, int op, int fd, struct epoll_event *event);
```

**Что принимает:**
    1. `int epfd` — дескриптор вашего epoll.
    2. `int op` — операция: `EPOLL_CTL_ADD` (добавить сокет в дерево), `EPOLL_CTL_MOD` (изменить флаги слежения), `EPOLL_CTL_DEL` (удалить сокет из дерева, например при дисконнекте).
    3. `int fd` — целевой сокет клиента, которым управляем.
    4. `struct epoll_event *event` — структура, описывающая, какие события ловить (`EPOLLIN`, `EPOLLOUT`) и какие пользовательские данные привязать к этому сокету.
**Что возвращает:** `0` при успехе, `-1` при ошибке.

Операции:
- **`EPOLL_CTL_ADD`** — добавить fd.
- **`EPOLL_CTL_MOD`** — изменить маску событий.
- **`EPOLL_CTL_DEL`** — удалить fd. `event` может быть NULL.


```c
struct epoll_event {
    uint32_t     events;    // маска событий (EPOLLIN, EPOLLOUT, ...)
    epoll_data_t data;      // 8 байт для пользователя
};

typedef union epoll_data {
    void    *ptr;
    int      fd;
    uint32_t u32;
    uint64_t u64;
} epoll_data_t;
```

Cобытия представляют собой битовые маски (флаги). Они описывают, какое именно сетевое или системное событие произошло с файловым дескриптором (сокетом, пайпом и т. д.), за которым вы следите.

Все эти флаги упаковываются в поле `.events` структуры `struct epoll_event` при вызове `epoll_ctl()` (регистрация) и возвращаются ядром в вызове `epoll_wait()` (опрос).

- **`EPOLLIN`** — **Данные доступны для чтения**.
    - _Для обычного сокета:_ В сетевой буфер ядра прилетели новые байты от клиента. Вызов `read()` или `recv()` гарантированно не заблокирует поток и вернет данные.
    - _Для серверного (listening) сокета:_ Прилетел новый клиент (TCP SYN). Вызов `accept()` готов выдать `client_fd`.
    - _Для пайпа (pipe):_ Писатель на другом конце записал данные.
- **`EPOLLOUT`** — **Буфер отправки свободен для записи**.
    - Ядро Linux сообщает вашему приложению: _«Системный буфер отправки этого сокета освободился, сетевая карта успела отправить прошлые пакеты. Ты можешь снова вызывать `send()` или `write()` без риска заблокировать поток»_.

События ошибок и закрытия

Эти три флага уникальны тем, что **ядро возвращает их всегда**, даже если вы специально не просили следить за ними при вызове `epoll_ctl`.

- **`EPOLLRDHUP`** (начиная с Linux 2.6.17) — **Полузакрытое соединение (Stream socket peer closed connection)**.
    - Этот флаг сигнализирует, что удаленный клиент вызвал `close()` или `shutdown(SHUT_WR)`. То есть клиент больше ничего не пришлет по сети.
    - _Зачем нужен:_ Позволяет C++ коду мгновенно узнать, что клиент отключился, еще _до_ того, как вы вызовете `recv()`.
- **`EPOLLHUP`** — **Обрыв связи (Hang up)**.
    - Происходит, когда дескриптор больше не соединен с удаленной стороной. Например, если на другом конце пайпа уничтожили процесс-писатель, или сетевое TCP-соединение было принудительно разорвано (прилетел пакет `RST`). Читать или писать в такой сокет больше нельзя.
- **`EPOLLERR`** — **Критическая ошибка (Error condition)**.
    - На сокете произошла аппаратная или системная ошибка (например, сетевой провод физически выдернули, или сработал таймаут TCP ретрансмиссии).

Специальные и продвинутые события

- **`EPOLLPRI`** — **Приоритетные (Out-of-Band) данные**.
    - Используется крайне редко. Означает, что по TCP прилетели экстренные данные с высоким приоритетом (флаг `URG` в TCP-пакете).
- **`EPOLLET` (Edge-Triggered режим)** — **Переключатель поведения epoll**.
    - По умолчанию `epoll` работает в режиме **Level-Triggered (LT)**: ядро будет будить вас на `epoll_wait` бесконечно, пока в буфере сокета лежит хоть один байт.
    - Если добавить флаг `EPOLLET`, `epoll` переходит в **Edge-Triggered (ET)** режим: ядро дернет вас **ровно один раз** в момент прилета данных. Если вы вызовете `recv()`, прочитаете только половину и уснете, `epoll_wait` больше никогда вас не разбудит для этого пакета. Этот режим требует использования строго неблокирующих сокетов (`O_NONBLOCK`) и вычитывания буфера в цикле до тех пор, пока `recv` не вернет ошибку `EAGAIN`. Это самый высокопроизводительный режим.
- **`EPOLLONESHOT`** — **Одноразовое срабатывание**.
    - После того как событие сработало и `epoll_wait` вернул его, этот сокет автоматически отключается от мониторинга. Ядро больше не будет следить за ним, пока вы вручную не перерегистрируете его через `epoll_ctl` с флагом `EPOLL_CTL_MOD`.
    - _Зачем нужен:_ В многопоточных серверах (Thread Pool), чтобы гарантировать, что пока один поток обрабатывает прилетевшие 100 байт от Клиента А, никакой другой поток параллельно не проснулся по этому же Клиенту А, если тот дослал еще байты. Защищает от Race Condition.
- **`EPOLLEXCLUSIVE`** (начиная с Linux 4.5) — **Защита от проблемы "грохочущего стада" (Thundering Herd)**.
    - Если у вас 10 потоков одновременно спят на одном `epoll`-дескрипторе (или слушают один порт), то при подключении _одного_ клиента исторически ядро будило _все 10 потоков_ сразу. 9 из них понимали, что клиента уже забрали, и засыпали обратно, зря тратя ресурсы CPU. Этот флаг заставляет ядро будить только один конкретный поток.

Поле `data` — **твоё**. Ядро его не трогает, оно просто возвращает тебе то, что ты положил. Обычно кладут `fd` или указатель на свою структуру.

#### Пример регистрации:

```c
struct epoll_event ev;
ev.events = EPOLLIN;
ev.data.fd = client_fd;
if (epoll_ctl(epfd, EPOLL_CTL_ADD, client_fd, &ev) < 0) {
    perror("epoll_ctl");
}
```

При регистрации сокета вы склеиваете флаги обычной побитовой операцией **ИЛИ (`|`)**:

```cpp
struct epoll_event ev{};
// Хотим читать данные (EPOLLIN), знать о дисконнекте (EPOLLRDHUP) 
// и использовать реактивный режим Edge-Triggered (EPOLLET)
ev.events = EPOLLIN | EPOLLRDHUP | EPOLLET; 
ev.data.fd = client_fd;

// Регистрируем в системе
epoll_ctl(epoll_fd, BPF_MAP_TYPE_RINGBUF, client_fd, &ev);
```

Удалить:

```c
epoll_ctl(epfd, EPOLL_CTL_DEL, client_fd, NULL);
```

### `epoll_wait()`

Этот вызов заставляет ваш C++ поток заснуть, пока в Ready List ядра не появится хотя бы одно событие. Возвращает количество готовых событий или -1 при ошибке. Может вернуть 0 при таймауте.

```c
int epoll_wait(int epfd, struct epoll_event *events, int maxevents, int timeout);
```

**Что принимает:**
    1. `int epfd` — дескриптор epoll.
    2. `struct epoll_event *events` — **указатель на обычный массив в коде**. Ядро скопирует туда готовые события.
    3. `int maxevents` — максимальный размер вашего C++ массива (чтобы ядро не переполнило его).
    4. `int timeout` — сколько миллисекунд спать в ожидании событий. Если передать `-1`, поток уснет навечно, пока кто-то не напишет в сокет. Если передать `0`, функция мгновенно проверит Ready List, заберет то, что есть, и пойдет дальше (неблокирующий опрос).

**Что возвращает:** **Количество сокетов, на которых реально произошли события**. Если вернулся `0` — вышли по таймауту. Если `-1` — произошла системная ошибка.


```c
const int MAX_EVENTS = 64;
struct epoll_event events[MAX_EVENTS];

while (1) {
    int n = epoll_wait(epfd, events, MAX_EVENTS, -1);
    if (n < 0) {
        if (errno == EINTR) continue;
        perror("epoll_wait");
        break;
    }

    for (int i = 0; i < n; ++i) {
        int fd = events[i].data.fd;
        uint32_t ev = events[i].events;

        if (ev & EPOLLIN) { /* есть что читать */ }
        if (ev & EPOLLOUT) { /* можно писать */ }
        if (ev & (EPOLLHUP | EPOLLERR)) { /* ошибка/закрытие */ }
    }
}
```


### Пример алгоритма работы

```c
#include <sys/epoll.h>
#include <unistd.h>
#include <iostream>
#include <vector>

int main() {
    // 1. Создаем epoll в ядре
    int epoll_fd = epoll_create1(0);
    
    // 2. Регистрируем наш СЕРВЕРНЫЙ сокет (который делает accept) в дерево epoll
    struct epoll_event ev{};
    ev.events = EPOLLIN; // Хотим знать, когда приходят новые клиенты
    ev.data.fd = server_fd; // Привязываем дескриптор сервера
    epoll_ctl(epoll_fd, EPOLL_CTL_ADD, server_fd, &ev);

    // Выделяем массив в User Space, куда ядро будет складывать готовые события
    std::vector<struct epoll_event> ready_events(100);

    // ГЛАВНЫЙ EVENT LOOP (Цикл событий)
    while (true) {
        // Поток засыпает здесь. Ядро разбудит его, как только Ready List наполнится
        int num_events = epoll_wait(epoll_fd, ready_events.data(), ready_events.size(), -1);
        if (num_events < 0) {
            perror("epoll_wait");
            break;
        }

        // Мы проснулись! В ready_events лежат СТРОГО готовые сокеты
        for (int i = 0; i < num_events; ++i) {
            int current_fd = ready_events[i].data.fd;

            if (current_fd == server_fd) {
                // Ситуация А: Событие на серверном сокете — пришел новый клиент!
                int client_fd = accept(server_fd, nullptr, nullptr);
                
                // Делаем client_fd НЕБЛОКИРУЮЩИМ (O_NONBLOCK) — это закон для epoll!
                // ... (код перевода сокета в неблокирующий режим)
                
                // Добавляем нового клиента в наше красно-черное дерево epoll
                struct epoll_event client_ev{};
                client_ev.events = EPOLLIN | EPOLLRDHUP; // Хотим читать и знать о дисконнекте
                client_ev.data.fd = client_fd;
                epoll_ctl(epoll_fd, EPOLL_CTL_ADD, client_fd, &client_ev);
                
                std::cout << "Подключился новый клиент, добавлен в epoll!\n";
            } 
            else {
                // Ситуация Б: Событие на клиентском сокете — клиент прислал команду!
                if (ready_events[i].events & EPOLLRDHUP) {
                    // Клиент отключился
                    std::cout << "Клиент ушел, удаляем из epoll.\n";
                    epoll_ctl(epoll_fd, EPOLL_CTL_DEL, current_fd, nullptr);
                    close(current_fd);
                } 
                else if (ready_events[i].events & EPOLLIN) {
                    // Читаем данные из сокета (вызов recv гарантированно не зависнет)
                    char buf[1024];
                    ssize_t n = recv(current_fd, buf, sizeof(buf), 0);
                    // Обрабатываем команду нашего мини-шелла...
                }
            }
        }
    }

    close(epoll_fd);
    return 0;
}
```

Когда мы добавляем серверный сокет (`server_fd`) в красно-черное дерево `epoll` вместе с остальными клиентскими сокетами, мы избавляемся от всех блокирующих ожиданий.

Наш единственный поток засыпает **строго в одном месте — на строчке `epoll_wait()`**.

Теперь ядро Linux выполняет роль диспетчера:

- Если Клиент №1 прислал данные, ядро будит сервер и говорит: _«Сработал сокет Клиента №1, вызови для него `recv()`»_. И этот вызов отработает мгновенно, без зависания.
- Если в этот же момент прилетает новое подключение от Клиента №2, ядро точно так же будит сервер, но выдает маркер: _«Сработал сокет сервера (`server_fd`)»_.
- Программа заходит в `if (current_fd == server_fd)` и понимает: _«Ага, это не данные от старого клиента, это стучится новый пользователь!»_. Сервер вызывает быстрый `accept()`, мгновенно регистрирует нового клиента в `epoll` и тут же возвращается обратно спать на строку `epoll_wait()`.

Таким образом, добавление серверного сокета в `epoll` позволяет обрабатывать и новые подключения, и данные от старых клиентов **в рамках одного общего цикла событий (Event Loop)**, вообще не блокируя поток.

#### Что будет, если массив C++ переполнен, и `epoll` принес больше готовых событий?

Если в ядре готовы, например, **150 сокетов**, а вы передали в `epoll_wait` массив размером **100** (`maxevents = 100`), **никакой катастрофы, падения или потери данных не произойдет.**

Ядро Linux отработает абсолютно корректно и безопасно:

1. За один такт оно скопирует из своей внутренней очереди (Ready List) первые 100 готовых сокетов в ваш C++ массив.
2. Функция `epoll_wait()` вернет число `100`.
3. Оставшиеся 50 сокетов **останутся мирно ждать внутри ядра Linux** в списке готовых событий.
4. Ваш C++ код в цикле `for` обработает эти 100 прилетевших клиентов.
5. На следующей итерации главного цикла `while(true)` программа снова вызовет `epoll_wait()`. Ядро увидит, что пришли за добавкой, и мгновенно (уже без всякого ожидания) отдаст оставшиеся 50 сокетов.

_Поэтому фиксированный размер массива (например, 100 или 1024) — это стандартная и безопасная практика. Сеть от этого не сломается._


#### Стоит ли разделять: 1 поток на `listen`/`accept`, а 2-й поток на `epoll_wait`?

**Выделять целый поток под один только `accept()` — неэффективно**.

Почему для `accept()` не нужен отдельный поток?

Системный вызов `accept()` отрабатывает мгновенно. Ядро Linux само на сетевом уровне выполняет TCP 3-Way Handshake. Когда клиент постучался, он уже сидит в готовой очереди ядра. Вызов `accept()` просто берет готовое число (дескриптор) из этой очереди. Это занимает наносекунды. Если выделить под это целый поток, он 99.9% времени будет просто спать, зря утилизируя контекст ОС.

Как устроена идеальная многопоточная архитектура (Стандарт Nginx / Envoy / Netty)

Чтобы утилизировать все ядра вашего процессора и сделать сервер по-настоящему реактивным, используют паттерн **Multi-Reactor**:

```
               ВХОДЯЩИЙ ТРАФИК (Тысячи клиентов)
                              │
                              ▼
        ┌──────────────────────────────────────────┐
        │  ПОТОК-ДИСПЕТЧЕР (Main Thread / Accept)  │ 
        │  Слушает ОДИН порт 8080 через epoll      │
        └─────────────────────┬────────────────────┘
                              │ РАВНОМЕРНО РАСКИДЫВАЕТ КЛИЕНТОВ (Round-Robin)
                              ▼
       ┌──────────────────────┬──────────────────────┐
       ▼                      ▼                      ▼
┌──────────────┐       ┌──────────────┐       ┌──────────────┐
│ Worker Thread│       │ Worker Thread│       │ Worker Thread│
│ (Свой epoll) │       │ (Свой epoll) │       │ (Свой epoll) │
│ Клиенты 1-10 │       │Клиенты 11-20 │       │Клиенты 21-30 │
└──────────────┘       └──────────────┘       └──────────────┘
```

1. **Главный поток (Main/Dispatcher):** Он действительно крутит свой маленький `epoll`, в котором зарегистрирован **только один** серверный сокет `server_fd`. Его единственная задача — просыпаться, когда прилетает новый клиент, вызывать `accept()` и... всё.
2. **Пул рабочих потоков (Worker Threads):** При старте сервера вы создаете, например, 4 или 8 потоков (строго по количеству ядер вашего CPU). **У каждого воркер-потока внутри запущен свой собственный, изолированный `epoll_create1()`**.
3. **Передача клиента:** Когда Главный поток вызвал `accept()` и получил `client_fd`, он не обрабатывает команду шелла сам. Он берет этот `client_fd` и с помощью обычной очереди передает его одному из воркеров (например, Воркеру №3).
4. **Асинхронная работа:** Воркер №3 ловит дескриптор, регистрирует его в **своем личном красно-черном дереве `epoll`** и начинает его обслуживать.

Благодаря такой схеме:
- Потоки-воркеры никогда не пересекаются друг с другом. У каждого своя память, свой `epoll` и свои клиенты.
- Нет никаких тяжелых мьютексов и блокировок (Race Condition отсутствует).
- Если один клиент отправил тяжелую команду, которая заняла Воркера №1 на пару миллисекунд, остальные 7 воркеров на других ядрах процессора продолжают на максимальной скорости обслуживать тысячи других людей


### `struct epoll_event` как сохранять данные каждого соединения отдельно

Для сохранения пользовательских данных в `epoll` используется **объединение `epoll_data_t` (поле `data`), находящееся внутри структуры `epoll_event`**. При регистрации дескриптора через `epoll_ctl` вы можете записать в это поле указатель на свой контекст. Когда `epoll_wait` вернет событие, этот указатель будет доступен в возвращенном массиве структур.

**Важный нюанс:** Поскольку `epoll_data` — это `union`, нельзя использовать поля `ptr` и `fd` одновременно. Если записать указатель в `ptr`, то сам дескриптор `fd` нужно сохранить внутри пользовательской структуры, иначе он будет утерян.

Пример со `struct client_data` :
```cpp
struct client_data{
	char ip_addr[16];
	int port;
	int fd;
}


for (int i = 0; i < num_fd; ++i) {
    // 1. Извлекаем указатель на наши данные
    client_data* data_ptr = reinterpret_cast<client_data*>(ready_events[i].data.ptr);
    
    // 2. Проверяем, является ли сокет серверным.
    // Если мы для сервера передавали nullptr (или проверяем совпадение fd внутри структуры)
    if (data_ptr == nullptr) { 
        // Это событие на слушающем (серверном) сокете
        sockaddr_in client_addr{};
        socklen_t client_len = sizeof(client_addr);

        int client_fd = accept(fd, reinterpret_cast<sockaddr*>(&client_addr), &client_len);
        if (client_fd < 0) { 
            perror("accept"); 
            continue;
        }

        // Выделяем память под данные нового клиента
        client_data* new_client = new client_data();
        new_client->fd = client_fd;
        new_client->port = ntohs(client_addr.sin_port);
        inet_ntop(AF_INET, &client_addr.sin_addr, new_client->ip_addr, sizeof(new_client->ip_addr));

        // Регистрируем в epoll, передавая указатель на структуру
        epoll_event client_ev{};
        client_ev.events = EPOLLIN | EPOLLRDHUP;
        client_ev.data.ptr = new_client; // <--- Ключевое изменение: сохраняем указатель

        if (epoll_ctl(epoll_fd, EPOLL_CTL_ADD, client_fd, &client_ev) == -1) {
            perror("epoll_ctl ADD");
            close(client_fd);
            delete new_client;
            continue;
        }

        std::cout << "Client connected: " << new_client->ip_addr << ":" << new_client->port << std::endl;
    } 
    else {
        // 3. Это событие от обычного клиента! У нас есть полный доступ к его данным.
        int current_fd = data_ptr->fd; 

        if (ready_events[i].events & EPOLLIN) {
            char buffer[1024];
            int bytes_read = recv(current_fd, buffer, sizeof(buffer) - 1, 0);
            
            if (bytes_read > 0) {
                buffer[bytes_read] = '\0';
                std::cout << "Message from " << data_ptr->ip_addr << ":" << data_ptr->port << " -> " << buffer << std::endl;
            }
        }

        // 4. Обязательно освобождаем память при отключении или ошибке
        if (ready_events[i].events & (EPOLLRDHUP | EPOLLHUP | EPOLLERR)) {
            std::cout << "Client disconnected: " << data_ptr->ip_addr << ":" << data_ptr->port << std::endl;
            
            epoll_ctl(epoll_fd, EPOLL_CTL_DEL, current_fd, nullptr);
            close(current_fd);
            
            delete data_ptr; // <--- Удаляем структуру, чтобы избежать утечки памяти
        }
    }
}
```

- **Инициализация сервера в epoll:** Чтобы условие `data_ptr == nullptr` сработало для серверного сокета, при его первоначальном добавлении в `epoll` (где-то выше в вашем коде) вы должны были написать: `server_ev.data.ptr = nullptr;` (вместо `data.fd = fd`).
- **Управление памятью:** Каждый раз при `accept` вызывается оператор `new`. Каждый раз, когда клиент отключается (события `EPOLLRDHUP`/`EPOLLHUP`), обязательно вызывается `delete data_ptr`, иначе приложение быстро исчерпает оперативную память.
