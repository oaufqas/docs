**Модель ветвления (Branching Strategy)** — это набор правил о том, как команда создает ветки, сливает их и выпускает релизы. В индустрии доминируют три основные модели: **GitFlow**, **GitHub Flow** и **Trunk-Based Development (TBD)**. Выбор зависит от скорости релизов и архитектуры проекта.

#### GitFlow (Классическая и тяжеловесная)

Модель построена вокруг строгих релизных циклов и параллельной поддержки нескольких версий продукта.

- **Как устроена:**
    - Две вечные ветки: **`main`** (только стабильный код с продакшена) и **`develop`** (интеграционная ветка для следующей версии).
    - Три типа временных веток:
        - `feature/*` — ответвляются от `develop` для разработки новых фич и возвращаются обратно в `develop`.
        - `release/*` — ответвляются от `develop` для финального тестирования и багфиксов перед релизом, затем вливаются в `main` (с установкой тега версии) и обратно в `develop`.
        - `hotfix/*` — ответвляются напрямую от `main` для срочного лечения критических багов на проде, затем вливаются в `main` и `develop`.
- **Плюсы:** Четкий контроль над версиями, возможность одновременно разрабатывать новую версию и чинить старую, жесткая изоляция нестабильного кода.
- **Минусы:** Высокая сложность, «ад слияний» (merge hell) при долгоживущих ветках, медленная доставка фич до пользователя, избыточность для непрерывного деплоя (CI/CD).
- **Для чего лучше использовать:** Коробочные продукты, мобильные приложения (где релиз зависит от ревью в App Store/Google Play), десктопный софт, проекты со строгим версионированием (v1.0, v2.0) и редкими релизами.


#### GitHub Flow (Простая и современная)

Упрощенная модель, заточенная под непрерывную доставку (Continuous Delivery) и веб-разработку.

- **Как устроена:**
    - Одна главная ветка: **`main`**. Код в ней всегда должен быть рабочим и готовым к деплою в продакшен.
    - Для любой задачи (новая фича или багфикс) от `main` создается короткоживущая ветка (например, `feature/auth`).
    - Разработчик пушит коммиты в свою ветку и открывает **Pull Request / Merge Request**.
    - После прохождения автоматических тестов в CI и Code Review ветка вливается в `main` и сразу же выкатывается в продакшен.
- **Плюсы:** Простота (легко понять новичкам за 5 минут), быстрый цикл обратной связи, идеальная совместимость с CI/CD-пайплайнами, нет долгоживущих веток.
- **Минусы:** Не подходит, если нужно поддерживать сразу несколько старых версий продукта; при одновременной работе большой команды над крупными фичами могут возникать конфликты в `main`.
- **Для чего лучше использовать:** Веб-сервисы, SaaS-платформы, микросервисы, стартапы и небольшие/средние команды, где существует только одна актуальная версия приложения в продакшене.


#### Trunk-Based Development / TBD (Индустриальный стандарт для CI/CD)

Модель, ориентированная на максимальную скорость разработки (Continuous Integration) и практику DevOps.

- **Как устроена:**
    - Все разработчики работают в едином «стволе» (**`trunk`** или **`main`**).
    - Допускаются либо прямые микро-коммиты в `main` (в маленьких командах), либо сверхкороткие ветки (живут **не дольше 1–2 дней**), которые по несколько раз в день вливаются в `main`.
    - **Главный инструмент TBD — Feature Flags (фича-тогглы).** Если большая фича не готова, она всё равно вливается в `main` по кусочкам, но скрывается от пользователей за конфигурационным флагом (`if feature_enabled: ...`), пока не будет полностью завершена.
    - Для релизов (если нужны) от `main` в нужный момент просто ответвляется read-only ветка `release/*` или ставится тег.
- **Плюсы:** Полное отсутствие болезненных merge-конфликтов (так как интеграция происходит ежедневно), максимально быстрая доставка ценности (Time-to-Market), высокая дисциплина тестирования (пайплайн гоняет тесты на каждый чих).
- **Минусы:** Высокий порог входа (требует зрелой культуры инженерии, отличного покрытия автотестами и инфраструктуры для управления Feature Flags), один сломанный коммит может остановить работу всей команды.
- **Для чего лучше использовать:** Высоконагруженные проекты, крупные DevOps-команды, микросервисная архитектура, продуктовая разработка с десятками деплоев в день.

### Принцип работы с GitHub

GitHub — это крупнейшее хранилище Git репозиториев, а так же центр сотрудничества для миллионов разработчиков и проектов. Огромный процент всех репозиториев хранится на GitHub, а многие проекты с открытым исходным кодом используют его ради Git хостинга, баг-трекера, рецензирования кода и других вещей.

На данный момент вы можете подключаться к репозиториям Git, используя протокол `https://` и авторизуясь при помощи только что созданных логина и пароля. Для того чтобы просто клонировать публично доступный проект, вам необязательно авторизовываться на сайте. Тем не менее, только что созданный аккаунт понадобится, когда вы захотите выгрузить (push) сделанные вами изменения.

При отправке изменений по HTTPS, git всегда будет запрашивать пароль разработчика (генерируется в настройках), что весьма неудобно, правда можно использовать локальное хранилище для этого пароля и логина как [[notes/16_git/Theory#Хранилище учётных данных|описано тут]], но лучше всего использовать SSH, для этого нужно просто добавить публичный SSH-ключ в настройки учетной записи на GitHub.

GitHub использует ваш почтовый адрес для привязки ваших Git-коммитов к вашей учётной записи. Если вы используете несколько почтовых адресов в своих коммитах и хотите, чтобы GitHub работал с ними корректно, то вам нужно будет добавить все используемые почтовые адреса в секцию под названием «Почтовые адреса» («Emails»).

### Внесение собственного вклада в проекты

Теперь наша учётная запись создана и настроена, пройдёмся по деталям, которые будут полезны при внесении вклада в уже существующие проекты.

>Создание ответвлений (fork)

Для того, чтобы создать ответвление проекта, зайдите на страницу проекта и нажмите кнопку «Создать ответвление» («Fork»), которая расположена в правом верхнем углу.

![[Pasted image 20261121195148.png]]

Если вы хотите вносить свой вклад в уже существующие проекты, в которых у нас нет прав на внесения изменений путём отправки (push) изменений, вы можете создать своё собственное ответвление (fork) проекта. Это означает, что GitHub создаст вашу собственную копию проекта, данная копия будет находиться в вашем пространстве имён и вы сможете легко делать изменения путём отправки (push) изменений.

Таким образом, проекты не обеспокоены тем, чтобы пользователи, которые хотели бы выступать в роли соавторов, имели право на внесение изменений путём их отправки (push). Люди просто могут создавать свои собственные ветвления (fork), вносить туда изменения, а затем отправлять свои внесённые изменения в оригинальный репозиторий проекта путём создания запроса на принятие изменений (Pull Request), сами же запросы на принятие изменений (Pull Request) будут описаны далее. Запрос на принятие изменений (Pull Request) откроет новую ветвь с обсуждением отправляемого кода, и автор оригинального проекта, а так же другие его участники, могут принимать участие в обсуждении предлагаемых изменений до тех пор, пока автор проекта не будет ими доволен, после чего автор проекта может добавить предлагаемые изменения в проект. Вот как это обычно работает:

1. Создайте форк проекта.
2. Создайте тематическую ветку на основании ветки `master`.
3. Создайте один или несколько коммитов с изменениями, улучшающими проект.
4. Отправьте эту ветку в ваш проект на GitHub.
5. Откройте запрос на слияние на GitHub.
6. Обсуждайте его, вносите изменения, если нужно.
7. Владелец проекта принимает решение о принятии изменений, либо об их отклонении.
8. Получите обновлённую ветку `master` и отправьте её в свой форк.


Для начала, нажмите кнопку «Fork», чтобы заполучить собственную копию проекта. Мы зарегистрированы на GitHub под именем «tonychacon», так что наша копия окажется по адресу `[https://github.com/tonychacon/blink](https://github.com/tonychacon/blink)`, где мы сможем редактировать её. Мы клонируем её, создадим тематическую ветку, внесём необходимые изменения и, наконец, отправим их на GitHub.

Теперь, если мы зайдём на страничку нашей копии на GitHub, мы увидим, что GitHub заметил наши изменения и предлагает открыть запрос на слияние с помощью большой зелёной кнопки.

Также можно зайти на страницу «Branches», по адресу `https://github.com/<user>/<project>/branches`, найти интересующую ветку и открыть запрос оттуда.

![[Pasted image 20261121195535.png|592]]

Если нажать на эту кнопку, появится экран ввода заголовка и описания предлагаемых изменений на рассмотрение владельцу проекта. Рекомендуется серьёзно подойти к составлению описания и сделать его максимально информативным, чтобы владелец проекта понимал, зачем эти изменения и какую пользу они принесут.

Также мы видим список коммитов в нашей тематической ветке, «опередивших» ветку `master` (в данном случае всего один коммит) и предпросмотр всех изменений, вносимых этими коммитами.

На этом этапе, владелец проекта может просмотреть предложенные изменения, принять, отклонить или прокомментировать их. Предположим, ему импонирует идея, но он предпочёл бы большую задержку перед включением или выключением света. Как только владелец прокомментирует изменения, автор запроса на слияние (а также все подписавшиеся на этот репозиторий) получат уведомления. Далее мы рассмотрим как настроить уведомления, но сейчас, если Тони включил уведомления через электронную почту, он получит следующее письмо:

![[Pasted image 20261121195802.png]]

Кто угодно может оставлять комментарии к запросу на слияние. На странице обсуждения запроса на слияние можно увидеть пример, где владелец проекта оставил комментарии как к строке кода, так и в основной секции обсуждения. Как вы могли заметить, комментарии к коду так же приведены в виде обсуждения.

![[Pasted image 20261121200032.png|700]]

Примечательно, что если вы перейдёте на вкладку «Files Changed» в этом запросе на слияние, то увидите «унифицированную» разницу — это суммарные изменения, которые будут включены в основную ветку при слиянии тематической ветки. В терминологии `git diff` это эквивалентно команде `git diff master…​<branch>` для ветки, на которой основан этот запрос на слияние

GitHub так же проверяет может ли запрос на слияние быть применён без конфликтов и предоставляет кнопку для осуществления слияния на сервере. Эта кнопка отображается только если у вас есть права на запись в репозиторий и возможно простейшее слияние. По нажатию на неё GitHub произведёт «non-fast-forward» слияние, что значит даже если слияние **может** быть осуществлено перемоткой вперёд, всё равно будет создан коммит слияния.

При желании, можно стянуть ветку и произвести слияние локально. Если эта ветка будет слита в `master` ветку и отправлена на сервер, то GitHub автоматически закроет запрос на слияние.

Это основной рабочий процесс, который используется большинством проектов на GitHub. Создаются тематические ветки, открываются запросы на слияние, производится обсуждение, при необходимости производятся доработки в ветке и, наконец, запрос либо закрывается, либо сливается.

#### Продвинутые запросы на слияние

Если вы видите что-то вроде "запрос имеет конфликты слияния", то вам следует изменить свою ветку так, чтобы исключить конфликты и сопровождающий не делал лишнюю работу.

Существует два основных варианта это сделать. Вы можете либо перебазировать свою ветку относительно целевой ветки (обычно, относительно `master` ветки исходного репозитория), либо слить целевую ветку в свою.

Большинство разработчиков на GitHub выбирают последний вариант по тем же причинам, что и мы в предыдущем разделе. Важна история и окончательное слияние, а перебазирование не принесёт вам ничего, кроме немного более чистой истории, при этом оно **гораздо** сложнее и может стать источником ошибок.

Если вы хотите сделать запрос на слияние применяемым, то следует добавить исходный репозиторий как новый удалённый, слить изменения из его основной ветки в вашу тематическую, если имеются исправить все проблемы и, наконец, отправить все изменения в ту ветку, на основании которой был открыт запрос на слияние.

Предположим, что в примере «tonychacon», который мы использовали ранее, основной автор сделал изменения, которые конфликтуют с запросом на слияние. Рассмотрим это пошагово.

Как только это будет сделано, запрос на слияние будет автоматически обновлён и перепроверен на возможность слияния.

#### Работа в команде на github

Если работает несколько человек, а доступ с правами к общему репозиторию только у одного, это становится очень неудобно, каждому члену команды каждый раз создавать Pull Request, а единственному человеку с правами всегда принимать их. Поэтому можно добавить людей, у которых будут права для отправки коммитов.

Если Бен, Джефф и Льюис зарегистрировались на GitHub и вы хотите разрешить им делать «push» в ваш репозиторий, то добавьте их в свой проект. Это предоставит им «push» доступ; это означает, что они будут иметь права доступа как на чтение, так и на запись в проект и Git репозиторий.

В настройках нужного репозитория нужно выберать «Collaborators» в меню слева. Напишите имя пользователя в поле для ввода и нажмите кнопку «Add collaborator». Так вы можете добавить неограниченное количество пользователей. Чтобы отозвать доступ, просто нажмите «X» справа от имени пользователя.

![[Pasted image 20261122200654.png]]
