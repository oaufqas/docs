Git — это не «система контроля версий» в бытовом смысле. Внутри это **контентно-адресуемая файловая система**: хранилище объектов, каждый из которых идентифицируется SHA-1 (или SHA-256) хешем своего содержимого. Всё остальное — ветки, теги, коммиты — надстройки над этой моделью.

В Git ровно **четыре** типа объектов. Всё остальное (ветки, теги, HEAD, индекс) — это ссылки на них.

| Тип        | Что хранит                                            | Аналогия         |
| ---------- | ----------------------------------------------------- | ---------------- |
| **Blob**   | Содержимое файла (без имени, без прав)                | Файл             |
| **Tree**   | Список записей: имя + режим + хеш объекта             | Директория       |
| **Commit** | Указатель на tree, родители, автор, сообщение         | Снимок состояния |
| **A. Tag** | Указатель на объект + метаданные (аннотированный тег) | Метка на коммите |

#### Blob (binary large object)

Это только содержимое. Ни имени файла, ни прав, ни времени модификации. Если два файла в разных директориях имеют одинаковое содержимое, Git хранит **один** blob. Имя файла хранится не в blob, а в tree.

Проверить:

```bash
echo "hello" | git hash-object --stdin
# ce013625030ba8dba906f756967f9e9ca394464a
git cat-file -p ce0136
# hello
```

Содержимое blob **иммутабельно**. Изменить его нельзя — можно только создать новый blob с новым хешем.

#### Tree

Tree — это **директория**. Она содержит записи вида:

```text
<mode> <type> <hash> <name>
```

Пример:

```text
100644 blob a1b2c3...  README.md
100644 blob d4e5f6...  main.cpp
040000 tree 789abc...  src
120000 blob 012def...  link
```

- `mode` — права: `100644` (обычный файл), `100755` (исполняемый), `040000` (директория), `120000` (символическая ссылка), `160000` (submodule).
- `type` — `blob`, `tree` или `commit` (для submodule).
- `hash` — SHA-1 объекта.
- `name` — имя файла или директории.

Tree тоже иммутабельна. Если меняется один файл, создаётся новая tree для его директории, потом новая tree для родительской, и так до корня.

Проверить:

```bash
git cat-file -p HEAD^{tree}
```

#### Commit

Это **снимок** всего дерева в определённый момент. Он содержит:

```text
tree <hash корневой tree>
parent <hash родительского коммита>     (0, 1 или больше)
author <имя> <email> <timestamp> <tz>
committer <имя> <email> <timestamp> <tz>

<сообщение коммита>
```

- `tree` — корневая директория проекта на момент коммита.
- `parent` — родительские коммиты. Один — обычный, два и больше — merge.
- `author` — кто написал изменения.
- `committer` — кто применил (может отличаться после rebase/cherry-pick).
- `timestamp` — Unix time + часовой пояс.

Commit тоже иммутабелен. Любое изменение (сообщение, автор, содержимое) создаёт **новый** commit с новым SHA-1.

Проверить:

```bash
git cat-file -p HEAD
```

Пример вывода:

```text
tree 4b825dc642cb6eb9a060e54bf8d69288fbee4904
parent 8a1b2c3...
author Ivan Ivanov <ivan@example.com> 1700000000 +0300
committer Ivan Ivanov <ivan@example.com> 1700000000 +0300
Fix crash in parser
```

#### Tag (аннотированный)

Аннотированный тег — это **отдельный объект**, который указывает на commit (или другой объект) и содержит свои метаданные:

```text
object <hash коммита>
type commit
tag v1.2.3
tagger <имя> <email> <timestamp> <tz>

Release 1.2.3
```

Легковесный тег (`git tag v1`) — это просто ссылка в `refs/tags/v1`, без отдельного объекта. Аннотированный (`git tag -a v1 -m "..."`) создаёт объект `tag`.

### Как эти объекты связаны между собой


```text
[ Указатель ветки: main ]
         │
         ▼
┌────────────────────────────────────────────────────────┐
│                      COMMIT                            │
│  - Parent: ec34a1...                                   │
│  - Author: John Doe                                    │
│  - Message: "Add features"                             │
│  - Tree: ──┐                                           │
└────────────┼───────────────────────────────────────────┘
             ▼
       ┌──────────┐
       │   TREE   │  (Корневая папка проекта "/")
       │ (root)   │
       └─────┬────┴───────────────┐
             │                    │
    README.md│           src/     │
             ▼                    ▼
       ┌──────────┐         ┌──────────┐
       │   BLOB   │         │   TREE   │  (Папка "/src")
       │ (контент)│         └─────┬────┘
       └──────────┘               │
                         index.js │
                                  ▼
                            ┌──────────┐
                            │   BLOB   │
                            │ (контент)│
                            └──────────┘
```

Допустим, в проекте из примера выше вы изменили **только одну строчку** в файле `src/index.js` и сделали новый коммит:

1. Git создаст **новый `blob`** для измененного `index.js`. Старый `blob` останется нетронутым (на него всё ещё ссылаются старые коммиты).
2. Git создаст **новый `tree`** для папки `src`, записав туда хэш нового `blob`.
3. Так как папка `src` изменилась, корневой `tree` тоже изменится — создается **новый корневой `tree`**. Однако для файла `README.md` внутри корневого дерева запишется хэш **старого** `blob`, ведь этот файл не менялся!
4. Создается **новый `commit`**, который ссылается на новый корневой `tree`, а в поле `parent` указывает хэш предыдущего коммита.

Благодаря этой архитектуре Git работает молниеносно: вместо высчитывания разниц (диффов) между строками при каждом переключении веток, он просто мгновенно разворачивает сохраненное дерево объектов `tree` и `blob`.

Цепочка коммитов:

```text
A ← B ← C ← D   (main)
         ↑
         └── E  (feature)
```

Каждый коммит указывает на родителя. Merge-коммит имеет двух родителей.

#### Где это всё лежит

Объекты хранятся в `.git/objects/<первые 2 символа>/<остальные 38>`.

```text
.git/objects/
├── ce/
│   └── 013625030ba8dba906f756967f9e9ca394464a
├── 4b/
│   └── 825dc642cb6eb9a060e54bf8d69288fbee4904
└── ...
```

Хеш — это SHA-1 от `"<type> <size>\0<content>"`.

```bash
# Проверить
echo -n "hello" | git hash-object --stdin
# ce013625030ba8dba906f756967f9e9ca394464a

# Что лежит внутри?
git cat-file -t ce0136    # blob
git cat-file -s ce0136    # 5
git cat-file -p ce0136    # hello
```


#### Сжатие (zlib) и packfiles

На первый взгляд хранение каждого снимка отслеживаемого файла отдельно кажется расточительным, но Git спроектирован невероятно умно. Проект не раздувается до огромных размеров благодаря двум ключевым механизмам: **упаковке в Pack-файлы (дельта-компрессия)** и **дедупликации данных**.

Сначала объекты хранятся как отдельные zlib-сжатые файлы (**loose objects**). Когда их накапливается много (или при `git gc` / `git repack`), Git собирает их в **packfile**:

```text
.git/objects/pack/
├── pack-abc123.pack      # сжатые объекты
└── pack-abc123.idx       # индекс: hash → offset в .pack
```

Packfile использует delta-сжатие: похожие объекты хранятся как дельта от базового. Это сильно экономит место в больших репозиториях.
- Вместо хранения полных копий, он сохраняет **одну полную версию файла**, а для всех остальных версий записывает **только разницу (дельту)** — какие строки были добавлены или удалены.
- **Секрет эффективности:** Git обычно хранит в виде полной копии _самую последнюю_ версию файла, а старые версии превращает в дельты. Это сделано потому, что к последней версии обращаются чаще всего (при `git checkout` или `git status`), и её нужно разворачивать мгновенно.

#### Дедупликация (Шаринг объектов)

В отличие от традиционных систем (где история пишется для каждого файла отдельно), Git оперирует снимками всего проекта. Но если из 10 000 файлов в коммите изменился только один, Git **не копирует оставшиеся 9 999 файлов**.

Новый объект `tree` (каталог) просто получит ссылки на те же самые хэши `blob`, которые уже были созданы в прошлых коммитах. Таким образом:

- Сам измененный файл занимает место (вначале как целый `blob`, затем как микро-дельта в pack-файле).
- Все остальные тысячи неизмененных файлов в новом коммите весят ровно **0 байт**, так как на них просто ведут указатели (SHA-1 хэши).

>Если вы переписали историю (например, через `git commit --amend` или `git rebase`), старые «неудачные» версии файлов не удаляются из базы мгновенно. Они становятся «осиротевшими» (dangling) объектами.

Периодически Git автоматически запускает `git gc`. Эта команда:

- Удаляет объекты, на которые больше не ссылается ни одна ветка, тег или коммит (если они старше определенного срока, обычно 2 недели).
- Сжимает и перепаковывает оставшиеся loose-объекты в pack-файлы.

Если у вас есть текстовый файл размером **1 МБ**, и в 1000 коммитов вы меняли в нём по одной строчке:

1. В "наивной" системе без сжатия это заняло бы **1 ГБ**.
2. В Git в процессе работы (пока объекты loose) это займет чуть меньше 1 ГБ (благодаря сжатию текста через zlib).
3. После автоматической упаковки (`git gc`) этот огромный хвост истории сожмется всего в **несколько мегабайт**, так как 999 коммитов превратятся в крошечные текстовые диффы по паре байт каждый.

#### `.git/refs/` и `.git/HEAD`

Ссылки — это просто файлы с SHA-1 внутри.

```text
.git/refs/heads/main      → "8a1b2c3..."       (ветка)
.git/refs/tags/v1.2.3     → "abc123..."        (тег)
.git/HEAD                 → "ref: refs/heads/main"  (текущая ветка)
```

`HEAD` — это либо `ref: refs/heads/<branch>` (на ветке), либо сам SHA-1 (**detached HEAD**).

Проверить:

```bash
cat .git/HEAD
cat .git/refs/heads/main
git rev-parse HEAD
git rev-parse main
```

#### `.git/index` (staging area)

Индекс — это **бинарный файл**, в котором записано, что попадёт в следующий коммит. Формат: список записей `<mode> <hash> <path>` плюс метаданные (время модификации, размер) для быстрой проверки изменений.

```bash
git ls-files --stage
# 100644 ce0136... 0	README.md
# 100644 a1b2c3... 0	src/main.cpp
```

Индекс — **не** объект. Он существует только локально, в рабочем каталоге. При коммите Git берёт дерево из индекса и создаёт commit-объект.

### Итог

#### Коммит — это снимок, а не diff

Git не хранит «изменения между версиями». Он хранит **полные снимки** дерева. Каждый коммит — это ссылка на полное дерево. Diff'ы вычисляются **на лету** при `git diff` или `git log -p`. Это делает операции быстрыми. Переключение на любую ветку — это просто смена указателя и распаковка нужных blob'ов из packfile. Не нужно применять цепочку патчей.

#### Дедупликация через хеши

Если в 100 коммитах файл не менялся, blob хранится **один раз**. Tree тоже дедуплицируются: если директория не менялась, все коммиты ссылаются на одну и ту же tree.

Именно поэтому `.git` в большом репозитории может занимать меньше, чем сумма всех версий файлов.

#### Иммутабельность и переписывание истории

Раз объекты иммутабельны, «изменить коммит» невозможно. `git commit --amend`, `git rebase`, `git filter-repo` — все они создают **новые** объекты и переставляют ссылки.

Старые объекты остаются в `.git/objects`, пока их не удалит `git gc`. Именно поэтому:

- после `git reset --hard` старые коммиты можно найти через `git reflog`;
- после `git rebase` старые коммиты висят «в воздухе» до garbage collection;
- после `git filter-repo` нужно делать `gc` и force-push, чтобы удалить секреты из истории.

#### Merge и rebase через призму модели

**Merge** создаёт **новый commit** с двумя родителями. История сохраняется:

```text
A ← B ← C ← M   (main)
         ↑   │
         └── D  (feature)
```

**Rebase** создаёт **новые коммиты** с другими родителями. Старые остаются в объектах, но ссылки переставляются:

```text
A ← B ← C ← D'  (main)
```

где `D'` — копия `D`, но с родителем `C`.

#### `git cat-file` — окно в модель

Главная команда для изучения:

```bash
git cat-file -t <hash>     # тип объекта
git cat-file -s <hash>     # размер
git cat-file -p <hash>     # содержимое (pretty print)
```

Пройтись по цепочке от `HEAD`:

```bash
# Кто я?
git rev-parse HEAD
# Что за коммит?
git cat-file -p HEAD
# Какое дерево?
git cat-file -p HEAD^{tree}
# Что внутри файла?
git cat-file -p HEAD:README.md
```

#### `git fsck` — найти «висячие» объекты

```bash
git fsck --lost-found
```

Покажет объекты, на которые не ссылается ни одна ветка/тег. Полезно при восстановлении после `reset`/`rebase`.

#### `git gc` — уборка

```bash
git gc
```

- Собирает loose objects в packfile.
- Удаляет недостижимые объекты старше `gc.pruneExpire` (по умолчанию 2 недели).
- Пересчитывает дельты.

После `filter-repo` обязательно:

```bash
git reflog expire --expire=now --all
git gc --prune=now --aggressive
```

Иначе удалённые секреты останутся в `.git/objects`, и их можно будет найти.
