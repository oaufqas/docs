Git — это не «система контроля версий» в бытовом смысле. Внутри это **контентно-адресуемая файловая система**: хранилище объектов, каждый из которых идентифицируется SHA-1 (или SHA-256) хешем своего содержимого. Всё остальное — ветки, теги, коммиты — надстройки над этой моделью.

Когда вы выполняете `git init` в новом или существовавшем ранее каталоге, Git создаёт подкаталог `.git`, в котором располагается почти всё, чем он манипулирует. Если требуется выполнить резервное копирование или клонирование репозитория, достаточно скопировать лишь этот каталог, чтобы получить почти всё необходимое. Данная глава почти полностью посвящена его содержимому. Вот так выглядит только что созданный каталог `.git`:

```bash
$ ls -F1
config
description
HEAD
hooks/
info/
objects/
refs/
```

В зависимости от используемой версии Git здесь могут присутствовать и другие файлы, но по умолчанию команда `git init` создаёт именно такое содержимое в каталоге `.git`. Файл `description` используется только программой GitWeb, не обращайте на него внимание. Файл `config` содержит специфичные для этого репозитория конфигурационные параметры, а в каталоге `info` расположен файл с глобальными настройкам игнорирования файлов  — он позволяет исключить файлы, которые вы не хотите помещать в `.gitignore`. В каталоге `hooks` располагаются клиентские и серверные хуки.

Итак, осталось четыре важных элемента: файлы `HEAD` и `index` (ещё не созданный) и каталоги `objects` и `refs`. Это ключевые элементы Git. В каталоге `objects` находится база данных объектов Git; в `refs` — ссылки на объекты коммитов в этой базе (ветки, теги и другие); файл `HEAD` указывает на текущую ветку, a в файле `index` хранится содержимое индекса.

#### `.git/index` (staging area)

Индекс — это **бинарный файл**, в котором записано, что попадёт в следующий коммит. Формат: список записей `<mode> <hash> <path>` плюс метаданные (время модификации, размер) для быстрой проверки изменений.

```bash
git ls-files --stage
# 100644 ce0136... 0	README.md
# 100644 a1b2c3... 0	src/main.cpp
```

Индекс — **не** объект. Он существует только локально, в рабочем каталоге. При коммите Git берёт дерево из индекса и создаёт commit-объект.


---

В Git ровно **четыре** типа объектов. Всё остальное (ветки, теги, HEAD, индекс) — это ссылки на них, эти типы находятся в каталоге `.git/objects`

| Тип        | Что хранит                                            | Аналогия         |
| ---------- | ----------------------------------------------------- | ---------------- |
| **Blob**   | Содержимое файла (без имени, без прав)                | Файл             |
| **Tree**   | Список записей: имя + режим + хеш объекта             | Директория       |
| **Commit** | Указатель на tree, родители, автор, сообщение         | Снимок состояния |
| **A. Tag** | Указатель на объект + метаданные (аннотированный тег) | Метка на коммите |

### Blob (binary large object)

Содержимое blob **иммутабельно**. Изменить его нельзя — можно только создать новый blob с новым хешем. Ни имени файла, ни прав, ни времени модификации. Если два файла в разных директориях имеют одинаковое содержимое, Git хранит **один** blob. Имя файла хранится не в blob, а в tree.

Проверить:

```bash
echo "hello" | git hash-object -w --stdin
# ce013625030ba8dba906f756967f9e9ca394464a
git cat-file -p ce0136
# hello
```

В простейшем случае `git hash-object` берёт переданный контент и возвращает уникальный ключ, который будет использоваться для хранения данных в базе Git. Параметр `-w` указывает команде `git hash-object` не просто вернуть ключ, а ещё и сохранить объект в базе данных. Последний параметр `--stdin` указывает, что `git hash-object` должна использовать данные, переданные на стандартный поток ввода; в противном случае команда ожидает путь к файлу в качестве аргумента.

Результат выполнения команды — 40-символьная контрольная сумма. Это SHA-1-хеш — контрольная сумма содержимого и заголовка, который будет рассмотрен позднее. Теперь можно посмотреть, как Git хранит ваши данные:

```bash
$ find .git/objects -type f
.git/objects/ce/013625030ba8dba906f756967f9e9ca394464a
```

Мы видим новый файл в каталоге `objects`. Это и есть начальное внутреннее представление данных в Git — один файл на единицу хранения с именем, являющимся контрольной суммой содержимого и заголовка. Первые два символа SHA-1 определяют подкаталог файла внутри `objects`, остальные 38 — его имя.

Извлечь содержимое объекта можно при помощи команды `cat-file`. Она подобна швейцарскому ножу для анализа объектов Git. Ключ `-p` указывает команде `cat-file` автоматически определять тип объекта и выводить результат в соответствующем виде:

```bash
$ git cat-file -p d670460b4b4aece5915caf5c68d12f560a9fe3e4
test content
```

Теперь вы умеете добавлять данные в Git и извлекать их обратно. То же самое можно делать и с файлами. Например, можно проверсионировать один файл. Для начала создадим новый файл и сохраним его в базе данных Git:

```bash
$ echo 'version 1' > test.txt
$ git hash-object -w test.txt
83baae61804e65cc73a7201a7252750c76066a30
```

Теперь изменим файл и сохраним его в базе ещё раз:

```bash
$ echo 'version 2' > test.txt
$ git hash-object -w test.txt
1f7a7a472abf3dd9643fd615f6da379c4acb3e3a
```

Теперь в базе содержатся две версии файла, а также самый первый сохранённый объект:

```bash
$ find .git/objects -type f
.git/objects/1f/7a7a472abf3dd9643fd615f6da379c4acb3e3a
.git/objects/83/baae61804e65cc73a7201a7252750c76066a30
.git/objects/ce/013625030ba8dba906f756967f9e9ca394464a
```

Теперь можно откатить файл к его первой версии:

```bash
$ git cat-file -p 83baae61804e65cc73a7201a7252750c76066a30 > test.txt
$ cat test.txt
version 1
```

или ко второй:

```bash
$ git cat-file -p 1f7a7a472abf3dd9643fd615f6da379c4acb3e3a > test.txt
$ cat test.txt
version 2
```

Однако запоминать хеш для каждой версии неудобно, к тому же теряется имя файла, сохраняется лишь содержимое. Объекты такого типа называют блобами (англ. _blob_ — binary large object). Имея SHA-1-хеш объекта, можно попросить Git показать нам его тип с помощью команды `cat-file -t`:

```bash
$ git cat-file -t 1f7a7a472abf3dd9643fd615f6da379c4acb3e3a
blob
```

### Tree

Следующий тип объектов — деревья, они решают проблему хранения имён файлов, а также позволяют хранить группы файлов вместе. Git хранит данные сходным с файловыми системами UNIX способом, но в немного упрощённом виде. Содержимое хранится в деревьях и блобах, где дерево соответствует каталогу на файловой системе, а блоб более или менее соответствует индексу узла (inode) или содержимому файла. Tree тоже иммутабельна. Если меняется один файл, создаётся новая tree для его директории, потом новая tree для родительской, и так до корня.

```bash
<mode> <type> <hash> <name>
```

Дерево может содержать одну или более записей, содержащих SHA-1-хеш, соответствующий блобу или поддереву, права доступа к файлу, тип и имя файла. Например, дерево последнего коммита в проекте может выглядеть следующим образом:

```bash
$ git cat-file -p master^{tree}
100644 blob a906cb2a4a904a152e80877d4088654daad0c859      README
100644 blob 8f94139338f9404f26296befa88755fc2598c289      Rakefile
040000 tree 99f1a6d12cb4b6f19c8655fca46c3ecf317074e0      lib
```

- `mode` — права: `100644` (обычный файл), `100755` (исполняемый), `040000` (директория), `120000` (символическая ссылка), `160000` (submodule).
- `type` — `blob`, `tree` или `commit` (для submodule).
- `hash` — SHA-1 объекта.
- `name` — имя файла или директории.

Обратите внимание, что подкаталог `lib` — не блоб, а указатель на другое дерево:

```bash
$ git cat-file -p 99f1a6d12cb4b6f19c8655fca46c3ecf317074e0
100644 blob 47c6340d6459e05787f644c2447d2595f5d3a54b      simplegit.rb
```

### Commit

Формат объекта коммита прост: в нём указано дерево верхнего уровня, соответствующее состоянию проекта на некоторый момент; родительские коммиты, если существуют (в примере выше объект коммита не имеет родителей); имена автора и коммиттера (берутся из полей конфигурации `user.name` и `user.email`) с указанием временной метки; пустая строка и сообщение коммита. Это **снимок** всего дерева в определённый момент. Он содержит:

```text
tree <hash корневой tree>
parent <hash родительского коммита>     (0, 1 или больше)
author <имя> <email> <timestamp> <tz>
committer <имя> <email> <timestamp> <tz>

<сообщение коммита>
```

- `tree` — корневая директория проекта на момент коммита.
- `parent` — родительские коммиты. Один — обычный, два и больше — merge.
- `author` — кто написал изменения.
- `committer` — кто применил (может отличаться после rebase/cherry-pick).
- `timestamp` — Unix time + часовой пояс.

Commit тоже иммутабелен. Любое изменение (сообщение, автор, содержимое) создаёт **новый** commit с новым SHA-1.

Проверить:

```bash
git cat-file -p HEAD
```

Пример вывода:

```text
tree 4b825dc642cb6eb9a060e54bf8d69288fbee4904
parent 8a1b2c3...
author Ivan Ivanov <ivan@example.com> 1700000000 +0300
committer Ivan Ivanov <ivan@example.com> 1700000000 +0300
Fix crash in parser
```

### Branches 

Если вас интересует история репозитория начиная с определённого коммита, например `1a410e`, то для её отображения вы можете воспользоваться командой `git log 1a410e`, однако при этом вам всё ещё необходимо помнить хеш коммита `1a410e`, который является начальной точкой истории. Было бы неплохо, если бы существовал файл, в который можно было бы сохранить значение SHA-1 под простым именем, а затем использовать это имя вместо хеша SHA-1.

В Git такие файлы называются ссылками («references» или, сокращённо, «refs») и расположены в каталоге `.git/refs`. В нашем проекте этот каталог пока пуст, но в нём уже прослеживается некая структура:

```bash
$ find .git/refs
.git/refs
.git/refs/heads
.git/refs/tags
$ find .git/refs -type f
```

Чтобы создать новую ссылку, которая поможет вам запомнить SHA-1 последнего коммита, технически, достаточно выполнить примерно следующее:

```bash
$ echo 1a410efbd13591db07496601ebc7a059dd55cfe9 > .git/refs/heads/master
```

Теперь в командах Git вместо SHA-1 можно использовать только что созданную ссылку:

```bash
$ git log --pretty=oneline master
1a410efbd13591db07496601ebc7a059dd55cfe9 Third commit
cac0cab538b970a37ea1e769cbbde608743bc96d Second commit
fdf4fc3344e67ab068f836878b6c4951e3b15f3d First commit
```

Тем не менее, редактировать файлы ссылок вручную не рекомендуется, вместо этого Git предоставляет более безопасную команду `update-ref` на случай, если вам потребуется изменить ссылку:

```bash
$ git update-ref refs/heads/master 1a410efbd13591db07496601ebc7a059dd55cfe9
```

Вот что такое, по сути, ветка в Git — простой указатель или ссылка на последний коммит в цепочке. Для создания ветки, соответствующей предыдущему коммиту, можно выполнить следующее:

```bash
$ git update-ref refs/heads/test cac0ca
```

Данная ветка будет содержать лишь коммиты по указанный, но не те, что были созданы после него:

```bash
$ git log --pretty=oneline test
cac0cab538b970a37ea1e769cbbde608743bc96d Second commit
fdf4fc3344e67ab068f836878b6c4951e3b15f3d First commit
```

Теперь база данных Git схематично выглядит так, как показано на рисунке:

![Объекты в каталоге .git, а также указатели на вершины веток](https://git-scm.com/book/ru/v2/images/data-model-4.png)

Объекты в каталоге .git, а также указатели на вершины веток

При выполнении команды `git branch <branch>` Git в действительности запускает команду `update-ref`, которая добавляет SHA-1-хеш последнего коммита текущей ветки в файл с именем указанной ветки.

### HEAD

Как же Git получает хеш последнего коммита при выполнении `git branch <имя ветки>`? Ответ кроется в файле HEAD.

Файл `HEAD` — это символическая ссылка на текущую ветку. Символическая ссылка отличается от обычной тем, что она содержит не сам хеш SHA-1, а указатель на другую ссылку.

В некоторых случаях файл `HEAD` может содержать SHA-1 хеш какого-либо объекта. Это происходит при извлечении тега, коммита или удалённой ветки, что приводит репозиторий в состояние [[releases-tags#Detached HEAD|Detached HEAD]]

Если вы заглянете внутрь `HEAD`, то увидите следующее:

```bash
$ cat .git/HEAD
ref: refs/heads/master
```

Если выполнить `git checkout test`, Git обновит содержимое файла:

```bash
$ cat .git/HEAD
ref: refs/heads/test
```

При выполнении `git commit` Git создаёт коммит, указывая его родителем объект, SHA-1 которого содержится в файле, на который ссылается `HEAD`.

При желании можно вручную редактировать этот файл, но лучше использовать команду `symbolic-ref`. Получить значение `HEAD` этой командой можно так:

```bash
$ git symbolic-ref HEAD
refs/heads/master
```

Изменить значение `HEAD` можно так:

```bash
$ git symbolic-ref HEAD refs/heads/test
$ cat .git/HEAD
ref: refs/heads/test
```

Символическую ссылку на файл вне `.git/refs` поставить нельзя:

```bash
$ git symbolic-ref HEAD test
fatal: Refusing to point HEAD outside of refs/
```

### Ссылки на удалённые ветки

Если вы добавили удалённый репозиторий и отправили в него какие-нибудь изменения, Git сохранит последнее отправленное значение SHA-1 в каталоге `refs/remotes` для каждой отправленной ветки. Например, можно добавить удалённый репозиторий `origin` и отправить туда ветку `master`:

```bash
$ git remote add origin git@github.com:schacon/simplegit-progit.git
$ git push origin master
Counting objects: 11, done.
Compressing objects: 100% (5/5), done.
Writing objects: 100% (7/7), 716 bytes, done.
Total 7 (delta 2), reused 4 (delta 1)
To git@github.com:schacon/simplegit-progit.git
  a11bef0..ca82a6d  master -> master
```

Позже вы сможете посмотреть, где находилась ветка `master` с сервера `origin` во время последней синхронизации с ним, заглянув в файл `refs/remotes/origin/master`:

```bash
$ cat .git/refs/remotes/origin/master
ca82a6dff817ec66f44342007202690a93763949
```

Ссылки на удалённые ветки отличаются от веток (ссылок в `refs/heads`) тем, что они считаются неизменяемыми. Это означает, что вы можете переключиться на любую из таких веток с помощью `git checkout`, но Git не установит `HEAD` на неё, а значит, вы не сможете фиксировать свои изменения в ней с помощью `git commit`. Git воспринимает удалённые ветки как закладки на последние известные состояния веток на удалённых серверах.

### Tags

Объект тега очень похож на объект коммита: он содержит имя своего автора, дату, сообщение и указатель. Разница же в том, что объект тега указывает на коммит, а не на дерево. Он похож на ветку, которая никогда не перемещается: он всегда указывает на один и тот же коммит, просто давая ему понятное имя. Аннотированный (`git tag -a v1 -m "..."`) создаёт объект `tag`. 

Аннотированный тег — это **отдельный объект**, который указывает на commit (или другой объект) и содержит свои метаданные:

```bash
object <hash коммита>
type commit
tag v1.2.3
tagger <имя> <email> <timestamp> <tz>

Release 1.2.3
```

Мы можем создать аннотированный тег, используя опцию `-a`:

```bash
$ git tag -a v1.1 1a410efbd13591db07496601ebc7a059dd55cfe9 -m 'Test tag'
```

Вот значение SHA-1 созданного объекта:

```bash
$ cat .git/refs/tags/v1.1
9585191f37f7b0fb9444f35a9bf50de191beadc2
```

Теперь выполним `git cat-file -p` для этого хеша:

```bash
$ git cat-file -p 9585191f37f7b0fb9444f35a9bf50de191beadc2
object 1a410efbd13591db07496601ebc7a059dd55cfe9
type commit
tag v1.1
tagger Scott Chacon <schacon@gmail.com> Sat May 23 16:48:58 2009 -0700

Test tag
```

Обратите внимание, что в поле `object` записан SHA-1 помеченного коммита. Также стоит отметить, что это поле не обязательно должно указывать на коммит; вы можете пометить любой объект в Git. Например, в исходниках Git сопровождающий проекта добавил свой публичный GPG-ключ в блоб и пометил его. Увидеть этот ключ можно, выполнив команду:

```bash
$ git cat-file blob junio-gpg-pub
```

>Легковесный тег (`git tag v1`) — это просто ссылка в `.git/refs/tags/v1`, без отдельного объекта. Его можно создать командой:

```bash
$ git update-ref refs/tags/v1.0 cac0cab538b970a37ea1e769cbbde608743bc96d
```

Вот и всё, легковесный тег — это ветка, которая никогда не перемещается.

```text
[ Указатель ветки: main ]
         │
         ▼
┌────────────────────────────────────────────────────────┐
│                      COMMIT                            │
│  - Parent: ec34a1...                                   │
│  - Author: John Doe                                    │
│  - Message: "Add features"                             │
│  - Tree: ──┐                                           │
└────────────┼───────────────────────────────────────────┘
             ▼
       ┌──────────┐
       │   TREE   │  (Корневая папка проекта "/")
       │ (root)   │
       └─────┬────┴───────────────┐
             │                    │
    README.md│           src/     │
             ▼                    ▼
       ┌──────────┐         ┌──────────┐
       │   BLOB   │         │   TREE   │  (Папка "/src")
       │ (контент)│         └─────┬────┘
       └──────────┘               │
                         index.js │
                                  ▼
                            ┌──────────┐
                            │   BLOB   │
                            │ (контент)│
                            └──────────┘
```

Допустим, в проекте из примера выше вы изменили **только одну строчку** в файле `src/index.js` и сделали новый коммит:

1. Git создаст **новый `blob`** для измененного `index.js`. Старый `blob` останется нетронутым (на него всё ещё ссылаются старые коммиты).
2. Git создаст **новый `tree`** для папки `src`, записав туда хэш нового `blob`.
3. Так как папка `src` изменилась, корневой `tree` тоже изменится — создается **новый корневой `tree`**. Однако для файла `README.md` внутри корневого дерева запишется хэш **старого** `blob`, ведь этот файл не менялся!
4. Создается **новый `commit`**, который ссылается на новый корневой `tree`, а в поле `parent` указывает хэш предыдущего коммита.

Благодаря этой архитектуре Git работает молниеносно: вместо высчитывания разниц (диффов) между строками при каждом переключении веток, он просто мгновенно разворачивает сохраненное дерево объектов `tree` и `blob`.

Цепочка коммитов:

```text
A ← B ← C ← D   (main)
         ↑
         └── E  (feature)
```

Каждый коммит указывает на родителя. Merge-коммит имеет двух родителей.

#### Где это всё лежит

Объекты хранятся в `.git/objects/<первые 2 символа>/<остальные 38>`.

```text
.git/objects/
├── ce/
│   └── 013625030ba8dba906f756967f9e9ca394464a
├── 4b/
│   └── 825dc642cb6eb9a060e54bf8d69288fbee4904
└── ...
```

Хеш — это SHA-1 от `"<type> <size>\0<content>"`.

```bash
# Проверить
echo -n "hello" | git hash-object --stdin
# ce013625030ba8dba906f756967f9e9ca394464a

# Что лежит внутри?
git cat-file -t ce0136    # blob
git cat-file -s ce0136    # 5
git cat-file -p ce0136    # hello
```


### Сжатие (zlib) и packfiles

На первый взгляд хранение каждого снимка отслеживаемого файла отдельно кажется расточительным, но Git спроектирован невероятно умно. Проект не раздувается до огромных размеров благодаря двум ключевым механизмам: **упаковке в Pack-файлы (дельта-компрессия)** и **дедупликации данных**.

Сначала объекты хранятся как отдельные zlib-сжатые файлы (**loose objects**). Когда их накапливается много (или при `git gc` / `git repack`), Git собирает их в **packfile**:

```text
.git/objects/pack/
├── pack-abc123.pack      # сжатые объекты
└── pack-abc123.idx       # индекс: hash → offset в .pack
```

Для наглядности добавим в репозиторий файл `repo.rb` размером 22 Кб, и зафиксируем изменения в коммит. Если посмотреть на полученное дерево, мы увидим значение SHA-1 блоба для файла `repo.rb`:

```bash
$ git cat-file -p master^{tree}
100644 blob fa49b077972391ad58037050f2a75f74e3671e92      new.txt
100644 blob 033b4468fa6b2a9547a70d88d1bbe8bf3f9ed0d5      repo.rb
100644 blob e3f094f522629ae358806b17daf78246c27c007b      test.txt
```

Посмотрим, сколько этот объект занимает места на диске, используя `git cat-file`:

```bash
$ git cat-file -s 033b4468fa6b2a9547a70d88d1bbe8bf3f9ed0d5
22044
```

Теперь немного изменим этот файл и посмотрим на результат:

```bash
$ echo '# testing' >> repo.rb
$ git commit -am 'Modify repo.rb a bit'
[master 2431da6] Modify repo.rb a bit
 1 file changed, 1 insertion(+)
```

Взглянув на дерево, полученное в результате коммита, мы увидим любопытную вещь:

```bash
$ git cat-file -p master^{tree}
100644 blob fa49b077972391ad58037050f2a75f74e3671e92      new.txt
100644 blob b042a60ef7dff760008df33cee372b945b6e884e      repo.rb
100644 blob e3f094f522629ae358806b17daf78246c27c007b      test.txt
```

Теперь файлу `repo.rb` соответствует совершенно другой блоб; это означает, что после добавления всего одной единственной строки в конец 400-строчного файла, Git сохранит новый контент в отдельный объект:

```bash
$ git cat-file -s b042a60ef7dff760008df33cee372b945b6e884e
22054
```

Итак, мы имеем два практически одинаковых объекта, занимающих по 22 Кб на диске (в сжатом виде — приблизительно 7 Кб каждый). 

Первоначальный формат для сохранения объектов в Git называется «рыхлым» форматом (loose format). Однако, время от времени Git упаковывает несколько таких объектов в один pack-файл для сохранения места на диске и повышения эффективности. Это происходит, когда «рыхлых» объектов становится слишком много, а также при ручном вызове `git gc` или отправке изменений на удалённый сервер.

Packfile использует delta-сжатие: похожие объекты хранятся как дельта от базового. Это сильно экономит место в больших репозиториях.
- Вместо хранения полных копий, он сохраняет **одну полную версию файла**, а для всех остальных версий записывает **только разницу (дельту)** — какие строки были добавлены или удалены.
- **Секрет эффективности:** Git обычно хранит в виде полной копии _самую последнюю_ версию файла, а старые версии превращает в дельты. Это сделано потому, что к последней версии обращаются чаще всего (при `git checkout` или `git status`), и её нужно разворачивать мгновенно.

```bash
.git/objects/pack/pack-978e03944f5c581011e6998cd0e9e30000905586.idx
.git/objects/pack/pack-978e03944f5c581011e6998cd0e9e30000905586.pack
```

Pack-файл — это файл, в котором теперь находится содержимое всех удалённых объектов. Индекс — это файл, в котором записаны смещения для быстрого доступа к содержимому прежних объектов. Упаковка данных положительно повлияла на общий размер файлов: если до вызова команды `gc` в сжатом виде они занимали примерно 15 Кб, то pack-файл занимает всего 7 Кб. За счёт упаковки объектов мы только что освободили как минимум половину занимаемого дискового пространства

Посмотреть содержимое сжатого файла можно командой:

```bash
$ git verify-pack -v .git/objects/pack/pack-978e039...
```

#### Дедупликация (Шаринг объектов)

В отличие от традиционных систем (где история пишется для каждого файла отдельно), Git оперирует снимками всего проекта. Но если из 10 000 файлов в коммите изменился только один, Git **не копирует оставшиеся 9 999 файлов**.

Новый объект `tree` (каталог) просто получит ссылки на те же самые хэши `blob`, которые уже были созданы в прошлых коммитах. Таким образом:

- Сам измененный файл занимает место (вначале как целый `blob`, затем как микро-дельта в pack-файле).
- Все остальные тысячи неизмененных файлов в новом коммите весят ровно **0 байт**, так как на них просто ведут указатели (SHA-1 хэши).

>Если вы переписали историю (например, через `git commit --amend` или `git rebase`), старые «неудачные» версии файлов не удаляются из базы мгновенно. Они становятся «осиротевшими» (dangling) объектами.

Периодически Git автоматически запускает `git gc`. Эта команда:

- Удаляет объекты, на которые больше не ссылается ни одна ветка, тег или коммит (если они старше определенного срока, обычно 2 недели).
- Сжимает и перепаковывает оставшиеся loose-объекты в pack-файлы.

Если у вас есть текстовый файл размером **1 МБ**, и в 1000 коммитов вы меняли в нём по одной строчке:

1. В "наивной" системе без сжатия это заняло бы **1 ГБ**.
2. В Git в процессе работы (пока объекты loose) это займет чуть меньше 1 ГБ (благодаря сжатию текста через zlib).
3. После автоматической упаковки (`git gc`) этот огромный хвост истории сожмется всего в **несколько мегабайт**, так как 999 коммитов превратятся в крошечные текстовые диффы по паре байт каждый.

#### Коммит — это снимок, а не diff

Git не хранит «изменения между версиями». Он хранит **полные снимки** дерева. Каждый коммит — это ссылка на полное дерево. Diff'ы вычисляются **на лету** при `git diff` или `git log -p`. Это делает операции быстрыми. Переключение на любую ветку — это просто смена указателя и распаковка нужных blob'ов из packfile. Не нужно применять цепочку патчей.

#### Дедупликация через хеши

Если в 100 коммитах файл не менялся, blob хранится **один раз**. Tree тоже дедуплицируются: если директория не менялась, все коммиты ссылаются на одну и ту же tree.

Именно поэтому `.git` в большом репозитории может занимать меньше, чем сумма всех версий файлов.

#### Иммутабельность и переписывание истории

Раз объекты иммутабельны, «изменить коммит» невозможно. `git commit --amend`, `git rebase`, `git filter-repo` — все они создают **новые** объекты и переставляют ссылки.

Старые объекты остаются в `.git/objects`, пока их не удалит `git gc`. Именно поэтому:

- после `git reset --hard` старые коммиты можно найти через `git reflog`;
- после `git rebase` старые коммиты висят «в воздухе» до garbage collection;
- после `git filter-repo` нужно делать `gc` и force-push, чтобы удалить секреты из истории.

#### `git cat-file` — окно в модель

Главная команда для изучения:

```bash
git cat-file -t <hash>     # тип объекта
git cat-file -s <hash>     # размер
git cat-file -p <hash>     # содержимое (pretty print)
```

Пройтись по цепочке от `HEAD`:

```bash
# Кто я?
git rev-parse HEAD
# Что за коммит?
git cat-file -p HEAD
# Какое дерево?
git cat-file -p HEAD^{tree}
# Что внутри файла?
git cat-file -p HEAD:README.md
```

#### `git fsck` — найти «висячие» объекты

```bash
git fsck --lost-found
```

Покажет объекты, на которые не ссылается ни одна ветка/тег. Полезно при восстановлении после `reset`/`rebase`.

#### `git gc` — уборка

```bash
git gc
```

- Собирает loose objects в packfile.
- Удаляет недостижимые объекты старше `gc.pruneExpire` (по умолчанию 2 недели).
- Пересчитывает дельты.

После `filter-repo` обязательно:

```bash
git reflog expire --expire=now --all
git gc --prune=now --aggressive
```

Иначе удалённые секреты останутся в `.git/objects`, и их можно будет найти.
