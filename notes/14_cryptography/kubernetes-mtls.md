Kubernetes — это **полностью децентрализованная система**. У него нет единого пароля или логина. Чтобы например api-server мог сказать kubelet'у создать под на ноде, они оба должны убедиться в подлинности друг друга. Для этого используется mTLS:

Поэтому нужно создать для каждого компонента кластера, свой сертификат (приватный и публичный ключи)

![[Pasted image 20260721013123.png]]

Строки и поля внутри анкет (Стандарт X.509). Все эти аббревиатуры пришли из международного стандарта цифровых паспортов **X.509**:

- **CN (Common Name — Общее / Главное имя)**
    - _Что это:_ Имя владельца паспорта. Для человека это может быть имя-фамилия, для сайта — домен (например, `google.com`), а для Кубера — системное имя компонента (например, `system:kube-scheduler`).
- **C (Country — Страна)**
    - _Что это:_ Двухбуквенный международный код государства.
- **L (Locality — Локация / Город)**
    - _Что это:_ Физический город, где зарегистрирована система.
- **O (Organization — Организация / Компания)**
    - _Что это:_ Самое важное рабочее поле для Кубера. В обычной жизни это имя фирмы (например, `Google LLC`), а в Kubernetes это **имя системной группы прав (RBAC)**. Пиша туда `system:masters` или `system:nodes`, мы жестко определяем уровень привилегий компонента в ядре.
- **OU (Organizational Unit — Подразделение / Отдел)**
    - _Что это:_ Текстовое название отдела внутри компании.
- **SAN (Subject Alternative Name — Альтернативное имя субъекта)**
    - _Что это:_ Скрытый технический блок внутри сертификата, куда мы через запятую зашивали список всех IP-адресов и DNS-имен мастера (параметр `-hostname` в `cfssl`). Без этого блока клиенты выдадут ошибку безопасности при попытке вызвать API-сервер по сети.


Криптографические стандарты и утилиты

- **PKI (Public Key Infrastructure — Инфраструктура открытых ключей)**
    - _Что это:_ Общее название всей системы безопасности, которую мы строим. Это набор правил, компонентов и ключей, который позволяет узлам сети доверять друг другу без использования классических паролей.
- **CA (Certificate Authority — Центр сертификации / Удостоверяющий центр)**
    - _Что это:_ Главный доверенный узел («цифровой бог» кластера). Его единственная задача — проверять подлинность чужих анкет и ставить на них свою доверенную математическую печать (`ca.pem`).
- **CSR (Certificate Signing Request — Запрос на подпись сертификата)**
    - _Что это:_ Текстовая анкета-заявка (наши файлы `.json` и сгенерированные `.csr`), которую компонент отправляет в адрес **CA**, чтобы получить официальный паспорт (сертификат).
- **PEM (Privacy-Enhanced Mail — Почта с повышенной конфиденциальностью)**
    - _Что это:_ Историческое название формата файлов (расширение `.pem`). На самом деле это обычный текстовый файл, внутри которого бинарные криптографические ключи и сертификаты закодированы безопасным методом **Base64** и зажаты между строками `-----BEGIN ...-----` и `-----END ...-----`.
- **CRT / CERT (Certificate — Сертификат / Паспорт)**
    - _Что это:_ Публичный цифровой паспорт компонента. В `cfssl` он сохраняется с расширением `.pem`.
- **KEY (Private Key — Закрытый / Приватный ключ)**
    - _Что это:_ Секретная цифровая подпись компонента, которая всегда генерируется в паре с сертификатом.


Названия утилит, которые можно использовать для создания всех нужных сертификатов.

- **CFSSL (Cloudflare SSL — Инструмент работы со слоем защищенных сокетов от компании Cloudflare)**
    - _Что это:_ Программа-генератор, которая берет JSON-файлы и превращает их в криптографические ключи. **SSL/TLS** (Secure Sockets Layer / Transport Layer Security) — это те самые протоколы шифрования трафика в интернете.
- **CFSSLJSON**
    - _Что это:_ Вспомогательная утилита-парсер, которая берет огромный текстовый поток вывода от `cfssl` в формате **JSON** и аккуратно разрезает его на отдельные файлы `.pem` на жестком диске

#### Создание сертификатов kubernetes the hard way

>1) Созданием сертификатов в этом примере будут заниматься утилиты `cfssl` и парсер `cfssljson` от CloudFlare. Изначально нужно создать конфиг для `cfssl`, чтобы она знала, как нужно создавать серты, `ca-config.json`:

```yaml
{
  "signing": {
    "default": {
      "expiry": "87600h"
    },
    "profiles": {
      "kubernetes": {
        "usages": [
          "signing", # разрешено подписывать другие данные
          "key encipherment", # разрешено использовать для шифрования трафика
          "server auth", # этот сертификат может использоваться сервером
          "client auth" # этот сертификат может использоваться клиентом
        ],
        "expiry": "87600h"
      }
    }
  }
}
```

Это чисто служебный файл, в котором указываются параметры сертификатов и время жизни (87600h — 10 лет). **`usages`** — это галочки, которые утилита физически проставит в паспорте компонента.
- Если вы не пропишете здесь `client auth`, то утилита создаст сертификат, но когда воркер покажет его мастеру, мастер скажет что сертификат подлинный, но в нем **нет галочки**, разрешающей использовать его для авторизации клиента и не пропустит.

>2) Далее создаем главный сертификат кластера — ca (Certificate Authority) удостоверяющий центр, которым будем подписывать другие сертификаты компонентов. `ca-csr.json`:

```json
{
  "CN": "Kubernetes-CA",
  "key": { "algo": "rsa", "size": 2048 },
  "names": [{ "C": "one", "L": "two", "O": "Kubernetes", "OU": "three" }]
}
```

Команда для генерации:

```bash
cfssl genkey -initca ca-csr.json | cfssljson -bare ca
```

Произошла следующая цепочка событий:

1. Утилита `cfssl` прочитала вашу анкету `ca-csr.json`.
2. Она сгенерировала секретный ключ `ca-key.pem`.
3. На основе этого ключа она составила **официальный бинарный запрос на подпись сертификата — Certificate Signing Request (CSR)** `ca.csr`.
4. Поскольку вы передали флаг `-initca` (самоподпись), утилита сама же этот запрос и подписала, выдав финальный паспорт `ca.pem`

Мы будем создавать `json csr` конфиги для каждого сертификата, csr означает **Запрос на подпись сертификата** (то есть файлы .csr, которые появятся после использования утилит создания сертификатов, это не сами сертификаты, а только запросы, которые должен подписать удостоверяющий центр ca.pem, после чего появится еще 2 файла уже с расширением .pem, один публичный ключ, второй приватный). 

Но кто тогда подпишет csr сертификата удостоверяющего центра? Это исключение, ca-csr является самоподписным сертификатом (ключ `-initca` в команде). После создания главного сертификата, приступим к созданию сертификатов на каждый компонент кластера.


>3) **Сертификат администратора (для `kubectl`). `admin-csr.json`:**

```json
{
  "CN": "admin",
  "key": { "algo": "rsa", "size": 2048 },
  "names": [{ "C": "one", "L": "two", "O": "system:masters", "OU": "three" }]
}
```

Выдает права абсолютного корня кластера за счет того, что поле организации `O` указывает на системную группу супер-админов `system:masters`.

Команда для генерации:

```bash
cfssl gencert -ca=ca.pem -ca-key=ca-key.pem -config=ca-config.json -profile=kubernetes admin-csr.json | cfssljson -bare admin
```


>4) **Сертификат первой worker node (для `kubelet`). `node-0-csr.json`:**

```json
{
  "CN": "system:node:node-0",
  "key": { "algo": "rsa", "size": 2048 },
  "names": [{ "C": "one", "L": "two", "O": "system:nodes", "OU": "three" }]
}
```

Пропуск для первой рабочей ноды. Строка `O: system:nodes` дает право выполнять контейнеры, а префикс `CN: system:node:...` включает защиту Node Restriction.

Команда для генерации:

```bash
cfssl gencert -ca=ca.pem -ca-key=ca-key.pem -config=ca-config.json -profile=kubernetes -hostname=node-0,192.168.100.11 node-0-csr.json | cfssljson -bare node-0
```


>5) **Сертификат второй worker node (для `kubelet`). `node-1-csr.json`:**

```json
{
  "CN": "system:node:node-1",
  "key": { "algo": "rsa", "size": 2048 },
  "names": [{ "C": "one", "L": "two", "O": "system:nodes", "OU": "three" }]
}
```

Точно такой же сертификат, но персонально для второй ноды.

Команда для генерации:

```bash
cfssl gencert -ca=ca.pem -ca-key=ca-key.pem -config=ca-config.json -profile=kubernetes -hostname=node-1,192.168.100.12 node-1-csr.json | cfssljson -bare node-1
```


>6) **Сертификат диспетчера задач (для `kube-controller-manager`). `kube-controller-manager-csr.json`:**

```json
{
  "CN": "system:kube-controller-manager",
  "key": { "algo": "rsa", "size": 2048 },
  "names": [{ "C": "one", "L": "two", "O": "system:kube-controller-manager", "OU": "three" }]
}
```

Разрешает этому бинарнику на мастере следить за жизнедеятельностью подов и пересоздавать их в случае аварий. Строка `O: system:kube-controller-manager`.

Команда для генерации:

```bash
cfssl gencert -ca=ca.pem -ca-key=ca-key.pem -config=ca-config.json -profile=kubernetes kube-controller-manager-csr.json | cfssljson -bare kube-controller-manager
```


>7) **Сертификат сетевого диспетчера (для `kube-proxy`). `kube-proxy-csr.json`:**

```json
{
  "CN": "system:kube-proxy",
  "key": { "algo": "rsa", "size": 2048 },
  "names": [{ "C": "one", "L": "two", "O": "system:node-proxier", "OU": "three" }]
}
```

Дает право сетевому агенту на воркерах читать карту распределения сервисов кластера, чтобы нарезать правила для `iptables` хоста. Строка `O: system:node-proxier`.

Команда для генерации:

```bash
cfssl gencert -ca=ca.pem -ca-key=ca-key.pem -config=ca-config.json -profile=kubernetes kube-proxy-csr.json | cfssljson -bare kube-proxy
```


>8) **Сертификат планировщика (для `kube-scheduler`). `kube-scheduler-csr.json`:**

```json
{
  "CN": "system:kube-scheduler",
  "key": { "algo": "rsa", "size": 2048 },
  "names": [{ "C": "one", "L": "two", "O": "system:kube-scheduler", "OU": "three" }]
}
```

Дает право бинарнику оценивать свободную память нод и принудительно назначать, на какой воркер приземлится новый контейнер. Строка `O: system:kube-scheduler`.

Команда для генерации:

```bash
cfssl gencert -ca=ca.pem -ca-key=ca-key.pem -config=ca-config.json -profile=kubernetes kube-scheduler-csr.json | cfssljson -bare kube-scheduler
```


>9) **Сертификат для сервисных аккаунтов. `service-account-csr.json`:**

```json
{
  "CN": "service-accounts",
  "key": { "algo": "rsa", "size": 2048 },
  "names": [{ "C": "one", "L": "two", "O": "Kubernetes", "OU": "three" }]
}
```

Обычная пара ключей без прав RBAC, которая нужна мастеру исключительно для того, чтобы подписывать внутренние токены безопасности подов.

Команда для генерации:

```bash
cfssl gencert -ca=ca.pem -ca-key=ca-key.pem -config=ca-config.json -profile=kubernetes service-account-csr.json | cfssljson -bare service-account
```


>10) **Главный сертификат сервера (для `kube-apiserver`). `kubernetes-csr.json`:**

```json
{
  "CN": "kubernetes",
  "key": { "algo": "rsa", "size": 2048 },
  "names": [{ "C": "one", "L": "two", "O": "Kubernetes", "OU": "three" }]
}
```

В отличие от остальных, он будет работать в режиме **Server Auth**, подтверждая подлинность самого Кубера для всех внешних клиентов. `O: Kubernetes`.

Команда для генерации:

```bash
cfssl gencert -ca=ca.pem -ca-key=ca-key.pem -config=ca-config.json -profile=kubernetes -hostname=10.32.0.1,192.168.100.10,127.0.0.1,kubernetes,kubernetes.default,kubernetes.default.svc,kubernetes.default.svc.cluster.local kubernetes-csr.json | cfssljson -bare kubernetes
```


Для каждого компонента мы генерировали четыре файла. Вот что они значат на физическом уровне:

1. **`*-csr.json` (Конфигурация запроса на подпись):** Текстовый файл-конфигурация. В нем описывается: Я компонент X, хочу себе сертификат с такими-то параметрами.
2. `*.csr` (Certificate Signing Request / Запрос на подпись): Промежуточный ключ, который генерируют утилиты, но он еще не является сертификатом, его должен заверить главный ключ CA (Certificate Authority)
3. **`*-key.pem` (Private Key / Приватный ключ):** Самый секретный файл. Это ваша цифровая подпись. С его помощью компонент шифрует пакеты. Его **нельзя** никому передавать. Если злоумышленник получит `kubernetes-key.pem`, он сможет управлять вашим кластером.
4. **`*.pem` (Certificate / Сертификат):** Это ваш публичный паспорт, подписанный Корневым Центром (CA). Компонент показывает его при подключении. В нем написано: _«Я такой-то компонент кластера, мой публичный ключ такой-то, а подлинность моей личности подтверждает CA»_

После выполнения команд введите `ls -la`. Игнорируйте файлы `.json` и `.csr` (это были просто черновики). Ваша цель — **18 главных файлов криптографии** (9 секретных ключей и 9 публичных паспортов)

- `ca.pem` и `ca-key.pem` — Главная печать и её ключ.
- `admin.pem` и `admin-key.pem` — Паспорт и ключ администратора.
- `k8s-worker-1.pem` и `k8s-worker-1-key.pem` — Паспорт и ключ Воркера 1.
- `k8s-worker-2.pem` и `k8s-worker-2-key.pem` — Паспорт и ключ Воркера 2.
- `kube-controller-manager.pem` и `kube-controller-manager-key.pem` — Паспорт и ключ контроллера.
- `kube-proxy.pem` и `kube-proxy-key.pem` — Паспорт и ключ прокси.
- `kube-scheduler.pem` и `kube-scheduler-key.pem` — Паспорт и ключ планировщика.
- `kubernetes.pem` и `kubernetes-key.pem` — Главный серверный паспорт API-сервера.
- `service-account.pem` и `service-account-key.pem` — Пара ключей подписи внутренних токенов

#### Разбор конфигурационных файлов

- **`"algo": "rsa"`**: Указывает алгоритм асимметричного шифрования **RSA** (Rivest–Shamir–Adleman). Это классический стандарт, на котором держится безопасность большинства сайтов в интернете. Асимметричное шифрование означает, что данные, зашифрованные публичным ключом, можно расшифровать _только_ приватным ключом, и наоборот.

- **`"size": 2048`**: Длина ключа в битах (2048 бит). Это размер огромного случайного числа, которое ядро сгенерирует на основе пула энтропии (`/dev/urandom`). Ключ длиной 2048 бит считается криптографически стойким и безопасным: чтобы взломать его методом перебора (Brute Force) современным суперкомпьютерам понадобятся миллионы лет.

Зачем нужны поля `C, L, O, OU`? 
Это стандартные поля для любых мировых сертификатов (стандарт X.509). Они обозначают:
- **`C` (Country):** Страна.
- **`L` (Locality):** Город.
- **`O` (Organization):** Организация/Компания.
- **`OU` (Organizational Unit):** Отдел.

Должны ли поля C, L, OU совпадать у всех? 
Для работы Kubernetes эти поля (`C`, `L`, `OU`) **вообще не важны**. Вы можете в одном конфиге написать одно, а в другом совершенно другое, или вообще их стереть. Кластер будет работать идеально, потому что ядро Kubernetes на эти три поля даже не смотрит. Они нужны просто для красоты, чтобы при просмотре сертификата человеком было понятно, чей он. Поэтому их традиционно делают одинаковыми у всех конфигов, чтобы не путаться.

А вот поле **`O` — это самое главное рабочее поле для Kubernetes**.

Когда вы придете к API-серверу Кубера с сертификатом администратора, Кубер **НЕ будет** смотреть на имя `CN: admin`. Ему плевать на имя. Кубер заглянет строго в поле **`O`**.
- Если он увидит там строку **`system:masters`** и поймет, этот сертификат принадлежит организации супер-админов. Ему можно всё.
- Если воркер покажет сертификат, где в поле `O` написано **`system:nodes`**, Кубер поймет что это рабочая нода. Ей разрешено только запускать контейнеры, но смотреть чужие секреты запрещено.
